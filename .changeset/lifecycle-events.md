Start a workflow when another one finishes, without the finishing workflow knowing about it. When a run settles, the engine publishes `run.completed:<workflow>` or `run.failed:<workflow>` with the run's input, output, error, tags and search attributes, and `@OnWorkflowCompleted(Workflow, { where, input })` / `@OnWorkflowFailed(Workflow, { where, input, statuses })` subscribe to it. With a class ref, the subscriber's `run` input is type-checked against the event, or against what `input` builds from it.

Delivery is exactly once per subscriber and settled run: the terminal status write also tags the run `durable:lifecycle:pending`, the live publish swaps it for `durable:triggered:<subscriber>` tags, and the `durable:work` tick (`engine.sweepLifecycleEvents`) publishes any run still marked after 30 seconds. Subscriber run ids are deterministic (`evt:<runId>:<kind>:<subscriber>`), so publishing twice starts each subscriber once. A subscriber whose `where` throws or whose start fails is reported as `run.trigger_failed` and not retried.

`onEvent` entries can now be `{ event, where, input }`. The two runs are linked both ways: the run detail carries `triggered` and `triggeredBy` (read from the run rows, so any process can answer), and the dashboard's run header lists them. `engine.triggeredRuns(runId)`, `triggeredRunsOf(run)` and `lifecycleSourceOf(run)` give the same links in code. The engine emits `run.triggered` and `run.trigger_failed`, counted by the metrics as `runs.triggered` and `runs.triggerFailed`.

Retention skips a run still tagged `durable:lifecycle:pending`, so a short retention window cannot delete a run before its lifecycle event is published.

Subscriptions are announced by the fleet, so a subscriber registered on only some instances (or during a rolling deploy) is not lost. The terminal write also tags the run `durable:lifecycle:owed:<subscriber>` (`LIFECYCLE_OWED_TAG_PREFIX`) for every subscriber registered locally or announced by the fleet, read with a 5s cache from two places: the lifecycle subscription registry in the state store, which works with every transport (one completed `__lifecycle_registry` run per engine with `onEvent` subscriptions, `LIFECYCLE_REGISTRY_WORKFLOW`, `lifecycleRegistryRunId`, `LIFECYCLE_REGISTRY_TAG`, `LifecycleRegistryEntry`, `lifecycleRegistrySubscriptions`, rewritten every 10s by the `durable:work` tick through `engine.heartbeatLifecycleRegistry()`, live for 35s, deleted 10 minutes after its engine stopped: `LIFECYCLE_REGISTRY_HEARTBEAT_MS`, `LIFECYCLE_REGISTRY_TTL_MS`, `LIFECYCLE_REGISTRY_STALE_MS`), and the new `subscribes` field of a worker descriptor's `registrations` (how a Python subscriber is announced). Registry runs are kept by retention (`retentionKeeps`) and left out of a policy's `maxCount`, and `engine.listRuns` / `countRuns` / `runFacets` / `runValueFacets` leave them out through the new `RunQuery.excludeWorkflows` (`NOT IN`, implemented by the in-memory and Lucid stores) unless the query names the registry workflow. A run is owed only to the subscribers that serve its namespace (`engine.lifecycleSubscribers(workflow, kind, namespace)`): the settling instance's own when it has no namespace or the run's, registry rows of instances in that namespace or with none (`LifecycleRegistryEntry.engineNamespace`, `null` for an instance with no namespace, read by `lifecycleRegistryNamespace`), and descriptors serving it, so an instance with no namespace no longer marks a tenant's run owed to another tenant's subscribers. Each instance starts only the owed subscribers it has and drops `durable:lifecycle:pending` with the last owed tag; an owed subscriber no live worker announces is dropped after 24 hours (`LIFECYCLE_ORPHAN_MS`) with `run.trigger_failed`.

`ctx.waitForRun(runId, { timeoutMs })` (and `ctx.waitForRun(WorkflowClass, runId)`, typed as `LifecycleEventOf<C>`) waits durably for any run to settle, following a continue-as-new chain to its last run (at most 100 hops), and resolves with its lifecycle event, at once if it already settled. An unknown run throws a non-retryable `FatalError`; the timer sweep (`engine.sweepRunWaits`) wakes waiters whose wake was lost.

`engine.republishLifecycle({ runId } | { workflow, kind, since, until, limit })`, with an optional `subscriber`, publishes settled runs' lifecycle events again (idempotent, returns `{ runs, started, failed }`) to backfill a subscriber registered after the runs settled. It starts the subscribers registered on the calling instance and marks any other one owed again, for the sweep of an instance that has it. The workflow form takes a `namespace`. It is also a run gateway verb carried by the tenant proxy in both forms (`{ kind: 'republishLifecycle', target }`: a run is ownership-checked like `retry`, a workflow's runs are forced to the tenant's namespace), the `durable:lifecycle:republish` ace command, `POST /runs/:id/republish-lifecycle`, and a "Republish lifecycle event" action in the dashboard, whose run detail now carries `lifecycleSubscribers`.

`eventBatch` takes a `key` (debounce and batch), so events coalesce per key into their own accumulator (`__evtacc__:<target>#<key>`; the unkeyed id is unchanged), and is now a `static workflow` option. `@OnWorkflowCompleted` / `@OnWorkflowFailed` take `debounce: { windowMs, key }` or `batch: { maxSize, windowMs, key }`, with `key` typed by the subscriber's input and a batched subscriber typed as `{ events }`.

A Python workflow (Aviary's `durable-worker`: `@worker.workflow("notify", on_workflow_completed="ingest", on_workflow_failed=..., on_event=[...])`) announces `subscribes` and is started by name, under the deterministic lifecycle id with the event as input, by an engine that reaches its worker group (registered with `registerRemote`, or a live group of that name); `publishEvent` starts an announced `on_event` subscriber the same way. A subscriber another Node engine announces is left to it, and one registered locally is started once, through its own `onEvent`.

The lifecycle sweep pages through marked runs (at most 1000 read per tick) and skips the ones it cannot act on, so runs owed only to subscribers on other instances no longer starve the ones it can publish. `sweepRunWaits` skips waiters on runs still in flight, reads at most 1000 waited-on runs per call and resumes where the last call stopped.

With `attachDurableOtel`, a lifecycle subscriber's run span links to its source run's span and carries `durable.lifecycle.source_run_id` and `durable.lifecycle.kind`. The bridge installs `engine.setRunTraceparent`, the run's first suspend write (or else its settling write) records its root span as a `durable:lifecycle:trace:<traceparent>` tag (`LIFECYCLE_TRACE_TAG_PREFIX`, `lifecycleTraceparentOf`), so the link holds when the run settles on an instance that never saw its first turn, and the subscriber's `run.started` carries it as `sourceTraceparent`. The metrics count subscriber runs by settled workflow and subscriber (`triggeredBySubscriber`, `durable_runs_triggered_total{workflow,subscriber}`).

`engine.workflowLifecycle(workflow)` (`WorkflowLifecycleLinks` of `LifecycleSubscriptionLink`, plus `parseLifecycleEvent`) answers who starts whom: the workflows that start when it settles and the ones whose settling starts it, local and announced, with their `where`, `input` and debounce/batch. `engine.workflowLifecycle(workflow, { namespace })` keeps only one namespace's subscriptions. It is a run gateway verb (`workflowLifecycle`, carried by the tenant proxy and scoped to the tenant's namespace, like the run detail's lifecycle links), `GET /workflows/:name/lifecycle`, the run detail's `workflowLifecycle`, and a workflow page in the dashboard (`#/workflow/<name>`).

A tenant proxy talking to a control plane older than `republishLifecycle` or `workflowLifecycle` rejects at once with the new `RunGatewayError` (code `unsupported-request`, `<verb> is not supported by this server`), which every refused `ProxyRunGateway` call now rejects with (`RunGatewayErrorCode`); the dashboard answers `501`.

The dashboard shows where every lifecycle feature stands. The run detail (`GET /runs/:id`, from `engine.getRunDetail`) carries `lifecycleDeliveries` (`LifecycleDelivery`, `LifecycleDeliveryState`, built by `lifecycleDeliveriesOf`): per subscriber of a settled run, `started` with its run and status, `owed` with since when (`owedSince`) and, when no live instance has it, when the sweep drops it (`orphanAt`), `coalesced` with the accumulator run when derivable, or `not-started`; `waitsFor` and `awaitedBy` (`RunWaitLink`), the `ctx.waitForRun` waits on either side of a run with the other run's status; and `triggeredBy` (`LifecycleSource`) adds the source run's `status`, `namespace` and the `traceId` of its recorded span. The detail's ETag covers those reads of other runs (`extendEtag`), and a tenant proxy keeps them to the tenant's own runs. The run list names a `ctx.waitForRun` wait as `waiting: { on: 'run', name: <runId> }`, and has a "lifecycle pending" chip selecting runs tagged `durable:lifecycle:pending`. The run header shows "started by `<run>` on completed / failed" with the source's status and a copyable trace id, "Waiting for run `<id>`", "Awaited by", and a "Lifecycle subscribers" list beside the Republish action. `GET /workflows/:name/lifecycle` adds `triggerCounts` (started and failed per subscriber, counted by the dashboard's process), shown on the workflow page, from the new `triggerFailedBySubscriber` metric (`durable_runs_trigger_failed_total{workflow,subscriber}`).

The Telescope "Workflows" dashboard adds "Failed triggers" (recent `run.trigger_failed`) and "Owed lifecycle events" (settled runs still owed past the 30s grace) to "Needs attention", and a "Lifecycle" section with "Lifecycle triggers over time" and "Triggered by subscriber", backed by the new `durable.failedTriggers`, `durable.owedLifecycle` and `durable.lifecycleTriggers` providers (`durableFailedTriggersProvider`, `durableOwedLifecycleProvider`, `durableLifecycleTriggersProvider`). The diagnostics bridge stamps a lifecycle subscriber's events with `lifecycleSourceRunId` and `lifecycleKind`, and `dedupeRunEvents` keeps apart two subscribers of one run whose events share an instant. "Needs attention" also has an "Owed runs" stat (`durable.owedLifecycle` with `{ metric: 'count' }`, one `countRuns`). The opt-in `DurableTelescopeWatcher` (wired to Telescope's `safeRecord`, with `buildDurableEntry`, `durableEntryTags`, `DURABLE_DIAGNOSTIC_EVENTS`, `traceIdOfTraceparent`, `TelescopeRecordInput`, `WatcherContext`) records durable's diagnostics events with the same tags as the NestJS watcher (`run:<id>`, `parent:`, `workflow:`, `triggered`, `trigger_failed`, `subscriber:<name>`, `lifecycle`, `source:<id>`, `sourceTrace:<id>`), claiming the `durable:*` keys so the generic watcher skips them.

A subscriber a settled run could not start (its `where` threw, its input was rejected, its start failed, or the sweep dropped it as an orphan) gets a `durable:trigger_failed:<subscriber>` tag (`LIFECYCLE_TRIGGER_FAILED_TAG_PREFIX`, `lifecycleTriggerFailedTag`) in the same tag write that drops its owed tag, removed by the write that records a later start of it; it is left out of the event's `tags`. `LifecycleDeliveryState` gains `failed` and `LifecycleDelivery` gains `error` (not stored with the run: the reason stays in the `run.trigger_failed` event), and the dashboard row shows "failed" with the reason when the page saw the event; Republish retries it. The run detail has an "Events" panel rendering the run's live stream (the last 200 events while the page is open, nothing stored), linking `run.triggered`, lifecycle-started and child runs both ways.

A run that settles before its instance has read the fleet's subscriptions (right after boot, or while the read fails) is marked `durable:lifecycle:pending` with no owed tag: its owed set is unresolved, and the first publish with a successful read (the live publish, or the sweep, which reads again on every tick while the last read failed) resolves it into owed tags for every subscriber the run's tags do not record as started or failed (`deliveredSubscribersOf`). Until then an instance starts its own subscribers and keeps the run marked. Each sweep also heals the runs settled in the last two minutes (`LIFECYCLE_HEAL_WINDOW_MS`, up to 100 per subscribed workflow, through the new `RunQuery.updatedAfter`, implemented by the in-memory and Lucid stores and covered by the conformance suite): a subscriber announced just after a run settled is started or marked owed, once per instance. A subscriber that appears later is a backfill for `republishLifecycle`. The subscription registry is read page by page, so a fleet past 1000 rows is read whole.

Publishers of one run take turns: the live publish, the sweep, the heal and a republish each hold the run's lease (owner `<instanceId>#lifecycle#<uuid>`) while they read the run, start subscribers and write its tags, asking again after 50 to 800 ms and leaving a still-held run to the sweep (a republish reports it in `failed` with subscriber `*`); an explicit retry of a failed run waits for a publish holding it. `run.triggered` and `run.trigger_failed` are emitted only by the write that adds the subscriber's tag. A debounce/batch accumulator drops an event it already took (named by the subscriber run id it would start; an event published with the same `id`, for `publishEvent`), remembering the last 200 across bursts, so a routed event never counts twice.

`republishLifecycle` reads the fleet's subscriptions afresh and refuses a `subscriber` that does not subscribe to the run's ending (`subscriber <name> does not subscribe to <event>` in `failed`, nothing marked). Over the run gateway, the control plane also refuses, with the new `bad-request` code (`400` in the dashboard), a `limit` that is not a positive integer and a `subscriber` that does not subscribe in the tenant's namespace, and clamps `limit` to 1000.

Two `debounce`/`batch` configs on one workflow match when their mode, window, size and `key` source text match, so separately written identical `key` arrows no longer throw; keys whose source differs still do.
