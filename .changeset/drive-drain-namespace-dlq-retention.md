'@adonis-agora/durable': minor
---

New `config/durable.ts` options and one behaviour change.

- **`drive: false`**: the process never executes the runs it starts, requeues or recovers; they stay `pending` for `node ace durable:work` (which drives through its poll whatever the value) or a control plane. Pair it with `consumers: 'never'` on web pods whose workflow bodies are heavy, instead of a hand-written no-op `runDispatcher`. An explicit `runDispatcher` still wins, and `drive: false` together with `worker: { embedded: true }` throws at boot.
- **Drain on shutdown, always.** The provider now drains the engine on every app shutdown before it closes the transport and control plane, not only when the embedded worker runs. A web process mid-turn no longer has its transport closed under it. The budget is `worker.drainTimeoutMs` when set, else the new `drainTimeoutMs` (default 10 000), and the embedded loop is not drained twice. The `app.terminating(...)` hook the production docs used to suggest is no longer needed.
- **`queues`**: flow-control queues declared in config, registered on the engine at boot (`engine.registerQueue` shape). A queue named twice throws.
- **`deadLetterWorkflow`**: a fleet-default dead-letter workflow in config, a per-workflow `deadLetterWorkflow` (`static workflow`, `register`/`registerRemote` options), or an inline `deadLetter(ctx, dead)` method on a `BaseWorkflow` (registered as `<name>.dlq`). A run that goes `dead` starts it as `dlq:<runId>` with a `DeadLetter` input (`{ deadRunId, workflow, input, error }`), in the dead run's namespace. Declaring both the method and the option throws at boot.
- **Retention by count**: a `retention.policies` entry takes `maxCount` (keep the N newest runs of its status set within its scope), alone or with `maxAge` (a run goes once it is past either). A policy with neither now throws at boot.

**Behaviour change: an absent `namespace` is the `'default'` pool on a standalone engine.** It used to make the engine an operator that drove, recovered and resumed the runs of every namespace, so a standalone process with no namespace sharing a store with other pools (a laptop pointed at a shared database, a second app) would execute their runs. It now drives only `'default'` runs and rows written before namespaces existed (which read back as `'default'`). Only multi-pool deployments sharing one store are affected: a standalone process that was meant to drive every pool must become a `role: 'control-plane'`, which keeps the operator meaning when its namespace is unset. `scopeReads: true` with no `namespace` on a standalone engine now fences reads to `'default'` (it fenced nothing before).
