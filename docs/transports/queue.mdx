The `queue` driver carries steps over [`@adonisjs/queue`](https://github.com/adonisjs/queue) — the path for steps that run in another process. It rides any `@adonisjs/queue` adapter (Redis, a database adapter, or the fake adapter in tests), so it reuses the queue infrastructure you already run.

It ships **inside `@adonis-agora/durable`** — there's nothing extra to install. `@adonisjs/queue` is an optional peer, imported lazily only when you select the `queue` transport, so install and configure it where you use the driver:

```bash
npm i @adonisjs/queue
node ace configure @adonisjs/queue
```

You define the adapter and its host/credentials **once**, in `config/queue.ts` (the standard `@adonisjs/queue` place), as a named connection. The durable `queue` transport then just references that connection **by name** — exactly like `stores.lucid({ connection })` or `stores.redis({ connection })`:

```ts title="config/queue.ts"
import { defineConfig, drivers } from '@adonisjs/queue'

export default defineConfig({
  default: 'redis',
  adapters: {
    redis: drivers.redis({ connectionName: 'main' }), // @adonisjs/redis connection
  },
})
```

## How it works

- A dispatched `ctx.step` goes to a **per-name** task queue: `<prefix>:tasks:<token>`, where the routing token is `tenantGroup(sanitizeQueueToken(name), partition)` — a dedicated queue per handler name (with an optional `partition` suffix), never a single shared group queue.
- A worker that serves that name consumes it, runs the handler, and adds the result to the shared `<prefix>:results` queue.
- The engine-side instance consumes results and checkpoints them.
- Liveness flows on `<prefix>:heartbeats`; cross-instance control on `<prefix>:control`.

The default `prefix` is `durable` and the default `pollIntervalMs` is `200`.

Run **one instance engine-side** (consumes results) and **one or more worker processes** that serve the step handlers (each subscribes to a task queue per handler name it serves):

```ts title="config/durable.ts (engine side)"
import { defineConfig, transports } from '@adonis-agora/durable'

export default defineConfig({
  transport: 'queue',
  transports: {
    // References the connection named in config/queue.ts. Omit `connection` to
    // use that file's `default`.
    queue: transports.queue({ connection: 'redis' }),
  },
})
```

The idiomatic worker is the bundled ace command, which boots the app and reads the same `config/durable.ts` — no adapter wiring to repeat. It serves whatever step handlers the app registers (the `app/steps` [`@Step`/`defineStep` convention](/docs/durable/concepts/workflows-and-steps#serving-a-step-handler) is auto-discovered), subscribing to a task queue per served name:

```bash title="a separate worker process"
node ace durable:work
```

<Callout type="info">
Both the engine and the `durable:work` worker resolve the adapter from the `connection` you named in `config/queue.ts`, so the driver + host live in exactly one place. For a non-Adonis setup you can still construct the primitive `QueueTransport` (exported from `@adonis-agora/durable`) by hand and hand it a raw `@adonisjs/queue` adapter via its `adapter` option.
</Callout>

## Supported `@adonisjs/queue` versions

The transport works with `@adonisjs/queue` **0.6** (`@boringnode/queue` 0.6) and **0.7** (`@boringnode/queue` 0.9). It drives the adapter directly — not the queue manager's `Worker` — and picks the right adapter contract from each claim: on 0.7 every claim carries a lease token, which is what completes, retries or fails it.

Upgrading an app from 0.6 to 0.7:

- Follow the [`@adonisjs/queue` 0.7 upgrade notes](https://github.com/adonisjs/queue/releases/tag/v0.7.0): stop every process on the old version (do not run both side by side), then run `node ace queue:migrate` before starting the new ones. Durable keeps no schedules or dedup ids in the queue backend, so its own queues need nothing more — but your app's jobs and schedules do.
- `defaultJobOptions` (`maxRetries`, `retry`, `timeout`, `failOnTimeout`) and `worker.unknownJobRetries` only apply to jobs run by `queue:work`. Durable's jobs are never run by it: retries, timeouts and backoff stay governed by the step options (`retries`, `timeoutMs`…) and this transport's settings.
- Don't point `queue:work` at durable's queues (`<prefix>:…`). On 0.7 a worker that meets a job whose class it doesn't know puts it back in the queue up to `unknownJobRetries` times, then fails it.

## Options — `transports.queue(config)`

| Option | Default | Description |
| --- | --- | --- |
| `connection` | `config/queue.ts` `default` | Name of the `@adonisjs/queue` connection (a key of that file's `adapters`) whose adapter this transport uses. |
| `adapter` | — | Escape hatch: a raw `@adonisjs/queue` adapter factory, used instead of resolving from `config/queue.ts`. Takes precedence over `connection`. |
| `group` | — | **Deprecated.** Steps route by handler name, so an instance serves whatever names it registers — no group to declare. Accepted for back-compat and otherwise ignored; use `partition` for isolation. |
| `partition` | — | Optional isolation partition suffixing every per-handler task queue this worker subscribes to (`<name>@<partition>`), matching a dispatch's `partition` — so one backend can host several pools serving the same handler name without their tasks crossing. |
| `namespace` | from the engine | Worker-pool namespace folded into every queue name. Setting it here is explicit and wins over the engine's propagation of `config.namespace` — see [Namespaces](#namespaces--sharing-one-broker-across-pools). |
| `prefix` | `'durable'` | Namespaces the queues (`<prefix>:tasks:<token>`, `<prefix>:results`, …). |
| `pollIntervalMs` | `200` | Poll interval in ms between queue reads. |
| `concurrency` | `1` | How many jobs of one step name this worker runs at once: a number (fixed), or `'adaptive'` / `{ mode: 'adaptive', min, max, start, tickMs, ramCeilingPct, cpuCeilingPct }` to let a control loop move it — see [Adaptive concurrency](#adaptive-concurrency). More slots share one poll loop, so raising it adds no polling. |
| `resultConcurrency` | `1` | How many step results the engine side settles at once. |
| `idleBackoffMax` | `4` | Idle backoff for the task, heartbeat and control loops, in poll intervals: empty polls double the sleep up to this multiple (800ms at the default interval), and a found job resets it. `1` disables it. The results loop never backs off. |
| `stalledCheckIntervalMs` | `30_000` | How often the stalled-claim reclaim sweep runs. `0` disables it entirely. |
| `stalledThresholdMs` | `120_000` (2min) | How long a claim may go without being renewed before the sweep presumes its worker dead and re-delivers the job. `1_800_000` (30min) on an adapter without `renewJobs`. |
| `maxStalledCount` | `3` | How many times one job may be reclaimed before it is failed permanently — the bound on a poison job. A step task failed this way is reported to its run as a failed step (see [Poison jobs](#poison-jobs)). |
| `onError` | `console.error` | Where a poll-loop failure is reported. Point it at your app's logger. |
| `instanceId` | random uuid | Stable process id stamped on heartbeats and control messages. |
| `workerKeys` | the app database | Where the [worker advertisement](/docs/durable/transports#worker-advertisement) lives. Default: the `durable_transport_worker_keys` table through `@adonisjs/lucid`, when the app has it. Pass any `WorkerKeyStore` to keep the keys elsewhere, or `false` to advertise nothing. |
| `workerKeysConnection` | default Lucid connection | Lucid connection the default worker-key table lives on. |
| `workerKeysCacheMs` | `5000` | How long a read of the worker keys is reused. |

### Concurrency and idle polling

Every step name a worker serves gets its own task queue and poll loop. By default that loop runs **one job at a time**: a backlog of 100 `sendEmail` steps is worked through serially per worker process. Raise `concurrency` to run several at once:

```ts title="config/durable.ts"
queue: transports.queue({
  connection: 'redis',
  concurrency: 8,        // up to 8 jobs of each step name in flight per worker
  resultConcurrency: 8,  // the engine settles up to 8 results at once (wide fans)
}),
```

The slots share the step's single poll loop — it keeps popping while a slot is free and waits for one to free when all are busy — so `concurrency` costs no extra polling. Every in-flight claim is renewed, and `close()` waits (within its 5s budget) for all of them, like a single one. Fleet-wide parallelism for a step is `concurrency × worker processes`; use a [flow-control queue](/docs/durable/reliability/flow-control) when you need a cap across the fleet.

#### Adaptive concurrency

Pass `'adaptive'` instead of a number to let the worker tune its own limit. It is the same controller the [BullMQ transport](/docs/durable/transports/bullmq#concurrency) uses: every `tickMs` it grows the limit by one while steps saturate it at a steady latency, shrinks it by the latency gradient when steps start to queue, sheds one on a >20% error rate, a stall or the CPU ceiling, and cuts it by 20% when RSS reaches `ramCeilingPct` of the memory limit (the cgroup limit, else the host's memory).

```ts title="config/durable.ts"
queue: transports.queue({
  connection: 'redis',
  concurrency: { mode: 'adaptive', min: 1, max: 16, start: 2, tickMs: 2000, ramCeilingPct: 85, cpuCeilingPct: 90 },
}),
```

| Field | Default | Description |
| --- | --- | --- |
| `min` | `1` | Floor the limit never goes below. |
| `max` | `32` | Ceiling the limit never exceeds. |
| `start` | `min` | Initial limit, clamped into `[min, max]`. |
| `tickMs` | `2000` | Control-loop period. |
| `ramCeilingPct` | `85` | RSS percent of the memory limit at which the hard brake fires. |
| `cpuCeilingPct` | off | Process CPU percent (normalised over cores) above which the limit never grows and sheds one. |

A non-finite or out-of-range field falls back to its default. One controller serves every step name of the worker, and each step name's task loop reads the live limit on every poll, so a move applies at once — a lower limit lets jobs already running finish and stops taking new ones until in-flight work is under it. Only step durations feed the latency window. The results, heartbeat and control loops are not affected (`resultConcurrency` stays fixed).

Whatever the mode, each worker's [liveness heartbeat](#worker-health) carries the controller's snapshot — mode and live limit (with `min`/`max` when adaptive), in-flight count, RSS, CPU, throughput, p95 and the last adjustment with its reason — which the [dashboard's worker cards](/docs/durable/observability/dashboard#fleet-and-topology) render.

#### Idle polling

Polling is the cost of a backend-agnostic queue: each loop asks the adapter for a job every `pollIntervalMs`, and a worker serving 30 step names runs 30 task loops. So idle task, heartbeat and control loops **back off** — the sleep doubles after each empty poll up to `idleBackoffMax × pollIntervalMs` (800ms by default), and the first job found snaps the loop back to the base interval and drains the backlog without sleeping. The price is up to that much pickup latency for the first job after a quiet spell; set `idleBackoffMax: 1` for the old fixed cadence. The results loop never backs off, since every step's result is on its workflow's critical path.

### Worker advertisement

A queue hands each job to one consumer, so a worker's descriptor and heartbeat cannot travel over it:
every engine has to read every worker's. They go to a key store instead — by default the app database's
`durable_transport_worker_keys` table (created on first use, and by the migration `configure`
publishes), the same one the [db transport](/docs/durable/transports/db) uses. With no database and no
`workerKeys`, nothing is advertised and the engine routes without descriptors, as before.

### Worker health

Every worker process beats a liveness key for each step name it serves — `<prefix>-worker-heartbeat:<token>:<instanceId>` in the worker-key store, refreshed every 10s and live for 35s, carrying the `WorkerStatus` snapshot described [above](#adaptive-concurrency). A process that only produces (a `console`/`repl` process with [deferred consumers](#consumers--why-a-node-ace-script-does-not-drain-the-queue)) beats nothing until it starts consuming.

From those keys and the queue, the transport implements `groupHealth`, so `engine.workerHealth()`, the dashboard's `/api/workers` and `/api/health` and the [Telescope](/docs/durable/observability/telescope) worker panel report queue-transport groups:

- `liveWorkers`: the unexpired liveness keys of the group, with each worker's `instanceId`, `lastBeatAt` and `status`. A worker that dies drops out within 35s.
- `depth`: the task queue's **pending** jobs, from the adapter's `sizeOf`. This is narrower than BullMQ's depth (waiting + active + delayed + prioritized): the `@adonisjs/queue` adapter contract has no count for jobs in flight or delayed retries, so those are not included. `depth > 0` with no live worker is still the alert state, since pending jobs are the ones no worker has picked up.

`groupHealth` needs the worker-key store: with `workerKeys: false` (or no database and no store), no worker can advertise liveness, so the transport does not implement it and the panels stay empty rather than flagging every group as starved.

### Stalled-job reclaim

A worker that throws is easy: the job is redelivered a poll interval later. A worker that *vanishes* — killed mid-step, its pod evicted — throws nothing and leaves a claim that nobody will ever complete. The reclaim sweep is the net for that case: every `stalledCheckIntervalMs`, claims older than `stalledThresholdMs` are re-delivered.

While a step runs, the transport **renews its claim** every half `stalledThresholdMs` through the adapter's `renewJobs` — the same heartbeat `@adonisjs/queue`'s own worker runs, on both 0.6 and 0.7. A claim's age therefore measures how long its worker has been **silent**, not how long the step has run:

- a dead worker's job is re-delivered within about `stalledThresholdMs` (default **2 minutes**) plus one sweep interval;
- a healthy step is never re-delivered, however long it runs — a 3-hour import keeps its claim.

What *can* still look like a dead worker is a live one whose event loop is **blocked** longer than the threshold — a synchronous, CPU-heavy step body starves the renewal timer. Keep heavy work async or off the main thread, or raise the threshold above the longest block:

```ts
transports.queue({
  connection: 'redis',
  stalledThresholdMs: 5 * 60 * 1000, // a report renderer blocks the loop for up to ~3 minutes
  maxStalledCount: 3,
  onError: (err) => logger.error({ err }, 'durable queue transport'),
})
```

When a renewal finds a claim it no longer holds — the sweep re-delivered it while this worker was silent — the transport reports it to `onError` (`lost N of M claim(s) …`): the step may be running twice, so make steps idempotent on the `stepId` they receive.

<Callout type="info" title="Upgrading from a release without renewal">
Older releases never renewed a claim and defaulted the threshold to 30 minutes. During a rolling deploy, an **old** worker's long step can be reclaimed by a **new** instance's 2-minute sweep. That is the same at-least-once double-run the threshold always allowed — idempotent steps are safe — but pin `stalledThresholdMs` to the old value until every worker runs the new release if your steps are expensive to repeat. An adapter without `renewJobs` (only a custom one) keeps the 30-minute default and the old rule: raise the threshold above your longest step.
</Callout>

Set `stalledCheckIntervalMs: 0` to switch the sweep off — reasonable when an adapter already redelivers stalled jobs itself. Adapters that cannot report stalled jobs are detected and skipped silently, in which case [`engine.redispatchPending(runId)`](/docs/durable/reliability/failure-modes#lost-remote-dispatch-the-run-suspends-and-nothing-auto-redrives-it) is the recovery path.

### Poison jobs

A job reclaimed more than `maxStalledCount` times is one whose workers keep vanishing while they hold it, so the sweep fails it instead of re-delivering it again. For a step task, the transport then publishes a failed result for that step (`remote step worker failed: stalled more than N times`, marked retryable) on the results queue, the same bridge the BullMQ transport runs for a task job that fails terminally. The engine treats it like any failed attempt: it re-dispatches while the step has `retries` left, then fails the step into the workflow (a `try/catch` around the step sees a `RemoteStepError`; uncaught, the run fails). Without this, the run would wait on that step forever.

This needs `@adonisjs/queue` **0.7**: there the adapter hands a job that stalled too often back to the transport to fail. On **0.6** the adapter deletes such a job inside its own sweep and returns only a count, so the transport never sees it and no result is published. On 0.6, set the step's `timeoutMs` or the engine's `remoteRedispatchMs` (see [lost remote dispatch](/docs/durable/reliability/failure-modes#lost-remote-dispatch-the-run-suspends-and-nothing-auto-redrives-it)) so such a step does not wait forever. Stalled result, heartbeat and control jobs are failed without publishing anything.

### `consumers` — why a `node ace` script does not drain the queue

Broker queues are point-to-point: a job goes to exactly one consumer. That makes a short-lived process subscribing to them actively harmful — it claims step jobs it then dies holding, steals results addressed to the long-lived engine, and, with jobs queued, never exits because the drain loop keeps feeding it.

So by default a **`console` or `repl` process does not start the broker consumer loops**. It can still dispatch runs and read the store — it is a pure producer. `durable:work` re-enables consumption for itself, so the worker command behaves identically either way, and web and test processes always consume eagerly.

What this changes in practice: a `node ace` script that starts a run and waits for a remote step to come back will wait forever, because nothing in that process is listening for the result. Either let the worker fleet do the work (start the run and exit), or opt the process back in:

```ts title="config/durable.ts"
export default defineConfig({
  consumers: 'always', // every booted process consumes eagerly
})
```

Reach for `'always'` only for a script that genuinely must round-trip a remote step inline, and be aware it competes with the real worker fleet for jobs while it runs. In-process transports (`memory`, `event-emitter`) are unaffected — there is no broker to compete for.

`transports.queue(config)` returns the lazy driver thunk used in `config/durable.ts`; the underlying class is `QueueTransport`, also exported from `@adonis-agora/durable` for constructing a worker-side instance directly.

## Queue naming

| Queue | Direction | Purpose |
| --- | --- | --- |
| `<prefix>:tasks:<token>` | engine → workers | step dispatch, one queue per handler name (`tenantGroup(sanitizeQueueToken(name), partition)`) |
| `<prefix>:results` | workers → engine | step results |
| `<prefix>:heartbeats` | workers → engine | liveness for `timeoutMs` steps |
| `<prefix>:control` | bidirectional | lifecycle events + cancellation (best-effort) |

Because the payload is the documented `RemoteTask` / `StepResult` JSON, multiple worker processes can share the same queues — scale out by running more `durable:work` processes that serve the same step names.

## Namespaces — sharing one broker across pools

A worker-pool `namespace` (set on the engine in `config/durable.ts`) partitions a deployment so several non-interchangeable pools can safely share **one** state store **and one** broker without stealing each other's work. The engine stamps the namespace on every run, scopes its poll/recovery/timer paths to it, and **propagates it to the transport** — so the queue transport folds the namespace into every queue name:

```ts title="config/durable.ts"
import { defineConfig, transports } from '@adonis-agora/durable'

export default defineConfig({
  namespace: 'tenant-a', // ← partitions the store AND the queue names
  transport: 'queue',
  transports: { queue: transports.queue({ connection: 'redis' }) },
})
```

| `namespace` | Effective queue names |
| --- | --- |
| `'default'` (or unset) | `durable:tasks:<token>`, `durable:results`, … — **byte-identical** to a single-pool deployment |
| `'tenant-a'` | `durable-tenant-a:tasks:<token>`, `durable-tenant-a:results`, … |

A non-`'default'` namespace inserts a `-<namespace>` segment after the prefix; `'default'` (and unset) keeps the exact un-namespaced names, so **existing deployments are unaffected — zero migration**. An engine and its `durable:work` workers must run the same namespace to share queues.

<Callout type="info">
The same segmentation applies to the in-process `eventEmitter` transport (it scopes its internal event channels), so two engines on different namespaces sharing one process bus don't cross-process each other's tasks. A `namespace` passed explicitly to a transport's constructor takes precedence over the engine's propagation.
</Callout>

### Filtering runs by namespace

Read surfaces (the dashboard, `getRun`, the CLI) stay namespace-agnostic by default. To scope a run search to one pool, pass `namespace` to a `RunQuery` — it is ANDed with the other predicates only when provided:

```ts
// Only runs in the 'tenant-a' pool, ANDed with the other filters.
await engine.store.listRuns({ namespace: 'tenant-a', status: 'running' })
```
