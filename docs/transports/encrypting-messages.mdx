A broker is not a trust boundary. Whoever can read Redis, the `@adonisjs/queue` backend or the `db` transport's tables (a shared instance, a leaked password, a backup, an SSRF) would otherwise read every step's input and output, and whoever can write there could hand a worker a step of their choosing or settle someone else's step. So durable can seal what it puts on a transport:

- **Encrypted**: the data of a run (input, output, error, progress, workflow history, signal payloads, tenant tokens, request and reply bodies, engine events) is encrypted with AES-256-GCM. Nothing of it is readable on the broker.
- **Authenticated**: a message that was not sealed with the key, was changed, or was moved into another run, step or message kind is refused.
- **Routable**: the fields a broker routes on (run id, step id, handler name, group, attempt, priority) stay in clear, and are bound into the authentication.

This covers messages in transit and while they wait on the broker. To encrypt what the **store** keeps (run inputs, checkpoints), see [Encrypting payloads at rest](/docs/durable/stores#encrypting-payloads-at-rest).

## Turning it on: two steps

A process on 1.1 or earlier cannot read a sealed message (see [why](#why-two-steps)), so sealing is turned on in two steps:

1. **Upgrade every process to 1.2.1 or later.** Nothing else changes: messages are still sent plain, and every process already opens sealed ones.
2. **Turn sealing on**, once no older process is left:

```ts title="config/durable.ts"
export default defineConfig({
  messages: { seal: true }, // every broker transport and the control plane
  // …
})
```

Sealing becomes the default in the next major, when every receiver understands it. `node ace agora:doctor` (`durable.messages`) warns while a transport still sends plain.

<Callout type="warn">
1.2.0 sealed by default. That was reverted in 1.2.1: a sealed step task reaching a 1.1 worker ran its handler with `input` undefined. If you run 1.2.0, upgrade to 1.2.1 before (or while) upgrading the rest of the fleet: 1.2.1 opens what 1.2.0 sealed.
</Callout>

## Same app: nothing else to configure

The processes of one app (web, `durable:work` workers, schedulers) share its `APP_KEY`. With `seal: true`, every broker transport (`transports.bullmq`, `transports.queue`, `transports.db`) and `controlPlanes.redis` seal their messages with a key derived from it:

```ts title="config/durable.ts"
messages: { seal: true },
transports: {
  bullmq: transports.bullmq({ connection: 'main' }), // sealed with the app key
},
controlPlane: controlPlanes.redis({ connection: 'main' }), // sealed too
```

- **Key**: AES-256-GCM, derived from `APP_KEY` with HKDF-SHA256 (purpose `agora:durable:messages`). No crypto server, no key to create, no grant.
- **Where `APP_KEY` comes from**: `config/app.ts`'s `appKey`, else the default entry of `config/encryption.ts`, else the `APP_KEY` environment variable, the same way in every Agora lib. A string or a `Secret`, at least 16 characters, never logged.
- **Boot**: each transport logs its mode once: `[@adonis-agora/durable] bullmq messages: app key (auto)` (`control plane messages: …` for the control plane). Before step 2: `bullmq messages: sent plain, sealed ones opened with app key (auto)`.
- **Without an `APP_KEY`**: the transport stays plain, with a boot warning naming the fix when `seal: true` asked for sealing. Boot never fails for it.
- **Thin workers** built without AdonisJS (`new BullMQTransport({ ... })` in a [worker runtime](/docs/durable/cluster/thin-workers)) use `process.env.APP_KEY` the same way, or `messages: { appKey }`.
- `memory` and `eventEmitter` keep everything in one process: nothing to seal.

## Through the durable control plane: nothing to configure

[Tenant pods](/docs/durable/cluster) and their control plane are different apps with different `APP_KEY`s. Their messages are sealed (with `seal: true`) with keys the **control plane owns**, one per tenant partition. The tenants need nothing beyond what tenant topology already requires (`tenant.partition` and its token): no `@adonis-agora/crypto`, no grant, no shared secret.

- **One key per tenant.** The control plane derives each tenant's key from its own secret and the tenant's partition, so every replica derives the same key and nothing is stored. Where that secret lives is up to the control plane's app (below).
- **Handed over at first use.** A tenant pod generates an ephemeral X25519 key pair and asks the control plane for its key, authenticated with its tenant token. The control plane answers only to a verified token (`verifyTenant` is required), only for the partition that token verifies to, only to a request under a minute old, and **only once** (below). The answer is the key sealed to the pod's public key (ECDH-ES, HKDF-SHA256, AES-256-GCM, bound to the request id and partition). The pod keeps the key in memory; it never travels in clear and never lands on the broker.
- **Over HTTPS when it can.** A pod that knows the control plane's URL (`tenant.url` in `config/durable.ts`, or what authkit-client knows of `urn:agora:durable`) asks at `POST <url>/__durable/message-key`, its token as a bearer: the token never crosses the broker for this. A plain `http://` URL is used only for `localhost`. If the route cannot be used (no URL, not HTTPS, unreachable, a 404 from an older control plane, an HTML answer such as a CSRF refusal), the pod says so once and asks over the broker instead, as a `messageKey` run request. The boot line says which: `control plane key (partition acme, asked over HTTPS)` or `(…, asked over the broker)`; so does the doctor. With `@adonisjs/shield`'s CSRF on, add `/__durable/message-key` to its `exceptRoutes`.
- **Each tenant only reads its own.** A message to a tenant is sealed with that tenant's key; another tenant's key does not open it. App A starting a workflow whose step runs on app B works with no configuration: A's request opens at the control plane with A's key, and the step goes to B sealed with B's key.
- **Rotation.** Every message carries its key id (`kid`). When the control plane's secret rotates, the kid changes: a pod that sees a kid it does not hold asks again, and the control plane still opens messages sealed under the previous kid (in the processes that knew it).
- **Boot lines:** `[@adonis-agora/durable] bullmq messages: control plane keys (crypto, key durable-message-keys, partition hub)` or `control plane keys (app key)` on the control plane, `control plane key (partition acme)` on a pod.

Where the control plane keeps its secret, detected through the `agora.crypto` binding (never imported):

| The control plane's app | Its tenants' keys come from | Setup |
| --- | --- | --- |
| `@adonis-agora/crypto` embedded (the Agora Hub) | an HMAC under the crypto key `durable-message-keys` (type `hmac-sha256`) in its partition; rotating that key with `crypto:keys:rotate` rotates every tenant's key | none: the key is created at boot |
| a crypto tenant of a separate crypto app | the same HMAC, through its crypto client | grant its client `crypto:hmac:durable-message-keys` (and `crypto:keys:manage:durable-message-keys` to create it at boot), or create it on the crypto server: `node ace crypto:keys:create durable-message-keys --type hmac-sha256 --application <partition>`. The boot line names what is missing. |
| no `@adonis-agora/crypto` | HKDF over its `APP_KEY`; rotating `APP_KEY` rotates every tenant's key | none (the doctor notes it) |

#### Single use, and what remains

Every key request carries a fresh random nonce and its timestamp. The control plane remembers, in a store every replica shares (Redis `SET NX` with an expiry on `bullmq`; the worker-keys table on `db`, and on `queue` when its worker keys are in the database; per process otherwise, with a boot warning), two things:

- the pair (token, nonce) for twice the one-minute freshness window: the same request seen again, at any replica, is refused;
- the token itself (its `jti` when it is a JWT, else a hash of it) for the token's remaining lifetime (its `exp`, at most a day; a minute for a token that says nothing): a second key request with the same token is refused, and logged once per partition as a possible replay.

A pod whose request is refused this way asks again with a fresh token (authkit app-call tokens are minted per request), or after the minute with a static opaque token. A long-lived JWT reused by a pod that restarts stays refused until it expires: give pods tokens minted per request. If the guard's store cannot be reached, no key is handed out (it fails closed).

What this leaves:

- **Over HTTPS**, the token is only exposed to whoever can read that HTTPS traffic (the TLS terminator, the control plane's logs). Nothing on the broker helps an attacker get a key.
- **Over the broker**, whoever reads it while a pod asks sees the pod's token. Replaying the captured request is refused. Using the token for a new key request either loses the race to the pod (refused) or wins it. In that case the pod's own request is refused and logged as a possible replay, and the attacker holds the key, so the attack is detected but not prevented. It is limited to that one tenant, and lasts until the control plane's secret rotates. The same token also lets that reader act as the tenant on run requests until it expires, as it always did. Keep tenant tokens short-lived, give pods the control plane's URL so the key is asked over HTTPS, and watch for the replay warning.

Without a token (tenant) or a key (control plane: no `APP_KEY` and no crypto), the transport stays plain and warns at boot. 1.2.x sealed this traffic with `@adonis-agora/crypto` keys of each tenant's partition instead; if you turned `seal: true` on between tenants and their control plane on 1.2, upgrade both sides together (or turn it off during the upgrade).

### Two apps on one transport without a control plane

Processes of two apps that share a broker transport directly (both `standalone`) don't share an `APP_KEY`: a message of one does not open in the other, and is refused with a warning naming the fix. Give every process of both the same `messages: { secret }` or `messages: { crypto: { cipher } }`, or connect them through a control plane.

## Options

The top-level `messages: { seal, acceptPlain }` applies to every broker transport and the control plane. Each of them also takes a `messages` option, the same modes as the other Agora libs' channels; its own values win over the top-level ones, and explicit modes win over the automatic one.

```ts title="config/durable.ts"
messages: { seal: true },
transports: {
  bullmq: transports.bullmq({
    connection: 'main',
    messages: {
      acceptPlain: false, // refuse plain messages (the default of the next major)
    },
  }),
},
controlPlane: controlPlanes.redis({ messages: { acceptPlain: false } }),
```

| Option | Default | What it does |
| --- | --- | --- |
| `seal` | `true` with an explicit `secret` / `crypto`, else `false` in 1.x | Send messages sealed. Off, they are sent plain while sealed ones are still opened (with the mode below). Default in the next major. |
| (no mode) | | The app key; between a tenant and its control plane, the control plane's per-tenant key. |
| `secret` | | A shared secret (16+ characters, a string or a `Secret`), the same in every process: each message carries an HMAC-SHA256. **Authenticated, but readable** on the broker. For processes of several apps without crypto. |
| `crypto: { cipher, key?, owns? }` | | Encrypt with an `@adonis-agora/crypto` key (`() => crypto.client!`) or your own KMS (anything with `encrypt` / `decrypt`). Every process needs both on the key (default name `durable-messages`). `owns` recognizes the cipher's ciphertexts (default `agora:ct1:<key>:`). |
| `crypto: false` | | Turns the automatic mode off: plain (warns at boot). |
| `insecure: true` | `false` | Plain messages, even with `seal: true` (warns at boot). Still opens sealed messages when this process has the key. |
| `acceptPlain` | `true` | With `seal: true`: also accept plain messages (jobs queued before sealing was on), logged once per process and kind. `false` refuses them. Without `seal: true`, plain is always accepted. |
| `appKey` | `process.env.APP_KEY` | The key of a transport built without AdonisJS. |

| | `APP_KEY` (automatic) | Shared secret | `@adonis-agora/crypto` |
| --- | --- | --- | --- |
| For | the processes of one app | any processes | any processes (explicit) |
| Config | none | `messages: { secret }` in every process | `messages: { crypto: { cipher } }` in every process |
| Messages | encrypted | readable, authenticated | encrypted |
| Rotation | rotate `APP_KEY` | rotate the secret everywhere | crypto's `crypto:keys:rotate` and audit |

```ts title="config/durable.ts (your own KMS)"
const kms = {
  encrypt: async ({ key, plaintext, aad }) => ({ ciphertext: await myKms.encrypt(key, plaintext, aad) }),
  decrypt: async ({ key, ciphertext, aad }) => ({ plaintext: await myKms.decrypt(key, ciphertext, aad) }),
}

bullmq: transports.bullmq({
  connection: 'main',
  messages: { crypto: { cipher: kms, key: 'durable', owns: (c) => c.startsWith('kms:') } },
}),
```

None of `@adonis-agora/authkit`, `@adonis-agora/authz` or `@adonis-agora/crypto` is required: the automatic mode needs only the app's `APP_KEY`.

## What is sealed

A sealed message keeps its routing fields in clear and carries everything else in one `sealed` field, `dm1.<mode>.…` (`k` app key, `t` control-plane key, `c` crypto, `s` secret). The AAD binds it to the message kind and the identity fields listed here, so a sealed input cannot be replayed into another step, run or kind.

| Message | Transports | Clear (identity in **bold**) | Sealed |
| --- | --- | --- | --- |
| Step task (`RemoteTask`) | all | **runId, seq, stepId, name, group**, attempt, priority, transport, replyTo, traceparent | input, context |
| Step result (`StepResult`) | all | **runId, seq, stepId, status**, startedAt | output, error, events |
| Heartbeat | bullmq, queue | **runId, seq, stepId, group**, at | progress |
| Workflow turn (`WorkflowTask`) | all | **taskId, runId, workflow, group**, workflowVersion, attempt, priority | input, history, pending signals |
| Workflow decision (child starts included) | all | **taskId, runId, status** | commands, output, error |
| Live step event | all | **runId, seq, name, phase**, startedAt, finishedAt | output, error, events |
| Start run (tenant → control plane) | all | **workflow, runId** | tenant token, input, tags, search attributes |
| Run request (signals, updates, cancels, reads) | all | **requestId** | tenant token, body |
| Run reply | all | **requestId** | result |
| Tenant event | all | **tenant** | event |
| Control message (events, cancel, nudges, schedule pauses) | `controlPlanes.redis`, queue, db | **from** | kind, run id, event |

On the `db` transport a sealed row keeps its routing columns and stores the seal in its data column (`input` for a task, `error` for a result: `{"$durableSealed": "dm1.…"}`), the other data columns empty; heartbeat rows carry no data there.

Not sealed, as they carry no run data: worker liveness and descriptor keys, run-dispatch nudges (a run id), inbox registrations. The [federated console](/docs/durable/observability/federated-console) channel is authenticated on its own.

## When a message is refused

A message that does not open (another key, tampered, moved, or plain with `acceptPlain: false`) is never retried, since retrying would not change the verdict, and is logged once per process, kind and reason (error code `E_DURABLE_MESSAGE_REJECTED`):

- **A step task**: its handler does not run, and the step is reported **failed (retryable)** with the reason, so its run follows its retry policy instead of waiting. On BullMQ the job also stays in the failed set for a day.
- **Anything else** (result, heartbeat, decision, event, request, reply, control): dropped. The step or request then recovers as a lost message does (step timeout, `remoteRedispatchMs`, the request's timeout).

A process never crashes on a message it cannot open.

Changing `APP_KEY` changes the key: jobs sealed before the change are refused (a step is reported failed and retried with the new key), and during a rolling deploy processes on the old and new key refuse each other's messages.

## Why two steps

A process on 1.1 or earlier does not know the `sealed` field and sees only a message's clear fields. Checked against the published 1.1.1 on one Redis:

- **A sealed step task reaching a 1.1 worker runs its handler with `input` `undefined`** (and no context), and the result it returns is taken as the step's. That is why nothing is sealed until you turn it on.
- **A 1.2.1 process with the default config talks to 1.1 as before**: a 1.1 worker runs its tasks with their real input, a 1.1 engine reads its results (both covered by a test against the published 1.1.1).
- A 1.2.1 process opens sealed messages even while it sends plain, and replies **in kind** (a plain task gets a plain result, a plain run request a plain reply).
- 1.2.x receivers fail safe: a message carrying a seal they cannot open (another key, tampered, an unknown format or version) is refused, never read as plain, and a step handler never runs on it.

After step 2, once the queues hold no job from before sealing was on, set `acceptPlain: false`: plain messages are then refused. `node ace agora:doctor` warns while a transport still accepts them. Both sealing and strict mode become the default in the next major.

## NestJS and Python workers

The NestJS `nestjs-durable` transport and the Python worker read plain messages only. A BullMQ transport (and a control plane) shared with them must stay plain: `messages: { insecure: true }`.

## Doctor

`node ace agora:doctor` reports each broker transport's mode under `durable.messages`: `app key (auto)`, `secret`, `crypto (…)`, or `plain` with the reason and the fix. It warns for a transport that still sends plain (sealing off), for a plain one, and for one that still accepts plain messages, and errors when a transport sets more than one mode.
