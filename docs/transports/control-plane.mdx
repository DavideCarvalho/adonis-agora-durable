The task [transport](/docs/durable/transports) is **point-to-point**: it carries one task to one worker and a result back. The **control plane** is a separate, *broadcast* channel across **every** engine instance (every pod). It carries what each instance may need regardless of who runs a given run:

- **Lifecycle events** — so a dashboard-only pod can live-tail a run executing on a worker pod.
  A run's own events go out one per message. Step events, which a wide fan emits two per step, go out in order in one `events` message per batch: the ones emitted while a publish is in flight share the next message (up to 500), so a fan of 40,000 steps publishes a few hundred messages instead of 80,000, each delivered to every pod. An instance that does not know the `events` kind ignores it and only misses other instances' step events, which no engine logic reads.
- **Cancellation** — so the pod actually running a run learns it was cancelled elsewhere.
- **Enqueue nudges** — so a worker picks up a freshly enqueued run now instead of on the next poll.
- **Schedule pause/resume** — so a schedule paused or resumed at runtime (from the dashboard or the API) stops or restarts ticking on every instance. This is runtime state: a deploy resets it to the config's `paused`.

This is purely out-of-band signalling. It carries **no replay/determinism weight** — the deterministic engine never depends on it; the engine dedupes its own broadcasts by the originating `instanceId`, so a publish that Redis echoes back to its own subscriber is ignored.

## Local-only by default

Omit `controlPlane` and the engine is **local-only**: events and cancellation reach subscribers on *this* instance but don't fan out to other processes. That's exactly right for a single-instance app — no extra infrastructure.

```ts title="config/durable.ts"
import { defineConfig, transports } from '@adonis-agora/durable'

// No controlPlane → single-instance, local-only events + cancellation.
export default defineConfig({ transport: 'queue', transports: { /* ... */ } })
```

## Multi-replica: `controlPlanes.redis`

Running more than one replica? Without a control plane, a `cancel` issued on the API pod never reaches the worker pod running the run, and a dashboard pod can't live-tail runs executing elsewhere. Pick the Redis driver to fan both out over Redis pub/sub:

```ts title="config/durable.ts"
import { defineConfig, transports, controlPlanes } from '@adonis-agora/durable'

export default defineConfig({
  transport: 'queue',
  transports: { queue: transports.queue({ connection: 'redis' }) },
  // Fan out lifecycle events + cancellation across every replica.
  controlPlane: controlPlanes.redis({ connection: 'main' }),
})
```

`connection` names a connection from `config/redis.ts` (defaults to `'main'`). Like the other drivers, `@adonisjs/redis` is imported **lazily** — only when this driver is selected — so it stays an optional peer. The subscription rides that connection's own subscriber, which `@adonisjs/redis` manages and closes with the app.

| Option | Default | Meaning |
| --- | --- | --- |
| `connection` | `'main'` | `config/redis.ts` connection used for pub/sub. |
| `prefix` | `'durable'` | Channel is `` `${prefix}-control` ``, or `` `${prefix}-<namespace>-control` `` under a namespace. |
| `namespace` | the engine's `namespace` | Namespace folded into the channel this instance listens on. `'default'` keeps the bare channel. Messages about a run are still published on the run's namespace channel. |

Every instance that should hear each other must use the same channel, so give every engine (and every NestJS or Python process on the same Redis) the same `prefix`. The engine drops a message whose `from` is its own `instanceId`, so its own publishes echoed back by Redis are ignored.

<Callout type="info" title="Each namespace has its own channel">
The channel folds the engine's `namespace` in the same way the `bullmq` transport names its queues: an engine with `namespace: 'tenant-a'` listens on `durable-tenant-a-control`, and one with no namespace (or `'default'` or `''`) on `durable-control`. A Python or NestJS process pointed at the same prefix and namespace listens on the same channel. See [Python interop](/docs/durable/python).
</Callout>

### Which channel a message goes to

A message about a run (a cancel, an enqueue nudge, the run's own lifecycle events) is published on the channel of **that run's namespace**, whatever the publisher's namespace is. So a console with no namespace that cancels a run in `bulas` publishes on `durable-bulas-control`, where the `bulas` workers (Adonis, NestJS or Python) hear it at once. A message with no run (a schedule pause) or about a run of unknown namespace, and step events (which carry no namespace), go to the publisher's own channel.

```ts title="app/controllers/runs_controller.ts"
import engine from '@adonis-agora/durable/services/main'

export default class RunsController {
  // A console process with no namespace: the cancel still reaches the run's namespaced workers.
  async cancel({ params, response }: HttpContext) {
    await engine.cancel(params.id)
    return response.noContent()
  }
}
```

### What each engine observes

- **An engine with no namespace** (the operator view, such as a console over every namespace) listens on `durable-control` **and** on every namespace channel (a pattern subscription to `durable-*-control`). Its live tail and run events cover every namespace, as they would on one shared channel.
- **An engine with a namespace** listens on its own channel only, so it sees its namespace's events and nothing else.
- **An explicit `namespace` on `controlPlanes.redis(...)`** pins that one channel (`'default'` pins the bare one), with no pattern. It only picks what the instance listens on; it does not redirect what it publishes about runs.

An engine with no namespace therefore also hears cancels for runs of other namespaces. They reach `engine.onCancel` listeners like any other cancel, so a listener should act only on the runs it is executing.

Delivery is best-effort, as with any pub/sub. The cancel itself is recorded in the store first, so a worker that misses the message still finds the run cancelled at its next turn; the message only makes it immediate.

<Callout type="info">
**Interoperates with a NestJS fleet.** The channel (`` `${prefix}-control` ``) and the JSON payload match the NestJS BullMQ transport's control plane, so an AdonisJS fleet and a NestJS fleet sharing one Redis fan out across both runtimes on the same channel.
</Callout>

## Passing an instance directly

`controlPlane` also accepts a ready `ControlPlane` instance instead of a factory — useful for tests or a bespoke broker. Any object with `publishControl(msg)` and `onControl(handler)` works, as long as every instance receives every message. None of the shipped broker transports qualifies: `bullmq` has no control plane, and `queue` and `db` implement the two methods over a single-consumer queue or table, so each message reaches one instance only.

```ts
import { RedisControlPlane } from '@adonis-agora/durable'
import { Redis } from 'ioredis'

const controlPlane = new RedisControlPlane({ connection: new Redis(), prefix: 'durable' })
export default defineConfig({ controlPlane })
```

`RedisControlPlane` accepts **either** a raw `ioredis` instance (it duplicates a dedicated subscriber connection) **or** an `@adonisjs/redis` connection (which manages its own subscriber); it detects which by feature. The two carry the same messages on the same channel and differ only in who owns the subscriber connection, which only changes which connection the health check below pings.

| Constructor option | Default | Meaning |
| --- | --- | --- |
| `connection` | — (required) | A raw `ioredis` client or an `@adonisjs/redis` connection. |
| `prefix` | `'durable'` | Channel is `` `${prefix}-control` ``, or `` `${prefix}-<namespace>-control` `` under a namespace. |
| `namespace` | the engine's `namespace` | Namespace folded into the channel name. |
| `pingIntervalMs` | `30_000` | How often the watchdog pings the subscriber connection (both forms; `controlPlanes.redis({ pingIntervalMs })` too). `0` or `false` disables it. |

## Subscriber health

A pub/sub subscriber connection never writes on its own, so when a VPN, NAT gateway or idle timeout drops it silently, it stays "subscribed" while Redis has already dropped the subscription, and cancellations and live-tail events stop arriving.

- **Raw `ioredis` form.** The control plane `PING`s its dedicated subscriber every `pingIntervalMs`. A ping that fails, or takes longer than the smaller of 5 s and the interval, disconnects it so ioredis reconnects and resubscribes. The first subscriber error of each reconnect burst is logged with `console.warn`. This is the same watchdog the [`bullmq` transport](/docs/durable/transports/bullmq#subscriber-health-pingintervalms) runs.
- **`controlPlanes.redis()` (the `@adonisjs/redis` form).** The same watchdog pings the connection's own subscriber (`ioSubscriberConnection`) every `pingIntervalMs` and disconnects it on a failed or slow ping so it reconnects and resubscribes. The app-owned connection itself is never closed by the control plane.
