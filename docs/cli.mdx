`@adonis-agora/durable` ships two long-running workers (`durable:work` for a store-backed pod, `durable:worker` for a [store-less thin pod](/docs/durable/cluster/topology-and-config)), an [operator command](#operator-commands) for everything the console does, a lifecycle **republish**, a replay-fixture **exporter** and a **workflow generator**. They run against the engine (and store) your app is configured with.

```bash
node ace configure @adonis-agora/durable
```

`configure` registers the commands barrel (`@adonis-agora/durable/commands`) in `adonisrc.ts` so the commands become available to ace — there's no separate package to install.

## `durable:work` — the worker loop

The long-running worker. On an interval it picks up pending runs, recovers crashed runs, resumes due timers, sweeps execution timeouts, and fires any due [scheduled workflows](/docs/durable/authoring/scheduling). It stays alive until `SIGINT`/`SIGTERM`, then **drains** in-flight executions so a deploy hands off cleanly.

```bash
node ace durable:work
node ace durable:work --interval=500 --drain-timeout=15000
```

| Flag | Default | Description |
| --- | --- | --- |
| `--interval` | `1000` | poll interval in ms between ticks |
| `--drain-timeout` | `10000` | shutdown budget in ms, from the stop signal: the wait for the tick in flight plus the drain |

Each tick runs `engine.runPending()` → `engine.recoverIncomplete()` → `engine.resumeDueTimers()` → `engine.sweepTimeouts()` → `engine.sweepLifecycleEvents()` (owed [lifecycle events](/docs/durable/authoring/lifecycle-events#delivery-exactly-once-per-subscriber) and `ctx.waitForRun` waiters) → fire due [schedules](/docs/durable/authoring/scheduling) (the `schedules` from `config/durable.ts` merged with any colocated `static schedule`, config winning on a key collision, then the [persisted schedules](/docs/durable/authoring/persisted-schedules) when `persistedSchedules` is on) → `engine.sweepRetention()` ([retention eviction](/docs/durable/reliability/retention), self-throttled to once a minute) → `engine.sweepStalled()` (the [stalled-run pager](/docs/durable/reliability/failure-modes#the-stalled-run-pager--onstalled--stalledafter), same throttle, a no-op without listeners). Each phase is isolated: one that throws (a transient store hiccup) is logged as `tick phase <name> failed: …` and the rest of the tick still runs.

On start the loop also calls `engine.startConsumers()`. Broker transports (BullMQ, DB, queue) defer their consumer subscriptions when the app boots in the `console` or `repl` environment (the default `consumers: 'auto'` in `config/durable.ts`), so a one-shot `node ace` command (a migration, `durable:runs`, `node ace repl`) stays a pure producer and never claims jobs. `durable:work` is the process that declares itself a worker and flushes them. `consumers: 'always'` keeps consumers eager everywhere; `consumers: 'never'` defers them in every environment, web included. A custom loop built on `runWorkerLoop` gets the same behaviour; one built on `runTick` alone must call `engine.startConsumers()` itself.

On `SIGINT`/`SIGTERM` the loop stops picking up new runs, waits for the tick in flight, then calls `engine.drain()` with whatever is left of `--drain-timeout`. A tick that outlives the whole budget is abandoned with a warning instead of holding the pod past its termination grace period, so keep `--drain-timeout` below your orchestrator's grace period.

Run this as a dedicated process (or several) when you split web from worker. A single-process app can run the same loop in the web process with `worker: { embedded: true }` instead. One of the two is required: without a worker loop, started runs still execute in-process, but sleeps and retry timers never wake, crashed runs are never recovered and schedules never fire (see [Workers](/docs/durable/concepts/durability#workers-a-process-that-drains-pending-runs)).

<Callout type="info">
Any [scheduled workflows](/docs/durable/authoring/scheduling) registered under `schedules` in `config/durable.ts` are fired by this loop (the tick's 5th phase), so you need at least one `durable:work` process, or a web process with the [embedded worker](/docs/durable/authoring/scheduling#running-the-loop-in-the-web-process), running for them to start. This is also where a [queue](/docs/durable/transports/queue) or [DB](/docs/durable/transports/db) transport worker registers its handlers for a group.
</Callout>

## `durable:worker` — the store-less worker

The worker for a `topology: 'tenant'` pod: it serves step bodies and never touches a state store. It boots the container-bound `WorkerRuntime`, registers every handler under `stepsPath` (default `app/steps`; every directory when it's an array), advertises its descriptor and heartbeat so the control plane can route to it, and drains on `SIGINT`/`SIGTERM`.

```bash
node ace durable:worker
```

It takes no flags — everything comes from `config/durable.ts` (`partition`, which falls back to `namespace` and then `'default'`; `namespace`; `transport`; `stepsPath`; `workflowsPath`, whose workflow names it advertises in the descriptor). On a `topology: 'tenant'` pod it uses the runtime the provider bound, which publishes the descriptor and heartbeat on the shared Redis. On any other topology it builds a self-contained runtime from the configured transport whose advertising is a no-op, and it throws when that transport cannot serve handlers (no `handle()`). Running it on a store-backed topology logs a warning and points you at `durable:work`; see [Thin workers](/docs/durable/cluster/thin-workers) for the full topology.

## Operator commands

Everything the [console](/docs/durable/observability/dashboard) does is also an ace command. Each one runs the console's own handler, so it validates, answers and refuses exactly like the console: the same filters, the same `redact` hooks, the same `404` for an unknown run.

| Console | Command |
| --- | --- |
| Runs list, filters | `durable:runs` |
| Run detail | `durable:runs:show <id>` |
| Fan members | `durable:runs:fan <id> <group>` |
| Filter pickers (counts per value) | `durable:runs:values <field>` |
| Published event value | `durable:runs:event <id> <key>` |
| Retry | `durable:runs:retry <id>` |
| Fix and replay | `durable:runs:replay <id> --input '<json>'` |
| Redispatch a lost step | `durable:runs:redispatch <id>` |
| Cancel / cancel + undo | `durable:runs:cancel <id> [--compensate]` |
| Continue from a breakpoint | `durable:runs:continue <id>` |
| Send a signal | `durable:runs:signal <id> <token> [--payload '<json>']` |
| Send an update | `durable:runs:update <id> <name> [--arg '<json>']` |
| Complete / fail a task | `durable:tasks:complete <runId> <name>` / `durable:tasks:fail <runId> <name>` |
| Bulk retry / cancel | `durable:runs:bulk <retry\|cancel> [filters]` |
| Lifecycle links of a workflow | `durable:workflows:lifecycle <name>` |
| Republish a lifecycle event | `durable:lifecycle:republish --run <id>` |
| Schedules | `durable:schedules` |
| Pause / resume / run now | `durable:schedules:pause <key>` / `:resume <key>` / `:trigger <key>` |
| Workers panel | `durable:workers` |
| Health | `durable:health` |

What they share:

- **`--json`** prints the console's JSON answer (`{ data, meta }` for a list) instead of a table.
- **Exit code `1`** on any refusal: an unknown run, a bad flag, a token the run is not waiting on, a declined confirmation.
- **Confirmation.** `durable:runs:cancel`, `durable:runs:redispatch`, `durable:tasks:fail` and `durable:runs:bulk` ask before acting. `--force` skips the question; without a terminal (CI, a cron) they refuse unless you pass `--force`.
- **Audit.** Every action goes through the console's [`audit` hook](/docs/durable/observability/dashboard#request-guards-and-audit) (or the log line) before it runs, with the actor `cli:<os user>`, the method `CLI` and the path `<command> <target>`.
- **Tenancy.** With [tenancy](/docs/durable/concepts/tenancy) on, a command reads every tenant; `--tenant <id>` confines it to one, like the console's organization picker. Without tenancy, `--tenant` is refused.
- **Topology.** On a store-less `tenant` pod the commands go through the run gateway, like the console there; what the gateway cannot do answers the console's `404` / `501`.

They boot the app but start no worker and no server. An action that resumes a run hands it to the workers the same way the console does.

### Run filters

`durable:runs`, `durable:runs:values` and `durable:runs:bulk` take the console's run filter. Several values, repeated or comma separated, match any of them; different flags combine.

| Flag | Matches |
| --- | --- |
| `--status` | `pending` / `running` / `suspended` / `blocked` / `cancelling` / `completed` / `failed` / `cancelled` / `dead` |
| `--workflow` | workflow name |
| `--tag` | a tag the run carries |
| `--namespace` | worker namespace |
| `--origin` | origin attribution |
| `--attr` | a search-attribute predicate `key:op:value` (`tier:eq:pro`, `amount:gte:100`, `tier:in:pro\|enterprise`); repeat to AND them |
| `--created-after` / `--created-before` | creation time, ISO date or date-time |

```bash
node ace durable:runs --status failed,dead --workflow checkout
node ace durable:runs:values status --created-after 2026-11-01
node ace durable:runs:values attr.tier --workflow checkout
```

## `durable:runs` — list runs

Lists runs, newest first.

```bash
node ace durable:runs
node ace durable:runs --status failed
node ace durable:runs --workflow checkout --page 2 --size 100
node ace durable:runs --json
```

| Flag | Default | Description |
| --- | --- | --- |
| [run filters](#run-filters) | — | `--status`, `--workflow`, `--tag`, … |
| `--page` | `1` | page, 1-based |
| `--size` | `50` | rows per page, at most `200` |
| `--stale` | — | show only runs that look stranded. Bare `--stale` uses the 15-minute default; `--stale=1h` or `--stale=90s` sets your own threshold. |

The table has the columns `RUN`, `WORKFLOW`, `STATUS`, `UPDATED`, `RECOVERY` and `PENDING`, then the page and the total:

```text
RUN        WORKFLOW  STATUS     UPDATED  RECOVERY  PENDING
ord-42     checkout  suspended  4h32m    -         4h32m (attempt 1)
ord-43     checkout  suspended  41m3s    -         41m3s (attempt 1, hb 12s)
ord-40     checkout  completed  2d6h     -         -
page 1 of 1 (3 total)
```

Every row carries liveness signals: how long ago the run was updated, how many times recovery has picked it up, and the age of its oldest `pending` remote step. `suspended` alone cannot tell a run mid-step apart from a run whose dispatch was lost.

`--stale` is the query that separates them. It keeps the runs whose oldest pending remote step is older than the threshold, [the stranded signature](/docs/durable/reliability/failure-modes#the-stranded-signature), and prints a recovery hint for each one. A step whose worker [heartbeat](/docs/durable/reliability/failure-modes) is younger than the threshold is left out however old the step is: a beating worker is mid-flight, and re-driving it would run it twice.

```bash
# What has been sitting on a remote step for over an hour?
node ace durable:runs --stale=1h
```

The threshold is a single-unit duration: `ms`, `s`, `m`, `h` or `d` (`90s`, `15m`, `4h`, `2d`). Anything else (`--stale=15mins`) falls back to the 15-minute default. Without `--status`, `--stale` reads only `running` / `suspended` / `cancelling` runs, and it applies to the page it reads, so raise `--size` for a wide sweep. Set the threshold above your longest legitimate step that does not heartbeat.

With `--json` each row also carries `pending`: the oldest pending remote step (`seq`, `name`, `attempts`, `ageMs`, `heartbeatAgeMs`), or `null`.

For the listing to show runs across processes, the engine must be backed by a [persistent store](/docs/durable/stores/lucid); the in-memory store only sees this process's runs.

## `durable:runs:show` — one run

```bash
node ace durable:runs:show ord-42
node ace durable:runs:show ord-42 --json
node ace durable:runs:show ord-42 --field run.output     # one value, in full
node ace durable:runs:show ord-42 --field timeline.3.error
```

Prints the run (status, namespace, tags, what it is waiting on, input, output, error) and its step timeline, then its wide fans and child runs. A fan with more than 50 members is summarized; `--full` lists every member in the timeline instead, and `durable:runs:fan <id> <group>` pages through one (`--failed` for the failed members, `--page`, `--size` up to `500`).

## `durable:runs:values` — count runs by a field

```bash
node ace durable:runs:values status
node ace durable:runs:values workflow --status failed
node ace durable:runs:values attr            # search-attribute keys
node ace durable:runs:values attr.tier       # one key's values
```

Counts the runs matching the [run filters](#run-filters) by `status`, `workflow`, `namespace`, `tag`, `attr` or `attr.<key>`. `--limit` (default `20`) and `--search` narrow the values.

## `durable:runs:event` — a published value

```bash
node ace durable:runs:event ord-42 progress
```

Prints the latest value the run published for that key with `ctx.setEvent`. It has no side effect.

## Run actions

```bash
node ace durable:runs:retry ord-42
node ace durable:runs:replay ord-42 --input '{"sku":"A-1","qty":2}'
node ace durable:runs:redispatch ord-42
node ace durable:runs:cancel ord-42 --compensate
node ace durable:runs:continue ord-42
node ace durable:runs:signal ord-42 approved --payload '{"by":"ana"}'
node ace durable:runs:update ord-42 setPriority --arg '"high"'
node ace durable:tasks:complete ord-42 kyc --result '{"ok":true}'
node ace durable:tasks:fail ord-42 kyc --error 'document rejected'
```

- **`durable:runs:retry`** puts a failed, dead or stuck run back to `pending`: a worker replays its completed steps from their checkpoints and runs the failed one again with a fresh budget. Handy for a [dead](/docs/durable/reliability/dead-letter) run once you have shipped a fix.
- **`durable:runs:replay`** starts a fresh run of the same workflow with a corrected `--input` (JSON, required) and prints its id. The original run stays as it is.
- **`durable:runs:redispatch`** sends a run's pending remote steps to their workers again, for a step whose job was lost. A step a worker is still running runs twice, so it asks first.
- **`durable:runs:cancel`** cancels the run; `--compensate` also runs the compensations of its completed steps ([sagas](/docs/durable/reliability/sagas)). Asks first.
- **`durable:runs:continue`** resumes a run paused at `ctx.breakpoint()`, and fails when it is not paused at one.
- **`durable:runs:signal`** delivers `--payload` (JSON) to a run waiting on that token (`ctx.waitForSignal`). A token the run is not waiting on is refused, and the error lists the ones it waits on; `--buffer` keeps the signal for the run's next wait instead.
- **`durable:runs:update`** delivers `--arg` (JSON) to the run's `ctx.onUpdate(name)`. The workflow's validator decides; a rejection fails with its reason.
- **`durable:tasks:complete`** / **`durable:tasks:fail`** report on a [`ctx.task`](/docs/durable/authoring/external-tasks). When the run is not waiting on the task yet, the completion is kept until it is. `durable:tasks:fail` asks first.

Payloads are capped at 1 MiB, like the console's.

## `durable:runs:bulk` — act on a filter

```bash
# What would be retried?
node ace durable:runs:bulk retry --status failed --workflow checkout --dry-run

node ace durable:runs:bulk retry --status failed --workflow checkout --force
node ace durable:runs:bulk cancel --tag import-2026-11 --compensate
```

Retries or cancels every run matching the [run filters](#run-filters), at most 500. A run that cannot take the action (already settled, for a cancel) is skipped; the result reports how many matched and how many it applied to. `--dry-run` lists the matching runs and stops. Without `--dry-run` it asks first, naming how many runs it will touch; with no filter that is every run, up to 500.

## Schedules

```bash
node ace durable:schedules
node ace durable:schedules --workflow nightly-report --sort -nextFireAt
node ace durable:schedules:trigger nightly-report
node ace durable:schedules:pause nightly-report
node ace durable:schedules:resume nightly-report
```

`durable:schedules` lists the [schedules](/docs/durable/authoring/scheduling) the worker ticks (`config/durable.ts` plus the colocated `static schedule`s): cadence, paused, the current window's last and next fire, and that window's run status. Filters: `--workflow`, `--namespace`, `--paused true|false`; `--sort` by `key` (default), `workflow`, `nextFireAt` or `lastFireAt` (`-` for descending); `--page`, `--size` (default `100`, at most `200`). A pause set at runtime lives in the running workers, so the listing shows the configured state.

`durable:schedules:trigger` fires the current window now. It is idempotent: a window that already fired answers its existing run.

`durable:schedules:pause` / `:resume` broadcast the change on the [control plane](/docs/durable/transports/control-plane) to every ticking worker, and wait for it to go out before the command exits. Without a control plane the change would reach no worker, so they refuse. Like the console's, it is a runtime override: the next deploy goes back to the config.

## Workers and health

```bash
node ace durable:workers
node ace durable:health
node ace durable:health --json
```

`durable:workers` lists every worker group with its queue depth and each live worker's last heartbeat. `durable:health` prints, per group, the backlog, the live workers and whether it is **stalled** (work queued, no live worker), then how many runs are pending, dead and blocked. It exits `1` when a group is stalled, so it works as a probe.

## `durable:workflows:lifecycle` — lifecycle links

```bash
node ace durable:workflows:lifecycle ingestion
```

Lists the workflows that start when this one settles and the ones whose settling starts it ([lifecycle events](/docs/durable/authoring/lifecycle-events)), and whether each subscription is registered in this app.

## `durable:lifecycle:republish` — republish lifecycle events

Publishes settled runs' [lifecycle events](/docs/durable/authoring/lifecycle-events#republishing-and-backfilling) again through `engine.republishLifecycle`: a backfill for a subscriber registered after the runs settled, or a retry of one that failed. A subscriber run that already exists is not started again. The subscribers this app can deliver to are started (the ones registered in it, and [Python subscribers](/docs/durable/python#starting-on-another-workflows-lifecycle) whose worker it reaches); any other one is marked owed, and the lifecycle sweep of an instance that has it starts it. A `--subscriber` that does not subscribe to the runs' ending is reported as failed and nothing is marked. The lifecycle sweep heals only runs settled in the last two minutes, so this is how a subscriber deployed later reaches older runs.

```bash
# One run, to every subscriber it has not started yet.
node ace durable:lifecycle:republish --run ingest-42

# Every ingestion that failed in January, to the pager only.
node ace durable:lifecycle:republish --workflow ingestion --kind failed \
  --since 2026-01-01 --until 2026-02-01 --subscriber ingestion-pager
```

| Flag | Meaning |
| --- | --- |
| `--run` | One settled run id. |
| `--workflow` | Every settled run of this workflow, paged through the store. |
| `--since` / `--until` | With `--workflow`: runs settled at or after / at or before this ISO date or date-time. |
| `--kind` | With `--workflow`: `completed` or `failed` (failed, cancelled and dead). Both when absent. |
| `--limit` | With `--workflow`: at most this many runs. Default 1000. |
| `--subscriber` | Only this subscribing workflow. |

`--run` refuses a run that has not settled. It prints how many runs it published and subscriber runs it started, then one line per subscriber it could not start (`--json` for the result object), and exits `1` when any failed or the flags name no target.

## `durable:export` — capture a replay fixture

Exports a run's replayable history — the run row plus its full checkpoint timeline — as JSON, for the [replay-CI loop](/docs/durable/testing#replay-ci--assertreplayable). Commit the file and assert it with `assertReplayable(register, parseRunHistory(json))`: a code change that renames, reorders or removes a step at a position the history already recorded then fails the build instead of corrupting an in-flight run on deploy.

```bash
node ace durable:export ord-42                                       # JSON to stdout
node ace durable:export ord-42 --out tests/fixtures/checkout.json    # or to a file
```

| Flag | Default | Description |
| --- | --- | --- |
| `--out` | — | write the fixture to this file instead of stdout |

An unknown run id exits `1` with an error. In code, the same capture is `captureHistory(engine, runId)` from `@adonis-agora/durable/testing`.

## `make:workflow` — scaffold a workflow class

Scaffolds a `BaseWorkflow` subclass under `app/workflows/`, the parallel to `@adonisjs/queue`'s `make:job`. The generated class is auto-registered on the engine at boot — see [app/workflows & make:workflow](/docs/durable/authoring/app-workflows).

```bash
node ace make:workflow order
```

The name may carry the `Workflow` suffix or not: `order`, `Order`, `OrderWorkflow` and `order_workflow` all write `app/workflows/order_workflow.ts` with the class `OrderWorkflow` and the registered name `'order'`. The class extends `BaseWorkflow` with a `static workflow = { name, version }` identity and a `run(ctx, input)` method; standard generator flags (such as `--force`) are passed through to the stub.

## Building your own

The pieces these commands are made of are exported from `@adonis-agora/durable`, so a custom worker process or admin script composes them instead of re-implementing the loop:

| Export | What it does |
| --- | --- |
| `runWorkerLoop(engine, opts)` | the whole `durable:work` loop, including `startConsumers()` and graceful drain (`WorkerLoopOptions`: `intervalMs`, `drainTimeoutMs`, `stopSignal`, `schedules`, `logger`) |
| `runTick(engine, opts)` | one tick of it — pending, recovery, timers, timeouts, schedules, retention, stalled sweep; returns a `TickResult` with per-phase counts and the caught phase `errors` |
| `listRuns(source, opts)` | a recent-runs query (`ListRunsOptions`: `status`, `statuses`, `workflow`, `limit`); `source` is any `RunLister`, so an engine or a raw `StateStore` |
| `attachLiveness(engine, runs)` | annotate runs with update age, recovery attempts and pending-step age |
| `filterStale(liveRuns, thresholdMs)` / `DEFAULT_STALE_MS` | the `--stale` predicate and its 15-minute default |
| `renderRunsTable(liveRuns)` / `staleHint(runId)` | the terminal table and the per-run retry hint |
| `retryRun(engine, runId)` | `engine.requeue(runId)` |
| `parseDurationMs(input)` | parse `'1h'` / `'90s'` the way `--stale` does |

For example, an ops endpoint that reports stranded runs without shelling out to ace:

```ts title="app/controllers/ops_controller.ts"
import type { HttpContext } from '@adonisjs/core/http'
import { DEFAULT_STALE_MS, attachLiveness, filterStale, listRuns } from '@adonis-agora/durable'
import engine from '@adonis-agora/durable/services/main'

export default class OpsController {
  async strandedRuns({ response }: HttpContext) {
    const runs = await listRuns(engine, { statuses: ['running', 'suspended'], limit: 200 })
    const stale = filterStale(await attachLiveness(engine, runs), DEFAULT_STALE_MS)

    return response.ok({ stranded: stale.map(({ run }) => run.id) })
  }
}
```
