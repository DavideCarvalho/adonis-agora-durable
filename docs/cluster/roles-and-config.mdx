`config/durable.ts` is a **role-discriminated union**. You pick the topology with a single `role` field, and TypeScript narrows the accepted shape on the `role` literal — so an invalid combination (a store-less `tenant` pod that names a store) is a **compile error**, not a runtime surprise.

## Standalone (the default)

Omit `role` entirely and you get `standalone` — a control plane plus an embedded worker, identical to a config written before roles existed.

```ts title="config/durable.ts"
import { defineConfig, transports, stores } from '@adonis-agora/durable'

export default defineConfig({
  // role: 'standalone' is the default — you can omit it
  transport: 'queue',
  transports: { queue: transports.queue({ connection: 'redis', group: 'durable' }) },
  store: 'lucid',
  stores: { lucid: stores.lucid({ connection: 'pg' }) },
})
```

## Control plane

A pure coordinator: it owns the store and the transport, dispatches work, recovers crashes, fires timers, prunes retention, and answers thin-pod requests — but runs **no** embedded worker. Both `store` and `transport` are **required** here.

```ts title="config/durable.ts (control plane)"
import { defineConfig, transports, stores } from '@adonis-agora/durable'
import { hmacTenantVerifier } from '@adonis-agora/durable'

export default defineConfig({
  role: 'control-plane',
  transport: 'bullmq',
  transports: { bullmq: transports.bullmq({ connection: { host: '127.0.0.1', port: 6379 } }) },
  store: 'lucid',
  stores: { lucid: stores.lucid({ connection: 'pg' }) },
  // Optional: verify signed tenant tokens on incoming wire requests (see below)
  verifyTenant: hmacTenantVerifier(process.env.DURABLE_TENANT_SECRET!),
})
```

<Callout type="info">
For **cross-ecosystem** fleets (a Python or NestJS worker on the same control plane), select the [`bullmq` transport](/docs/durable/cluster/interop) — it speaks the aviary wire byte-for-byte. Store-less `tenant` pods also need `bullmq`: it is the only bundled transport that carries the run-request methods a `ProxyRunGateway` and the control plane's `RunRequestResponder` round-trip over. The [`queue`](/docs/durable/transports/queue) and [`db`](/docs/durable/transports/db) transports can still move step execution off the control plane to store-backed workers, but they cannot host `tenant` pods.
</Callout>

A `control-plane` serves no `app/steps` in-process (only `standalone` embeds a worker), and its engine uses a no-op run dispatcher: `start()` persists the run as `pending` and returns, and the `durable:work` dispatch/recovery/timers loop drives it from there instead of running the body inline on the request. The `RunRequestResponder` that answers tenant pods starts only when the selected transport carries the run-request methods; on any other transport the control plane simply has no tenant-facing surface.

## Tenant (store-less thin pod)

A `tenant` pod **never owns a store**. Everything round-trips over the wire via the `ProxyRunGateway`. The isolation is a **compile-time fact** — `store` and `stores` are typed `never`, so naming one fails to type-check:

```ts title="config/durable.ts (tenant)"
import { defineConfig, transports } from '@adonis-agora/durable'

export default defineConfig({
  role: 'tenant',
  transport: 'bullmq',
  transports: { bullmq: transports.bullmq({ connection: process.env.REDIS_URL }) },
  partition: 'acme-corp',            // which tenant this pod serves (required) — see Tenancy
  tenant: { token: process.env.DURABLE_TENANT_TOKEN }, // its signed claim
  requestTimeoutMs: 10_000,          // ProxyRunGateway round-trip timeout
  // store: 'lucid'                  // ❌ compile error — a tenant pod may not name a store
})
```

<Callout type="warn">
The three layers of store-less isolation: **(1) type** — a `tenant` config cannot mention a store; **(2) container** — the provider registers no store binding for the tenant role, so resolving one throws; **(3) object** — the `WorkerRuntime` and `ProxyRunGateway` have no store field at all.
</Callout>

## What each role validates

The checks split into compile-time (the config's type) and boot-time (the provider, when it builds the role's objects):

| `role` | Requires | Forbids | Checked at boot |
| --- | --- | --- | --- |
| `standalone` (or omitted) | nothing — no `store` selects the in-memory store, no `transport` the in-memory transport | — | — |
| `control-plane` | `store` **and** `transport` (both typed required) | — | The responder is started only on a transport with the run-request methods. |
| `tenant` | `transport` and `partition` (both typed required) | `store`, `stores` (typed `never`) | Resolving the `RunGateway` throws when the transport lacks the store-less methods (`dispatchStartRun`, `dispatchRunRequest`, `onRunReply`, `onTenantEvent`). Resolving the worker runtime throws when the transport cannot serve handlers (`handle()`). No engine and no store are bound, so resolving either throws. |

`partition` is the axis a `tenant` pod is named by: it suffixes the pod's `<name>@<partition>` routing tokens and is the tenant the proxy claims on the wire when no token is set. `namespace` stays a separate, optional field on every role (the operator's run scope); a tenant pod passes it to its transport and worker runtime. What each axis actually partitions is [Tenancy](/docs/durable/concepts/tenancy).

## Worker vs api — the entrypoint decides

A `tenant` pod's *shape* is not another config field — it's **which process you launch**. AdonisJS already separates the HTTP server from ace commands, and durable leans on exactly that:

<Tabs items={['Worker pod', 'API / dashboard pod']}>

<Tab value="Worker pod">

A store-less **task consumer**. It registers `app/steps` (served by the transport) and advertises `app/workflows` names in its descriptor, subscribes their `<name>@<tenant>` queues, executes bodies, and publishes results. It owns no store.

```bash
node ace durable:worker
```

`durable:worker` is the store-less loop — distinct from `durable:work` (the store-backed dispatch/recovery/timers loop). It stays alive until `SIGINT`/`SIGTERM`, then drains.

</Tab>

<Tab value="API / dashboard pod">

The ordinary **HTTP server**. Every durable read, control action, and run-start it performs is turned into a wire request answered by the control plane — through the very same `RunGateway` the dashboard and your routes already use, so no code changes.

```bash
node bin/server.js
```

Mount the [dashboard](/docs/durable/observability/dashboard) and it works unchanged — its reads proxy to the control plane over the wire.

</Tab>

</Tabs>

Run both processes on one pod if you want (less isolated; usually kept separate).

## Reading and steering runs: `runGateway`

Every role exposes the same read/control surface, the `RunGateway`, from `services/main`:

```ts title="app/controllers/runs_controller.ts"
import { runGateway } from '@adonis-agora/durable/services/main'
import type { HttpContext } from '@adonisjs/core/http'

export default class RunsController {
  async show({ params, response }: HttpContext) {
    const run = await runGateway.getRun(params.id)
    if (!run) return response.notFound()

    return response.ok({ run, timeline: await runGateway.getCheckpoints(params.id) })
  }

  async approve({ params, response }: HttpContext) {
    await runGateway.signal(params.id, `approve:${params.id}`, { by: 'ops' })
    return response.accepted({})
  }
}
```

**This is what makes application code portable across the three roles.** On a store role the gateway reads the store directly; on a store-less `tenant` pod the identical call becomes a wire request answered by the control plane. The controller above is byte-identical either way — you never branch on `role`, and moving a pod from `standalone` to `tenant` changes only `config/durable.ts`.

The full surface:

| Verb | Purpose |
| --- | --- |
| `topology()` | this pod's `role`, plus its `tenant` on a store-less pod. Synchronous — no round-trip. |
| `getRun(runId)` | one run, or `null` |
| `listRuns(query)` | a filtered listing (status, workflow, tag, namespace, search attributes) |
| `getCheckpoints(runId)` | the run's step timeline |
| `getRunChildren(runId)` | the ids of the run's child workflows |
| `getRunDetail?(runId, { summarizeFansOver? })` | the run, its timeline and its children in one read, or `null`. With `summarizeFansOver: n`, each fan of more than `n` members comes back as one `FanSummary` in `fans` instead of a row per member, `children` lists the first 200 ids and `childCount` the total |
| `getFanMembers?(runId, group, { offset?, limit?, failedOnly? })` | one page of a fan's members in seq order (`limit` defaults to 100, at most 500), with the matching `total`, or `null` for an unknown run |
| `getSearchAttributes(runId)` | the run's [search attributes](/docs/durable/authoring/queries-and-updates) |
| `start(workflow, input, opts?)` | start a run; `opts.runId` is the idempotency key, and omitting it mints one |
| `signal(runId, signal, payload?)` | deliver a [signal](/docs/durable/concepts/sleep-and-signals) |
| `cancel(runId, opts?)` | cancel a run, with `{ compensate: true }` to run its [saga undo](/docs/durable/reliability/sagas) first |
| `redispatchPending(runId)` | re-enqueue every remote step still `pending` — [the operator escape hatch](/docs/durable/reliability/failure-modes) |
| `workerHealth()` | queue depth and live workers per group |
| `subscribe(runId, onEvent)` | live-tail one run's lifecycle events; returns the unsubscribe |

On a `tenant` pod every verb except `topology()` and `subscribe()` is a wire round-trip bounded by `requestTimeoutMs` (default `10_000`). A request whose reply never arrives rejects with an error naming the verb (`durable control plane did not answer getRun within 10000ms`) instead of hanging. A reply the control plane refuses rejects with an `Error` carrying a `code`: `unauthorized` for an invalid or tampered token, `cross-tenant` for a run owned by another tenant. Over a tenant proxy, `workerHealth()` is scoped to the tenant's own groups — the control plane keeps only groups ending in `@<tenant>`. `subscribe()` bridges onto the transport's per-tenant event stream, which the responder republishes for the tenant's own runs only.

`getRunDetail` and `getFanMembers` are optional on the interface, and every built-in gateway implements them. A custom gateway without them still works: the dashboard and the responder build the same detail from `getRun`, `getCheckpoints` and `getRunChildren`, and the exported `loadRunDetail` / `loadFanMembers` helpers do it for your own code.

```ts
const detail = await runGateway.getRunDetail?.(params.id, { summarizeFansOver: 50 })
// detail.fans: [{ group: 'steps:3:40000', label: 'processLine', size: 600, total: 40000, counts: { completed: 580, pending: 20 }, … }]
```

<Callout type="warn" title="Upgrade the control plane before its tenants">
On a store-less `tenant` pod the [dashboard](/docs/durable/observability/dashboard) reads run detail through the `getRunDetail` run-request verb, and pages a fan through `getFanMembers`, so the control plane summarizes a wide fan before it crosses the wire. A control plane on an older version rejects verbs it does not know, so run detail fails on an upgraded tenant until its control plane is upgraded too. The responder answers an unknown verb with an `unknown run-request verb` error reply, so the tenant sees the failure at once rather than after `requestTimeoutMs`. Upgrade the control plane first, or with its tenants. Before answering either verb, the responder checks tenant ownership on the run alone, without loading its timeline.
</Callout>

On a store role, `engine` (the default export of `services/main`) is still there for everything the gateway does not cover — registering workflows, driving poll loops, `continue`, `retryWithInput`. On a `tenant` pod there is no engine to resolve, which is exactly the point: reach for `runGateway` in anything that must run on more than one role.

## Layered tenant authentication

The `tenant` on a wire request is a **claim**. Without authentication, the isolation boundary is meaningless — any pod could ask for any tenant's runs. Durable stacks **two** layers (spec-driven; use one or both):

<Steps>

<Step>

### Prefix / network baseline

Each tenant runs on a segmented transport prefix/namespace behind a Redis/network ACL, so a pod can only reach its own prefix. This is the aviary model and needs no application code.

</Step>

<Step>

### Signed token on top

Each `tenant` pod carries a secret-signed token. The control plane's `RunRequestResponder` **verifies the signature and derives the tenant from the token**, ignoring any `tenant` in the request body. Defense in depth.

```ts
import { signTenantToken, hmacTenantVerifier } from '@adonis-agora/durable'

// On the tenant pod — mint the token it presents (config.tenant.token):
const token = signTenantToken('acme-corp', process.env.DURABLE_TENANT_SECRET!)
// Optionally expiring (the `.exp<epochMs>` suffix is signed, so it can't be stripped/extended);
// a captured token then stops replaying after the ttl instead of being valid forever:
const shortLived = signTenantToken('acme-corp', process.env.DURABLE_TENANT_SECRET!, { ttlMs: 24 * 60 * 60 * 1000 })

// On the control plane — verify it (config.verifyTenant). A secret LIST makes rotation a
// two-step deploy: verify with [next, current] first, then re-mint tokens with `next` at leisure:
verifyTenant: hmacTenantVerifier([process.env.DURABLE_TENANT_SECRET_NEXT!, process.env.DURABLE_TENANT_SECRET!])
```

<Callout type="warn">
Without `verifyTenant`, the wire `tenant` field is trusted **verbatim** — any process with broker access can list, signal, cancel and start runs as any tenant (prefix/network isolation only). The responder now logs a loud warning at start when no verifier is configured; treat running without one as a conscious choice that your broker is fully isolated per tenant, not a default.
</Callout>

</Step>

</Steps>

The `RunRequestResponder` is the **trust boundary**. Beyond checking the token, it forces `listRuns` to the requester's own tenant (no cross-tenant enumeration), validates `run.namespace === tenant` on every get/signal/cancel (anti-IDOR), and rejects unknown verbs and tampered tokens.
