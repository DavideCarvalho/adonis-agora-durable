Already running [Telescope](/docs/telescope)? The `@adonis-agora/durable/telescope` subpath adds a dedicated **Workflows** view so durable flows appear next to your requests, queries, and jobs — with a health dashboard built from the engine's lifecycle events and live store reads. It ships in the main `@adonis-agora/durable` package — no extra install.

## Registering the extension

Register `durableTelescopeExtension()` under Telescope's `extensions`:

```ts title="config/telescope.ts"
import { defineConfig } from '@adonis-agora/telescope'
import { durableTelescopeExtension } from '@adonis-agora/durable/telescope'

export default defineConfig({
  extensions: [
    durableTelescopeExtension({
      runHref: '/durable#/run/{runId}',
      recentFailuresWindowMs: 24 * 60 * 60 * 1000, // default: only show failures from the last 24h
    }),
  ],
})
```

The extension contributes a `durable` entry type (labeled **Workflows** in the nav), a `durable.workflows` dashboard, thirteen data providers, and your workflows' schedules on Telescope's Live Schedules screen. Both options are optional:

- `runHref` is a URL template used to deep-link a run row out to the [durable dashboard](/docs/durable/observability/dashboard). `{runId}` is substituted per row. The default is `'/durable#/run/{runId}'`. Pass your own when the console is mounted somewhere other than `/durable` (the `path` in `config/durable_dashboard.ts`), because the extension can't know the mount path. Keep the `#/run/` shape: the console is a hash-routed SPA, so a plain path such as `/durable/runs/<id>` is answered by your app's router and 404s.
- `recentFailuresWindowMs` sets how far back the **Stuck runs** table looks. The default is 24 hours, so a healthy system shows an **empty** table instead of surfacing days-old failures as a live incident. Pass `0` to disable the window and show every failed and dead run.

## How runs become entries

Nothing needs registering for the dashboard. The `@adonis-agora/durable` provider bridges every engine lifecycle event onto the [`@adonis-agora/diagnostics`](/docs/diagnostics) bus as `agora:durable:<type>` (e.g. `agora:durable:run.failed`) when diagnostics is installed. Telescope's generic diagnostics watcher captures that bus. You get one entry per lifecycle event (`run.started`, `step.completed`, `run.completed`, `run.failed`, …), recorded as a `diagnostic` entry tagged `lib:durable`, with the whole engine event as its payload. When diagnostics isn't installed, the bridge is an inert subscription and costs nothing.

### One entry per event across a fleet

With a [control plane](/docs/durable/transports/control-plane) configured, every pod hears every other pod's lifecycle events: that is what lets a dashboard pod live-tail a run executing on a worker. The bridge forwards only the events its **own** instance produced, so a fleet records each event once, on the pod that ran the work. (Before 0.51, every pod forwarded what it heard too, and a three-pod fleet counted every `run.completed` three times.) `isRemoteEvent(event)`, exported from `@adonis-agora/durable`, tells the two apart if you subscribe to the engine yourself. To mirror the whole fleet into one pod's recorder anyway, attach the bridge yourself with `attachDurableDiagnostics(engine, { includeRemote: true })` (see [Local events only](/docs/durable/observability/diagnostics#local-events-only) for the caveat next to the provider's own bridge).

The entry-backed providers also collapse copies of one event before they count, keyed by event, run id, the event's emission instant (`payload.at`, set once where the event was produced) and, for `run.triggered` / `run.trigger_failed`, the subscriber, so two subscribers of one run whose events share an instant both count. That keeps history recorded before 0.51, or by older pods sharing one Telescope store, from reading N times too high, while a retried run's second `run.failed` and a run's tenth `run.suspended` still count: each has its own instant. `dedupeRunEvents(entries)` is exported from `@adonis-agora/durable/telescope`.

An event of a child run started by `ctx.all`, `ctx.child` or `ctx.startChild` (without a caller-chosen id) also carries `parentRunId` in its payload. Each child is its own run, so that field is how you find every child of one parent, a whole `ctx.all` fan included. `parentRunIdOf(runId)` is exported from `@adonis-agora/durable` if you need the same mapping yourself.

An event of a run started by a [lifecycle event](/docs/durable/authoring/lifecycle-events) (an `@OnWorkflowCompleted` / `@OnWorkflowFailed` subscriber) carries `lifecycleSourceRunId` and `lifecycleKind` (`completed` / `failed`): the settled run that started it and how that run ended, read from the subscriber run's id (`lifecycleSourceOf`). Its `run.started` also carries `sourceTraceparent`, the source run's W3C traceparent, when the engine knows it (see [OpenTelemetry](/docs/durable/observability/otel)). The settled run's own entries include `run.triggered` (one per subscriber run started, with the subscriber as `name` and its run as `triggeredRunId`) and `run.trigger_failed` (with `name` and `error`). Telescope's generic watcher records these as payload fields and tags every entry only `lib:durable`, `event:<type>` and `trace:<id>`; to search them by tag, add the watcher below.

### Tagged entries: `DurableTelescopeWatcher`

`@adonis-agora/telescope`'s `TelescopeExtension` contract takes no watchers, so the tagging watcher is wired by hand, to Telescope's own `safeRecord` (which keeps Telescope's pause, heartbeat and self-observation rules):

```ts title="start/telescope.ts"
import { safeRecord } from '@adonis-agora/telescope/watchers'
import { DurableTelescopeWatcher } from '@adonis-agora/durable/telescope'

new DurableTelescopeWatcher().register({ record: (entry) => safeRecord(entry, 'durable') })
```

It records each `agora:durable:<type>` event as the generic watcher does (same `diagnostic` type, `durable:<type>` family and content, so every panel below reads it unchanged) and adds the tags durable's NestJS twin records: `durable`, the event type, `run:<id>`, `parent:<id>`, `workflow:<name>`, `kind:<step kind>`, `failed`, `routed` / `unrouted` with `onError:<code|*>`, `triggered` with the started run's `run:<id>` (so a `run:<id>` search shows the trigger from both runs), `trigger_failed` with `subscriber:<name>`, and on the `run.started` of a lifecycle-started run `lifecycle`, `source:<source run id>` and `sourceTrace:<trace id>` (from `sourceTraceparent`, when the source recorded its span). `register()` claims every `durable:<type>` key in `@adonis-agora/diagnostics`' claim registry, so the generic watcher (from `@adonis-agora/telescope` 0.6.0) skips them and nothing is recorded twice; `dispose()` gives them back. `buildDurableEntry`, `durableEntryTags`, `DURABLE_DIAGNOSTIC_EVENTS` and `traceIdOfTraceparent` are exported with it.

Telescope groups entries into a trace by their `traceId` and has no span links, so a lifecycle-started run is linked to its source by those tags, not by a shared trace: open the source run's trace and search `source:<its run id>`, or the started run's entries and search `sourceTrace:`. The traces are the ones `@adonis-agora/context` resolves where the events are emitted; durable does not derive a trace from the run id.

A dead-lettered run shows up as a `run.failed` entry with `error.code: 'max_recovery_attempts'` (see [Dead-letter queue](/docs/durable/reliability/dead-letter)), so it counts toward the failure rollups.

## The Workflows dashboard

The `durable.workflows` dashboard is laid out in five sections:

- **Health** has **Success rate** (a gauge that warns below 98% and turns bad below 95%), **Duration p95** (warns above 2 s, bad above 5 s), **Backlog** (the count of `pending` runs; warns above 50, bad above 200) and **Throughput** (completed runs per hour, with a trend spark).
- **Needs attention** has **Top failing workflows** (the eight workflows producing the most failures), **Stuck runs** (recent failed and dead runs as a table, deep-linked via `runHref` and bounded by `recentFailuresWindowMs`), **Failed triggers** (recent `run.trigger_failed` events: time, source workflow, source run deep-linked via `runHref`, subscriber, error), **Owed lifecycle events** (settled runs still tagged `durable:lifecycle:pending` 30 seconds after settling, the grace the lifecycle sweep gives the live publish: when the run settled, its workflow, the run deep-linked, and the subscribers it still owes its event to, read from the store like Stuck runs), **Worker health** (every worker group with its queue depth and live-worker count; `STARVED` groups, which have a backlog and zero live workers, are sorted first and flagged in the Status column), and **Owed runs** (how many settled runs are still owed a lifecycle event past the grace, one `COUNT`; warns at 1, bad at 50).
- **Workers** (new in 0.51) has one row per **live worker instance**: its group, instance id, concurrency mode (`fixed` / `adaptive`), limit and adaptive range (`min–max`, adaptive mode only), in-flight saturation (`inFlight/limit`), the group's queued count, RAM %, CPU %, steps per minute, p95, the last adaptive adjustment (`shrink 8→6 2m ago`) and when it last beat. A cell reads `n/a` when the worker's heartbeat carries no status at all (an older SDK) and `—` when the worker reports fine but has nothing measured yet (an idle worker), so an idle worker is not mistaken for a broken one.
- **Lifecycle** has **Lifecycle triggers over time** (stacked `triggered` / `failed` counts of `run.triggered` and `run.trigger_failed`) and **Triggered by subscriber** (subscriber runs started per `<workflow> → <subscriber>`, most first), both from the captured entries.
- **Trends** has **Runs over time** (stacked done/failed), **Duration distribution** (a histogram with p50/p95/p99 markers) and **Runs by state** (a donut: running blue, pending amber, completed green, failed red, dead purple).

### Data providers

Thirteen providers back the panels, reading from three different places by design:

- **Telescope's own captured entries.** `durable.timeseries` (success rate, failed count, top failures), `durable.duration` (p50/p95/p99 and the histogram), `durable.runsOverTime`, `durable.successRate`, `durable.throughput`, `durable.failedTriggers` (the Failed triggers table) and `durable.lifecycleTriggers` (the Lifecycle section) aggregate the `lib:durable` entries Telescope already captured. This is the **recent-history** view, bounded by Telescope's prune window. Success rate and throughput compare a 24-hour window against the previous one to show a delta.
- **The live durable store.** `durable.state` (one status count, e.g. Backlog; defaults to `dead`), `durable.recentFailures` (the Stuck runs table), `durable.owedLifecycle` (the Owed lifecycle events table: one listing of runs by the `durable:lifecycle:pending` tag) and `durable.stateBreakdown` (the Runs-by-state donut) are read **live**, so they're exact and **not** limited by the prune window. The counts go through `engine.countRuns`, a `COUNT` on a store that has one (the Lucid store does), which stays exact and cheap when a wide fan puts tens of thousands of runs in one status. An engine without `countRuns` falls back to a listing capped at 10,000 runs.
- **The live worker layer.** `durable.workerHealth` reads `engine.workerHealth()` and returns per-group backlog and live-worker rows; `durable.workerStatus` flattens the same read to one row per live instance (the Workers table). Query it with `{ metric: 'starvedCount' }` for a single stat: the number of groups with a backlog and zero live workers. The list is empty when the transport can't introspect its groups: only the BullMQ, queue and db transports implement `groupHealth` today.

Every provider reads at query time; none of them needs the tagging watcher. The `durable.*` providers that take a query accept: `durable.state` `{ status }`; `durable.recentFailures` `{ windowMs, limit }`; `durable.timeseries` `{ metric: 'successRate' | 'failed' | 'total' | 'topFailures', limit }`; `durable.duration` `{ metric: 'p50' | 'p95' | 'p99' }` (omit for the histogram); `durable.successRate` and `durable.throughput` `{ windowMs }` (default 24 h); `durable.workerHealth` `{ metric: 'starvedCount' }`; `durable.failedTriggers` and `durable.owedLifecycle` `{ limit }` (10-200, default 50), and `durable.owedLifecycle` `{ metric: 'count' }` for the Owed runs stat; `durable.lifecycleTriggers` `{ buckets }` (default 24) or `{ metric: 'bySubscriber' }` for the per-subscriber counts.

Telescope is the health and visibility view, and deep-links out: **per-run actions** (retry, cancel) and the **step timeline** stay in the [durable dashboard](/docs/durable/observability/dashboard).

## Schedules on the Live Schedules screen

The extension also contributes your workflows' schedules to Telescope's **Live Schedules** screen, so nobody keeps a second, hand-typed list. It reports every schedule the engine discovered from a workflow class, either a [colocated `static schedule` or `@Scheduled`](/docs/durable/authoring/scheduling#colocate-the-schedule-with-the-workflow), read from the container once Telescope is ready:

- A `cron` schedule is listed as `cron` with its expression and timezone. An `every` schedule is listed as `interval`, rendered like `every 2m`.
- The schedule's pinned `namespace` is shown as the **pool** that services its runs. An unpinned schedule shows no pool, meaning whichever worker's tick wins fires it.
- A **paused** schedule is still listed. The screen shows what exists, and a cron that silently disappears is harder to debug than one marked paused.

Only schedules declared on workflow classes are contributed. Schedules listed under `schedules` in `config/durable.ts` don't appear on the screen.

## Origin and heartbeat labels

The worker tick runs labelled with Telescope's `origin: 'schedule'`, so the store queries and writes a tick makes are attributed to the scheduler instead of looking like orphan queries. The tick's liveness **probes** (the "is there a due timer / pending run / blocked run?" reads that run every few seconds on an idle app) are marked as heartbeats, which Telescope drops, so an idle worker does not flood the query list. The work a tick finds is **not** marked: the lease, the checkpoints and the result are the run's history and stay recorded.

Both labels are read structurally from a global slot `@adonis-agora/telescope` publishes, and are no-ops without it. They are exported as `withScheduleOrigin(fn)` and `asHeartbeat(fn)` from `@adonis-agora/durable` for a custom loop built on [`runTick` / `runWorkerLoop`](/docs/durable/cli#building-your-own). Wrap only the probe read in `asHeartbeat`, never the work it leads to, or real work disappears from Telescope.

## Mounting just the dashboard spec

If you want the durable health dashboard's spec to compose into your own Telescope layout, the package also exports `durableDashboard(opts?)` (returning the dashboard spec, with the same `runHref` / `recentFailuresWindowMs` options), `durableSchedules(ctx)`, and the individual data providers (`durableStateProvider`, `durableTimeseriesProvider`, `durableRecentFailuresProvider`, `durableWorkerHealthProvider`, `durableWorkerStatusProvider`, `durableDurationProvider`, `durableRunsOverTimeProvider`, `durableSuccessRateProvider`, `durableThroughputProvider`, `durableStateBreakdownProvider`, `durableFailedTriggersProvider`, `durableOwedLifecycleProvider`, `durableLifecycleTriggersProvider`) so you can pick and place panels yourself. `dedupeRunEvents(entries)` is exported for a custom provider reading the same `lib:durable` entries, and the structural SDK types (`TelescopeExtension`, `DataProvider`, `ExtensionContext`, `ContainerLike`, `TelescopeStoreLike`, `TelescopeRecordInput`, `WatcherContext`) are re-exported for typing one.

<Callout type="info">
The extension object structurally satisfies `@adonis-agora/telescope`'s `TelescopeExtension` type without importing it, so `@adonis-agora/durable` takes no dependency on Telescope. The engine-backed providers resolve `WorkflowEngine` from the AdonisJS container at query time.
</Callout>
