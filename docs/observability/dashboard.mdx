The dashboard mounts an operations console into your AdonisJS app: a React single-page app plus the JSON API it runs on. It reads straight from the [state store](/docs/durable/stores) through the engine's read API, so it works without an OpenTelemetry collector. It ships in the main `@adonis-agora/durable` package — no extra install.

```bash
node ace configure @adonis-agora/durable
```

`configure` registers `@adonis-agora/durable/dashboard_provider` in `adonisrc.ts` and publishes `config/durable_dashboard.ts`. The provider registers the routes on boot — nothing else to wire.

## Configuration

`config/durable_dashboard.ts` controls where it mounts and who may reach it:

```ts title="config/durable_dashboard.ts"
import { defineConfig } from '@adonis-agora/durable/dashboard'

export default defineConfig({
  // enabled: true,
  // path: '/durable',
  // authorize: (ctx) => ctx.auth.user?.isAdmin === true,
})
```

| Option | Default | Description |
| --- | --- | --- |
| `enabled` | `true` | When `false`, no routes are registered at all. |
| `path` | `'/durable'` | Route prefix the console mounts under. `'/'` mounts at the root. |
| `authorize` | open outside production, `403` in production | Who may reach the console: a function `(ctx) => result`, an authorizer class, or a lazy import of one. See [Authorization](#authorization). |
| `audit` | app logger | `(entry) => void` sink for every mutating attempt: `{ at, actor, method, path }`. |
| `redact` | absent | `{ run?, checkpoint? }` hooks applied to every serialized run and checkpoint right before it leaves the API. See [Redacting payloads](#redacting-payloads). |
| `accessDenied` | built-in page | Tweak or replace the [access-denied page](#the-access-denied-page). |
| `viewer` | `ctx.auth.user` | `(ctx) => ({ label, email?, role? }) \| null`: who the sidebar footer shows as signed in. See [Signed-in user and sign-out](#signed-in-user-and-sign-out). |
| `signOut` | announced by authkit | The footer's sign-out: a POST action path, `{ href }` for a link, or `false` for none. |

### Authorization

Without `authorize`, the console is open when the app is not in production. In production every request, the console page and its API alike, gets `403`, and the app logs this once at boot:

```
[@adonis-agora/durable] console has no `authorize` configured: it is open outside production and denies every request in production. Set `authorize` in config/durable_dashboard.ts.
```

Set `authorize` to choose who may open it. It takes the same contract as every `@adonis-agora` console (`ConsoleAuthorize`, exported from `@adonis-agora/durable/dashboard`), in three forms:

```ts title="config/durable_dashboard.ts"
import { defineConfig } from '@adonis-agora/durable/dashboard'
import ConsoleAccess from '#policies/console_access'

export default defineConfig({
  // 1. an inline function
  authorize: (ctx) => ctx.auth.user?.isAdmin === true,

  // 2. an authorizer class (built by the container, so `@inject()` works)
  // authorize: ConsoleAccess,

  // 3. a lazy import of that class
  // authorize: () => import('#policies/console_access'),
})
```

```ts title="app/policies/console_access.ts"
import { inject } from '@adonisjs/core'
import type { HttpContext } from '@adonisjs/core/http'
import type { ConsoleAuthorizer } from '@adonis-agora/durable/dashboard'
import AuditService from '#services/audit_service'

@inject()
export default class ConsoleAccess implements ConsoleAuthorizer {
  constructor(private audit: AuditService) {}

  async authorize(ctx: HttpContext) {
    if (!(await ctx.auth.check())) return { redirectTo: '/login' }
    const allowed = ctx.auth.user!.isAdmin
    await this.audit.record('durable-console', ctx.auth.user!.id, allowed)
    return allowed
  }
}
```

The class is the same for every console, so one `ConsoleAccess` can gate durable, telescope, media, payments and agent.

What `authorize` returns decides the answer. A denial gets JSON for an API call and the [access-denied page](#the-access-denied-page) for a browser:

| Result | Status | API body |
| --- | --- | --- |
| `true` / `{ allowed: true }` | request proceeds | — |
| `{ allowed: false, reason: 'unauthenticated' }` | `401` | `{ "error": "unauthenticated" }` |
| `{ allowed: false, reason: 'forbidden' }`, `{ allowed: false }`, `false` | `403` | `{ "error": "forbidden" }` |
| `{ redirectTo: '/login' }` | `302` to that path for a page, `401` for an API call | `{ "error": "unauthenticated", "redirectTo": "/login" }` |
| it throws | `403` | `{ "error": "forbidden" }` |

Only `true` or `allowed: true` lets a request through — any other value denies. A guard that already answered the request itself (`ctx.response.redirect(...)`, a body) keeps its answer; the console writes nothing over it. When an API call gets a `401` carrying `redirectTo`, the bundled console sends the browser there.

```ts
export default defineConfig({
  authorize: async (ctx) => {
    if (!(await ctx.auth.check())) return { allowed: false, reason: 'unauthenticated' } // 401
    return ctx.auth.user?.isAdmin === true // false -> 403
  },
})
```

If you use `@adonis-agora/authz` for RBAC, the shared `authorizeByRoles` helper reads
your user and roles for you — same semantics as the `requireRole` middleware, no ctx
narrowing:

```ts
import { authorizeByRoles } from '@adonis-agora/authz'

export default defineConfig({
  authorize: authorizeByRoles({ roles: ['ADMIN'] }),
})
```

The user is resolved from `ctx.auth.getUser()` (authkit) or `ctx.auth.user` (any guard);
`roles` is any-of over `effectiveRoles` (token claims ∪ DB roles). Anonymous requests are
denied (`false`). The same helper works across every `@adonis-agora` dashboard — durable,
telescope, media and agent — so one RBAC gate config reads the same everywhere.

#### Scripts and scrapers: `authorizeByToken`

For machine access (a script, a Prometheus scrape of [`/api/metrics`](#live-queries-webhooks-and-metrics)), `authorizeByToken` lets a request through when its `Authorization: Bearer <token>` header matches, and answers `401` otherwise. Only that header is read. An empty or missing token throws when the config loads.

```ts title="config/durable_dashboard.ts"
import env from '#start/env'
import { authorizeByToken, defineConfig } from '@adonis-agora/durable/dashboard'

export default defineConfig({
  authorize: authorizeByToken({ token: env.get('CONSOLE_TOKEN') }),
})
```

```sh
curl -H "Authorization: Bearer $CONSOLE_TOKEN" https://app.example.com/durable/api/runs
```

To let both operators and scripts in, pass both to `anyAuthorize`. It allows a request when any of them does, tried in order:

```ts title="config/durable_dashboard.ts"
import env from '#start/env'
import { authorizeByRoles } from '@adonis-agora/authz'
import { anyAuthorize, authorizeByToken, defineConfig } from '@adonis-agora/durable/dashboard'

export default defineConfig({
  authorize: anyAuthorize(
    authorizeByToken({ token: env.get('CONSOLE_TOKEN') }),
    authorizeByRoles({ roles: ['ADMIN'] }),
  ),
})
```

#### Request guards and audit

A browser-originated cross-site mutating request (by `Sec-Fetch-Site`, else `Origin` vs `Host`) gets `403 { "error": "cross-site request rejected" }` whatever `authorize` says. `Sec-Fetch-Site: same-site` counts as cross-site, so a sibling subdomain cannot drive the console's actions either; an `Origin: null` is rejected too. Non-browser clients send neither header and pass.

Every mutating attempt is **audited** before its handler runs: actor (`ctx.auth.user`'s `email`, `name` or `id`, `bearer` for a token caller, else `anonymous`), method and path without the query string. It goes to the app logger, or to your own `audit` hook. The same hook records the actions taken from the [ace commands](/docs/durable/cli) (actor `cli:<os user>`, method `CLI`, path `<command> <target>`). Reads are not audited. Payloads an operator submits (fix-and-replay input, signal/update/task bodies, webhook callbacks) are capped at 1 MiB (`413`). A handler that throws answers a generic `500 { "error": "internal error" }`; the detail goes to the app logger, never to the client.

<Callout type="warn">
The console exposes retry, cancel, replay and bulk actions that mutate runs. Set `authorize` before you deploy; a staging app that does not run in production mode is open without it.
</Callout>

### The access-denied page

A refused **API** request gets JSON (`403 { "error": "forbidden" }` or `401 { "error": "unauthenticated" }`) — that is what the console's own `fetch` calls expect. A refused **page** navigation — the console shell or its assets — gets a real page instead: a dark card in the console's visual language showing the status, a sentence explaining the refusal, a "Back to app" link and, when you set `loginHref`, a "Sign in" button. It carries no inline script, so a nonce'd `script-src` CSP cannot break it (its one inline `<style>` picks up `@adonisjs/shield`'s request nonce).

Tweak it with `accessDenied` — every field optional:

```ts title="config/durable_dashboard.ts"
export default defineConfig({
  accessDenied: {
    brand: 'Entre Textos',           // eyebrow + <title>; default "Durable"
    title: 'Sem acesso',             // default depends on the refusal
    message: 'Peça ao admin para liberar o console de workflows.',
    homeHref: '/admin',              // "Back to app"; default "/", `false` hides it
    homeLabel: 'Voltar',
    loginHref: '/entrar',            // "Sign in" on a 401; absent by default
    loginLabel: 'Entrar',
    accent: '#f59e0b',               // any CSS colour; default: the console's lime
  },
})
```

Or replace it. Pass a function and it receives the refusal (`status`, `reason` — `'forbidden'` or `'unauthenticated'` — `basePath`, and the CSP `nonce` when there is one) plus the `HttpContext`. Return an HTML string to have it served with the right status; answer the request yourself and return nothing to make the provider stand down:

```ts title="config/durable_dashboard.ts"
export default defineConfig({
  accessDenied: (info, ctx) => {
    if (info.reason === 'unauthenticated') {
      ctx.response.redirect(`/login?next=${encodeURIComponent(info.basePath)}`)
      return
    }
    return `<!doctype html><title>${info.status}</title><h1>Sem acesso</h1>`
  },
})
```

An `authorize` hook that already wrote a redirect still wins — the provider never overwrites a `location` header, with or without `accessDenied`.

### Signed-in user and sign-out

The sidebar footer shows who is signed in, a light/dark toggle, and a sign-out button.

Each console has its own fixed accent colour: authkit indigo `#625fff`, durable lime `#a3e635`, telescope magenta `#e879f9`, payments cyan `#22d3ee`, media amber `#fbbf24`, agent rose `#fb7185` and flags emerald `#34d399`. The cms admin is the only one an app can rebrand (`admin.theme`). Every console has the light/dark toggle in the sidebar footer, remembered per browser.

Without `viewer`, the footer reads `ctx.auth.user` once the request is already authenticated; it never triggers authentication itself. The label is `fullName`, `name` or `email`. Roles come from the user's `role`, `roles` and `globalRoles` (strings, `{ name }` objects or authz role rows `{ role }`) and, when authkit is installed, from the global roles of authkit's per-request identity. The footer shows one of them: the first admin-like one (a name containing `admin`, such as `ADMIN` or `org_admin`), else the first. A `viewer(ctx)` hook replaces all of this.

Pass `viewer` to show something else, or return `null` to hide the user row:

```ts title="config/durable_dashboard.ts"
export default defineConfig({
  authorize: (ctx) => ctx.auth.user?.isAdmin === true,
  viewer: (ctx) => {
    const user = ctx.auth.user
    return user ? { label: user.fullName, email: user.email, role: 'admin' } : null
  },
  signOut: '/logout',
})
```

A string `signOut` is a path the button POSTs to, with the request's CSRF token as `_csrf` when shield is installed. `{ href: '/bye' }` renders a link instead. Without `signOut`, the console uses the sign-out that authkit's account console registers. `false` removes the button. Only same-origin paths are accepted.

### Redacting payloads

The store may hold payloads encrypted (a codec-wrapped store), but the console reads through the codec, so operators always see them **decoded**. `redact` keeps a card number or PII out of the operator's browser. Each hook receives the serialized shape and returns what to send. It runs on the runs list, the run detail and fan member pages:

```ts title="config/durable_dashboard.ts"
export default defineConfig({
  redact: {
    run: (run) => ({ ...run, input: undefined }),
    checkpoint: (cp) => ({ ...cp, output: '[redacted]' }),
  },
})
```

## Where it mounts

All routes are relative to `path` (default `/durable`), and every one of them runs behind the `authorize` guard.

### Pages

| Method | Route | Purpose |
| --- | --- | --- |
| `GET` | `/durable` | the React console (`index.html`, with the base path and API base injected) |
| `GET` | `/durable/assets/:file` | the console's hashed JS/CSS bundle, served immutable |

The console routes client-side on the URL hash, so a deep link needs no server-side rewrite: `#/run/<id>` opens a run, `#/workflow/<name>` a [workflow's page](#workflow-pages), `#/workers` the Workers page and `#/schedules` the Schedules page.

### Reading runs

| Method | Route | Purpose |
| --- | --- | --- |
| `GET` | `/durable/api/runs` | list runs — see the filters below |
| `GET` | `/durable/api/runs/values` | distinct values of one filter axis, with counts — what the pickers list |
| `GET` | `/durable/api/runs/:id` | run detail: the run, its step `timeline`, its `children`, its lifecycle links (`triggered`, `triggeredBy` with the source's `status` and `traceId`), `lifecycleSubscribers`, `lifecycleDeliveries`, its `ctx.waitForRun` links (`waitsFor`, `awaitedBy`) and its workflow's `workflowLifecycle` (absent when no workflow starts it or starts on it); a fan of more than 50 members comes back summarized in `fans` unless `?full=true` |
| `GET` | `/durable/api/runs/:id/fans/:group` | one page of a summarized fan's members, in seq order — see [paging a fan](#paging-a-fans-members) |
| `GET` | `/durable/api/runs/:id/stream` | Server-Sent Events: this run's lifecycle events, live |

Every list route here speaks the [`@adonis-agora/filter`](/docs/filter) wire format: filters in the
`filter[...]` envelope, `sort`, offset paging with `page` / `size`, and a `{ data, meta }` answer.
[`@adonis-agora/filter-client`](/docs/filter/guides/client) builds these query strings.

`GET /api/runs` filters:

| Filter | Meaning |
| --- | --- |
| `filter[status]` | one of `pending`, `running`, `suspended`, `blocked`, `cancelling`, `completed`, `failed`, `cancelled`, `dead`. A set (`filter[status][]=failed&filter[status][]=dead`) matches any of them. |
| `filter[workflow]` | exact workflow-name match; a set matches any of them. |
| `filter[tag]` | exact match against the run's tags; a set matches runs carrying any of them. |
| `filter[namespace]` | exact match against the run's [worker-pool namespace](/docs/durable/cluster/topology-and-config) — omit it and the listing spans every namespace. A set matches any of them. |
| `filter[origin]` | exact match against the run's [package attribution](/docs/durable/concepts/workflows-and-steps#run-origin--package-attribution). The "unknown" bucket (absent origin) can't be expressed as an exact match — the console filters that one client-side. |
| `filter[createdAfter]` / `filter[createdBefore]` | time-range bounds on the run's creation, as epoch ms or an ISO date string. |
| `filter[attr]` | a [search-attribute](/docs/durable/authoring/queries-and-updates) predicate, `key:op:value`; a set is ANDed. `filter[attr.<key>][<op>]=value` works as well. |

| Param | Meaning |
| --- | --- |
| `sort` | `-createdAt` (newest first) — the only order the stores list in, and the default. |
| `page` | 1-based page number, default `1` |
| `size` | page size, default `50`, capped at `200` |

The `attr` ops are `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in` (`filter[attr.<key>][<op>]` takes the filter lib's names: `equals`, `notEquals`, `gt`, `gte`, `lt`, `lte`, and `in`/`isAnyOf`). Values are coerced: `true`/`false` become booleans, anything numeric becomes a number, everything else stays a string. Only the first two colons delimit, so a value may contain colons of its own. `in` takes a `|`-separated set (`tier:in:pro|enterprise`) and matches it as OR inside the one predicate — two `eq` predicates on one key are ANDed like every other pair, which no run can satisfy.

```
GET /durable/api/runs?filter[namespace]=eu-west&filter[attr][]=amount:gte:5000&filter[attr][]=tier:eq:enterprise&filter[status]=failed&page=1&size=50
```

```ts
import { filterQuery } from '@adonis-agora/filter-client'

const qs = filterQuery()
  .where('namespace', 'eu-west')
  .where('status', 'failed')
  .where('attr', ['amount:gte:5000', 'tier:eq:enterprise'])
  .page(1, 50)
  .toQueryString()

const { data, meta, statuses } = await fetch(`/durable/api/runs?${qs}`).then((r) => r.json())
```

The answer:

```json
{
  "data": [{ "id": "run-1", "workflow": "checkout", "status": "failed", "...": "..." }],
  "meta": { "total": 120, "perPage": 50, "currentPage": 1, "lastPage": 3, "firstPage": 1 },
  "statuses": ["pending", "running", "suspended", "blocked", "cancelling", "completed", "failed", "cancelled", "dead"]
}
```

`meta.total` counts every run the filter matches. `statuses` lists every run status, for a status picker.

A request the endpoint can't read answers `400` instead of silently widening: an unknown filter field, an operator the field doesn't take, an `OR` group, a `sort` other than `-createdAt`, or a filter field sent bare (`?status=failed` instead of `filter[status]=failed`).

#### The picker enumeration

`GET /api/runs/values` answers what the console's tag, tenant and attribute pickers list: the distinct values one axis takes across the runs matching every OTHER active predicate, with counts — most common first, engine-minted tags (`singleton:<key>`) last. The axis rides `groupByCount[field]` (`workflow`, `status`, `namespace`, `tag`, `attr` for the keys in use, `attr.<key>` for the values under one key); the scope rides the same `filter[...]` envelope as `GET /api/runs` (minus `status`, which is dropped so the offers don't collapse to the status being viewed). It is the filter lib's group-by-count aggregation, so it pages the way that aggregation does: `groupByCount[limit]` bounds the rows (default `100`, capped at `200`), `groupByCount[offset]` pages them, `groupByCount[search]` narrows them server-side, so a rare value outside the first page stays reachable by typing. The response is a bare `[{ value, count }]` array.

```ts
const qs = filterQuery()
  .where('namespace', 'eu-west')
  .groupByCount('tag', { limit: 20, search: 'nig' })
  .toQueryString()
const rows = await fetch(`/durable/api/runs/values?${qs}`).then((r) => r.json())
// [{ value: 'nightly', count: 14 }]
```

There is no separate checkpoints route: a run's step timeline comes back as the `timeline` array of `GET /api/runs/:id`, each entry carrying `seq`, `name`, `kind`, `status`, `attempts`, `workerGroup`, input/output/error, `events`, `parallelGroup`, and the derived `durationMs` / `queueMs`.

A fan with more than 50 members (a `ctx.all` over children or over a step, a polyglot gather) is summarized: its members leave `timeline`, and the fan comes back as one entry of `fans` with its `group`, `label`, seq range, `size` (members started so far), `total` (its declared size: a `ctx.all` group carries it as `all:<seq>:n<size>`, a step fan as `steps:<seq>:<size>`), `notStarted`, `failFast`, `counts` by status (a failed child counts as `failed`), start and finish, and its first 20 failed members. A fan declared wider than 50 is summarized even while only a few of its waves have been sent. `children` then lists the first 200 child run ids and `childCount` carries the total. `GET /api/runs/:id/fans/:group` pages the members on demand (below). `?full=true` returns the detail unsummarized. On a store-less tenant pod the control plane summarizes before the detail crosses the wire.

#### Paging a fan's members

`GET /api/runs/:id/fans/:group` answers one page of the fan's members in seq order, as `{ data, meta }` with `meta.total` the member count. `page` and `size` (default `100`, capped at `500`) page it, `filter[status]=failed` keeps the failed members only, and `sort` takes `seq` only. Any other filter or sort is a `400`.

```
GET /durable/api/runs/run-1/fans/steps:12:40000?filter[status]=failed&page=1&size=100
```

#### Polling the run detail: ETag and 304

On a store with the checkpoint aggregates (`checkpointStats` + `queryCheckpoints`, which the Lucid and in-memory stores have), the summarized detail is built from one `GROUP BY` over the run's checkpoints plus a few targeted reads — the rows outside wide fans, each fan's first 20 failures, the folded checkpoints and the first child edges — instead of every checkpoint. A 40,000-member fan is drawn from a handful of rows.

Those responses carry an `ETag` (derived from the run row and the checkpoint buckets) and `Cache-Control: private, no-cache`. A request whose `If-None-Match` still names the ETag gets a bare `304`, answered after reading the run and the buckets only. The browser adds `If-None-Match` to the console's polls by itself, so an unchanged run costs a 304 instead of a body. `GET /api/runs/:id/fans/:group` is versioned the same way, per page. `?full=true`, and a store without the aggregates, answer in full without an ETag, as before. The options cross the tenant proxy unchanged.

#### Live-tailing one run

`GET /api/runs/:id/stream` is an SSE endpoint. Each frame is a default `message` event whose `data` is one serialized engine lifecycle event for that run:

```ts
const source = new EventSource(`/durable/api/runs/${runId}/stream`)

source.onmessage = (msg) => {
  const event = JSON.parse(msg.data)
  // event.type is one of run.started / run.completed / run.failed / run.suspended /
  // run.routed / run.unrouted / run.triggered / run.trigger_failed / step.started / step.completed / step.failed /
  // step.progress (a live step event, never persisted) / capability.unavailable / protocol.incompatible
  console.log(event.type, event.name, event.durationMs)
}
```

<Callout type="info">
The server writes a `: ping` comment every 25 seconds. That keeps intermediaries from reaping an idle stream, and it lets Node notice a dead client and drop the subscription. The stream ends when the client disconnects. `EventSource` reconnects on its own if a proxy cuts it anyway. The response carries `x-accel-buffering: no` so nginx does not buffer it.
</Callout>

Open streams are capped at **100 per instance and 10 per client address**. Past either cap the route answers `429 { "error": "too many open event streams" }`.

The tail is **cross-pod** when the engine has a [control plane](/docs/durable/transports/control-plane). Every instance broadcasts the lifecycle events it produces over the control plane, and the others deliver them to their local subscribers. A dashboard served from a web process can therefore live-tail a run that is executing on a `durable:work` pod. Without a control plane the stream still works, but only for runs executing in the same process as the dashboard.

### Acting on runs

| Method | Route | Purpose |
| --- | --- | --- |
| `POST` | `/durable/api/runs/:id/retry` | re-enqueue the run (→ `pending`, a worker resumes it) |
| `POST` | `/durable/api/runs/:id/retry-with-input` | **fix and replay**: start a new run from a corrected input |
| `POST` | `/durable/api/runs/:id/continue` | resume a run parked at a `ctx.breakpoint()` |
| `POST` | `/durable/api/runs/:id/cancel` | cancel the run — ask for the saga undo with `?compensate=true` or a `{ compensate: true }` body |
| `POST` | `/durable/api/runs/:id/redispatch` | re-enqueue every remote step still `pending` on this run |
| `POST` | `/durable/api/runs/:id/republish-lifecycle` | publish a settled run's [lifecycle event](/docs/durable/authoring/lifecycle-events#republishing-and-backfilling) again, to the subscribers it has not started (or `{ subscriber }` only); answers `{ result: { runs, started, failed } }`, `409` for a run that has not settled, `400` on a tenant pod whose control plane refuses the request (a `subscriber` that does not subscribe to the run's ending in the tenant's namespace), `501` on a tenant pod whose control plane is older than the verb |
| `POST` | `/durable/api/runs/:id/signal` | deliver a signal payload on a token the run is waiting on |
| `POST` | `/durable/api/runs/:id/updates/:name` | deliver a validated update to a `ctx.onUpdate` point |
| `POST` | `/durable/api/runs/:id/tasks/:name/complete` | complete an external `ctx.task` |
| `POST` | `/durable/api/runs/:id/tasks/:name/fail` | fail an external `ctx.task` |
| `POST` | `/durable/api/bulk/:action` | apply `retry` or `cancel` to everything a filter matches |

Every one of these is **non-blocking**: they enqueue work and return, never replaying a workflow inline in the HTTP request.

#### Fix and replay

A run that failed on a bad input cannot be "retried" into success — a retry replays the same input. `retry-with-input` instead **starts a brand-new run** with a corrected input:

```ts
const res = await fetch(`/durable/api/runs/${runId}/retry-with-input`, {
  method: 'POST',
  headers: { 'content-type': 'application/json', ...headers },
  body: JSON.stringify({ input: { orderId: 'ord_42', amount: 1999 } }),
})

const { result } = await res.json()
result.runId // 'run-abc~retry~1f4c9e02'
```

The new run inherits the original's workflow, tags and namespace, and starts with a clean history — no checkpoints are replayed. **The original run is left completely intact**, keeping its status, its error and its full timeline as the record of what went wrong.

The link between the two is the run id itself: the new id is `<originalRunId>~retry~<short-uuid>`, and the console parses that suffix to draw the lineage between them. There is no separate parent column.

#### Continuing a breakpoint

`ctx.breakpoint()` parks a run indefinitely at a known point, with a visible `breakpoint` checkpoint in its timeline and no wake timer — a deliberate manual gate rather than a failure. `POST /api/runs/:id/continue` releases it, which is the console's counterpart to calling [`engine.continue(runId)`](/docs/durable/authoring/external-tasks#human-in-the-loop-pauses--ctxbreakpoint) from code.

It answers `404` with `run <id> is not paused at a breakpoint` when the run has no pending breakpoint checkpoint, so the call is safe to fire blindly.

#### Human-in-the-loop: signals, updates and tasks

The runs list already *names* what a suspended run is parked on (the [`waiting`](#the-waiting-state) column); these three verbs let the operator act on it from the console instead of dropping into a REPL:

- **`POST /api/runs/:id/signal`** delivers `{ token, payload? }` to a [`ctx.waitForSignal`](/docs/durable/concepts/sleep-and-signals#signals-human-in-the-loop) rendezvous. It is **guarded**: unless you pass `force: true`, the token must be one the run is *currently waiting on* — a typo'd token would otherwise buffer a stray payload silently instead of resuming anything. A mismatch answers `409` carrying the `waitingOn` token list, so a client can offer the real choices; `force: true` buffers the payload anyway (the reliable-delivery path).
- **`POST /api/runs/:id/updates/:name`** delivers `{ arg? }` to a [`ctx.onUpdate(name)`](/docs/durable/authoring/queries-and-updates#updates) point. The workflow's registered validator arbitrates **server-side**: a rejection answers `422` with the reason, and nothing is delivered.
- **`POST /api/runs/:id/tasks/:name/complete`** (body `{ result? }`) and **`.../fail`** (body `{ error }`, a string; it defaults to `failed from console`) settle an external [`ctx.task`](/docs/durable/authoring/external-tasks#external-async-completion-tasks--ctxtask) — the console equivalents of `engine.completeTask` / `engine.failTask`. The response is honest about delivery: `{ result, delivered: true }` when a live waiter consumed it, `{ result: null, delivered: false }` when no waiter was live *yet* and the completion was **buffered** for the run to consume when it reaches the task's wait — buffered is success, not a 404.

On a store-less `tenant` pod these verbs answer `404`: they need the engine's signal surface. `retry`, `retry-with-input` and `continue` do work there; they ride the wire to the control plane (see [the gateway verbs](/docs/durable/cluster/topology-and-config#reading-and-steering-runs-rungateway)).

#### Bulk actions

`POST /api/bulk/:action` applies one action to **everything a filter matches**, where `:action` is `retry` or `cancel` (anything else is a `400`). The selection comes from the query string, in the same `filter[...]` envelope as `GET /api/runs` — there is no id list to assemble. A refused filter, including a filter field sent bare, is a `400` and acts on nothing:

```
POST /durable/api/bulk/retry?filter[status]=failed&filter[workflow]=charge-order&filter[namespace]=eu-west
POST /durable/api/bulk/cancel?filter[status]=suspended&filter[tag]=stuck&compensate=true
```

`?compensate=true` runs the [saga compensations](/docs/durable/reliability/sagas) and is honoured for `cancel` only.

#### Asking for the saga undo

Both cancel routes read `compensate` from **either** the query string or the JSON body, so `?compensate=true` and `{ "compensate": true }` are equivalent. A value spelled `true` / `1` / `yes` / `on` (or the bare `?compensate`) means yes; `false` / `0` / `no` / `off` means no; absent means no.

Anything else is a `400`. That is deliberate: the two ways to guess at an unreadable value are "skip an undo the operator asked for" and "run an undo they did not", and both would be silent. An explicit rejection is the only answer that cannot mislead.

<Callout type="info">
A compensating cancel answers with the status `cancelling`, not `cancelled`. The undo replays the workflow's saga in the background so the HTTP request never blocks on it: the completed steps' compensations run in reverse order, each visible as a `compensate:<step>` event in the timeline, and the run reaches `cancelled` once they finish — watch the run's [stream](#live-tailing-one-run) or poll it rather than reading the response body as the final state. A plain cancel is terminal in the response itself.
</Callout>

The response is `{ matched, applied }`. `matched` is how many runs the filter returned; `applied` is how many the action actually changed. They differ when a run has already moved on — a run that throws or answers "nothing to do" is skipped rather than aborting the batch.

<Callout type="warn" title="Bulk acts on at most 500 runs per call">
The filter is evaluated with a hard cap of 500 and no paging. A filter matching more than that silently acts on the first 500 — narrow the filter (a tighter `namespace`, a time-bounded `attr`) and repeat, rather than assuming one call drained the backlog. Compare `matched` against `500` to tell.
</Callout>

### Live queries, webhooks and metrics

| Method | Route | Purpose |
| --- | --- | --- |
| `GET` | `/durable/api/runs/:id/events/:key` | the latest value the run published for `key` with `ctx.setEvent` |
| `POST` | `/durable/api/webhooks/:token` | deliver a `ctx.webhook()` callback; the JSON body resumes the waiting run |
| `GET` | `/durable/api/metrics` | Prometheus text exposition of this process's counters plus backlog and worker gauges |

**`GET /api/runs/:id/events/:key`** is a side-effect-free read of a live (or finished) run, the HTTP form of [`engine.getEvent(runId, key)`](/docs/durable/authoring/queries-and-updates). It answers `{ value }`, or `{}` when the run never published that key, and `404` for an unknown run. The value goes through your `redact.checkpoint` hook as the `output` of the `event:<key>` checkpoint, since that is where it is stored.

**`POST /api/webhooks/:token`** resumes a run parked on [`ctx.webhook().wait()`](/docs/durable/authoring/webhooks). It only takes webhook tokens (`wh:<runId>:<seq>`), so it is not a second signal endpoint. A callback for a run waiting on that token resumes it and answers `{ result }`. One that lands before the run reaches `wait()` — the url was handed out, then the run kept going — is buffered and answers `202 { buffered: true }`, as long as the run exists, is not terminal and has not consumed that webhook yet; the later `wait()` consumes it. A callback for an unknown or terminal run, or a duplicate of one already delivered, answers `404` and buffers nothing. Past the 1 MiB payload limit it answers `413`.

<Callout type="warn" title="The webhook route is behind the console's guard">
Like every route here, `webhooks/:token` runs behind `authorize`. A webhook token embeds the run id, which a caller may know, so it is not a secret to rely on. Let the sender through in `authorize`, for example by checking a shared header or a signature for that path, or expose your own public route that verifies the sender and calls `engine.signal(token, body)`. Point `webhookUrl` in `config/durable.ts` at whichever route you choose.
</Callout>

**`GET /api/metrics`** serves `text/plain; version=0.0.4` for a Prometheus scrape:

```text
# TYPE durable_runs_total counter
durable_runs_total{event="completed"} 1284
durable_runs_total{event="failed"} 7
# TYPE durable_steps_total counter
durable_steps_total{event="completed"} 9921
...
# TYPE durable_pending_runs gauge
durable_pending_runs 12
# TYPE durable_running_runs gauge
durable_running_runs 3
# TYPE durable_dead_runs gauge
durable_dead_runs 0
# TYPE durable_group_queue_depth gauge
durable_group_queue_depth{group="reports"} 4
# TYPE durable_group_live_workers gauge
durable_group_live_workers{group="reports"} 0
```

- The **counters** are the [`collectMetrics`](/docs/durable/observability/metrics) counters of the process that served the scrape, started when the dashboard boots. They count only the events that process produced, so scrape every pod and sum: each event is counted once across the fleet. A `tenant` pod has no engine and serves no counters.
- The **gauges** are read at scrape time: `durable_pending_runs` (the dispatch backlog), `durable_running_runs`, `durable_dead_runs` (the dead-letter queue), and per worker group its queue depth and live-worker count. `depth > 0` with `0` live workers is the alert. On a `tenant` pod the run gauges count the tenant's own runs through the control plane, and are left out when the control plane is too old to answer.

### Schedules

| Method | Route | Purpose |
| --- | --- | --- |
| `GET` | `/durable/api/schedules` | the ticked schedules with their live control state and fire windows |
| `POST` | `/durable/api/schedules/:key/pause` | pause the schedule at runtime, fleet-wide |
| `POST` | `/durable/api/schedules/:key/resume` | resume it |
| `POST` | `/durable/api/schedules/:key/trigger` | fire the current window now (idempotent) |

These are the console's Schedules tab, riding [`engine.listSchedules` / `setSchedulePaused` / `triggerSchedule`](/docs/durable/authoring/scheduling#runtime-control--pause-resume-run-now). The listing is a `{ data, meta }` page (`page`, `size` default `100` and capped at `200`), sorted by `key` unless `sort` names `workflow`, `nextFireAt` or `lastFireAt` (`-` for descending); `filter[workflow]`, `filter[namespace]` and `filter[paused]=true|false` narrow it. Each entry carries the cadence (`cron`/`everyMs`/`timezone`), the *effective* `paused` state with a `pausedAtRuntime` flag telling you whether a console override (which wins over config until the next deploy) is in force, the current window's `lastFireAt`/`nextFireAt`/`currentWindowRunId`, and that run's `lastRunStatus` when it exists. `trigger` is idempotent by the window's deterministic run id — triggering a window that already fired returns the existing run rather than forking a duplicate. An unknown `:key` answers `404`; an action other than `pause`/`resume`/`trigger` is a `400`.

### Fleet and topology

| Method | Route | Purpose |
| --- | --- | --- |
| `GET` | `/durable/api/workers` | per-worker heartbeats, grouped by routing token |
| `GET` | `/durable/api/health` | the compact shape: queue depth and a `stalled` flag per group |
| `GET` | `/durable/api/topology` | this pod's topology (as the `role` field), plus its `tenant` when it is a store-less pod |
| `GET` | `/durable/api/compat` | protocol/capability negotiation across the fleet, plus blocked runs |
| `GET` | `/durable/api/workflows/:name/lifecycle` | who starts whom through [lifecycle events](/docs/durable/authoring/lifecycle-events): `{ workflow, startsOnSettle, startedBy, triggerCounts? }` (see [Workflow pages](#workflow-pages)); on a tenant pod only its namespace's subscriptions, `501` when its control plane is older than the verb |
| `GET` | `/durable/api/openapi.json` | the machine-readable API contract (OpenAPI 3.1) |

`GET /api/workers` returns `{ data: GroupHealth[] }` — for each routing token, its queue `depth` and the **individual live workers** with their `instanceId` and `lastBeatAt`. That is what tells "one worker is wedged" apart from "the whole group is down".

On the [BullMQ](/docs/durable/cluster/interop), [queue](/docs/durable/transports/queue#worker-health) and db transports, each worker's heartbeat also carries a live `status` telemetry snapshot (`WorkerStatus`) that the console renders on its worker cards: the concurrency mode and limit (`fixed` or `adaptive`, with `min`/`max`), `inFlight`, RSS (`rssBytes`, plus `rssLimitBytes`/`rssPct` when a ceiling is known), `cpuPct`, `throughputPerMin`, `p95Ms`, and the last adaptive concurrency adjustment with its reason. Workers that beat without one (a thin worker runtime's compact beat) omit `status` — the cards degrade to liveness only.

`GET /api/health` is the compact view of the same data, `{ data: [{ group, depth, liveWorkers, stalled }] }`: it collapses `liveWorkers` to a count and adds `stalled: depth > 0 && liveWorkers === 0`, which suits a probe.

`GET /api/compat` powers the compatibility panel described below: per group, each pod's protocol range and capabilities with a `compatible` / `degraded` / `incompatible` outcome and the exact reason, alongside every `blocked` run and why it parked.

The routes are all named (`durable_dashboard.index`, `durable_dashboard.runs.show`, `durable_dashboard.runs.retry_with_input`, `durable_dashboard.bulk`, …), so you can reference them from your own code or wrap them in middleware.

## What it shows

The sidebar has two groups. **Monitor** holds Runs and Workers. **Operations** holds Schedules, and is empty on a tenant deployment. The brand at the top switches to the other Agora consoles you may open. The topbar holds the organization picker, a run-id quick open and ⌘K search across every console. Below 768px the sidebar opens as a drawer. The theme is remembered per browser.

- **Workers** — the live fleet: one row per pod with its partition, the handlers it serves and its load (in-flight against its concurrency limit, RAM, CPU, throughput, p95 and the adaptive controller's last move). It also lists partitions with their worker, handler, queued and starved counts, queues that have work and no worker, the protocol negotiation of each pod against the control plane, and runs `blocked` for lack of a compatible worker.
- **Runs** — every run with its status, filterable by status, workflow, tag, namespace, [origin](/docs/durable/concepts/workflows-and-steps#run-origin--package-attribution), creation time and search attribute. The tag, tenant and attribute filters are value pickers: they list what the runs actually contain (counted server-side over the rest of the active filter, searchable, paged), take several values at once, and still accept a typed value. `pending` is a run created and enqueued but not yet picked up; a `dead` run carries a distinct badge so a [poison pill](/docs/durable/reliability/dead-letter) is easy to spot.
- **What a suspended run is waiting on** — a `suspended` run parked on a signal, a webhook callback, a child run or a breakpoint is surfaced as **waiting**, with what it is blocked on right in the row (`signal approve`, `child ord-42.child.0`, `breakpoint`). See below.
- **Step timeline** — the selected run's steps in order, tagged by kind (local / remote / sleep / signal), with worker group, queue wait and duration. In-flight steps appear while they run, not only on completion — a remote step in flight reads as `pending`, and a local step's executing body as `running` (the [`trackStepStart`](/docs/durable/concepts/workflows-and-steps#in-flight-visibility) option).
- **Live tail** — the open run streams its events over SSE, so a long run updates without a reload.
- **Children and lineage** — a run's [child workflows](/docs/durable/authoring/child-workflows) are linked from its detail, as is the original of a fix-and-replay run.
- **Lifecycle triggers** — a run started by another run's [lifecycle event](/docs/durable/authoring/lifecycle-events) links back to it ("started by `<run>` on completed / failed"), with the source run's status and, when the source recorded its span ([OpenTelemetry](/docs/durable/observability/otel)), its trace id with a copy button. A settled run with lifecycle subscribers lists them under **Lifecycle subscribers**, one row each (see [Lifecycle subscribers of a run](#lifecycle-subscribers-of-a-run)). Neither end is a child: they are not cancelled or awaited together.
- **Waits on other runs** — a run suspended in [`ctx.waitForRun`](/docs/durable/concepts/sleep-and-signals) shows "Waiting for run `<id>`", linked, with that run's current status, and the run it waits for shows **Awaited by** with each waiting run.
- **Workflow pages** — who starts whom through lifecycle events, per workflow, with each subscriber's started and failed counts. See [Workflow pages](#workflow-pages).
- **Lifecycle pending** — a chip under the tag filter selects the settled runs still tagged `durable:lifecycle:pending`, whose lifecycle event is owed to some subscriber. The registry's `__lifecycle_registry` runs never show.
- **Wide fans** — a fan of more than 50 members draws as one node in the graph and one row in the timeline, labelled `label ×total`, with a segmented progress bar against its declared size, a legend (`done`, `failed`, `running`, `pending`, `not started`), `600 of 40000 started`, and its sampled failures. Once the run has finished (`completed`, `failed`, `cancelled` or `dead`), members still running or pending read as `interrupted` and the ones never sent as `never ran`, marked `(failFast)` when a failFast fan stopped early. A `blocked` or `suspended` run is not finished, so its fans stay in flight. Expanding it lists the members in a virtualized list that pages them in as you scroll, with a failed-only toggle. The run header lists the first 12 children and counts the rest, and only the first 50 children's details are fetched to label their rows.
- **Actions** — retry, cancel, cancel + undo ([saga compensation](/docs/durable/reliability/sagas)), fix-and-replay, redispatch, continue, republish lifecycle event (on a settled run whose workflow has [lifecycle subscribers](/docs/durable/authoring/lifecycle-events#republishing-and-backfilling); a confirm dialog, then how many subscriber runs it started and which failed), the [human-in-the-loop verbs](#human-in-the-loop-signals-updates-and-tasks) (deliver a signal, a validated update, or a task completion), and the bulk equivalents of retry and cancel.
- **Schedules** — the ticked [scheduled workflows](/docs/durable/authoring/scheduling) with their fire windows and effective pause state, plus pause / resume / run-now controls that apply fleet-wide at runtime.
- **Worker cards** — on the BullMQ, queue and db transports, each worker's live telemetry: concurrency, in-flight, RSS/CPU, throughput and p95.

### Workflow pages

The workflow name in a run's header links to that workflow's page (`#/workflow/<name>`), which lists two things:

- **Starts when it settles**: the subscribers of `run.completed:<workflow>` and `run.failed:<workflow>`.
- **Started by**: the workflows whose settling starts this one.

Each entry links to the other workflow's page and is chipped with its `kind` (`on completed` / `on failed`) and what its subscription does: `where`, `input`, `debounce` / `batch` (`by key` when it has a `key`), or `announced` when this instance does not register it and only a live worker announces it (a [Python subscriber](/docs/durable/authoring/lifecycle-events#subscribers-in-python), or a TypeScript one served elsewhere). An announcement names only the event, so an announced entry states no `where`, `input` or coalescing. The same two lists appear on the run detail, under the lifecycle links, when either is non-empty.

When the dashboard serves an engine (not a store-less tenant pod), each "Starts when it settles" entry also shows how many runs that subscriber was started for and how many starts failed (`12 started · 1 failed`), counted by the dashboard's own process since it started, from the same counters as `GET /metrics` (`durable_runs_triggered_total`, `durable_runs_trigger_failed_total`). They count what that process published, not the fleet's total; for the fleet, see the [Telescope Lifecycle section](/docs/durable/observability/telescope) or your metrics backend.

The data comes from `engine.workflowLifecycle(workflow)`, built from the answering instance's registry plus the subscriptions the fleet announces (read at most every 5 seconds). It is a run gateway verb (`workflowLifecycle`) that a tenant proxy carries: on a store-less tenant pod the control plane answers with the subscriptions of the tenant's namespace only (as it does for the run detail's `workflowLifecycle` and `lifecycleSubscribers`), and the page answers `501` while the control plane is older than the verb. Announced entries come from the lifecycle subscription registry and live worker descriptors; the registry's own `__lifecycle_registry` runs never show in the run list.

```json
{
  "workflow": "ingestion",
  "startsOnSettle": [
    { "workflow": "refresh-summaries", "kind": "completed", "local": true, "announced": false,
      "where": true, "input": true, "coalesce": { "mode": "debounce", "keyed": true } },
    { "workflow": "notify", "kind": "failed", "local": false, "announced": true,
      "where": false, "input": false }
  ],
  "startedBy": [
    { "workflow": "upload", "kind": "completed", "local": true, "announced": false,
      "where": false, "input": false }
  ],
  "triggerCounts": {
    "refresh-summaries": { "triggered": 12, "failed": 0 },
    "notify": { "triggered": 0, "failed": 1 }
  }
}
```

### Lifecycle subscribers of a run

A settled run whose lifecycle event goes to some workflow lists each subscriber with where the event stands for it (`lifecycleDeliveries` on `GET /api/runs/:id`):

| State | Means | Links to |
| --- | --- | --- |
| `started` | Its run exists (a `durable:triggered:<subscriber>` tag). | the subscriber's run, with its status |
| `owed` | Still pending (a `durable:lifecycle:owed:<subscriber>` tag), shown as `owed for 2h`. When no live instance registers or announces the subscriber for the run's namespace, also `orphan in 22h`: when the [sweep](/docs/durable/authoring/lifecycle-events#which-subscribers-a-run-owes) drops it. | — |
| `coalesced` | Routed into the subscriber's debounce/batch accumulator (a `durable:coalesced:<subscriber>` tag). | the accumulator run, when the instance registers the subscriber and can compute its `key` |
| `failed` | Its last delivery failed (a `durable:trigger_failed:<subscriber>` tag): its `where` threw, its input was rejected, its start failed, or the sweep dropped it as an orphan. The reason is not stored with the run: the row says so and points at the `run.trigger_failed` event, which the run's **Events** panel shows when it arrives while the page is open. **Republish lifecycle event** retries it, and a start clears the state. | — |
| `not started` | No run and nothing owed: its `where` declined the event, or it subscribed after the run settled. | — |

The rows come from the run's tags and the subscribers of its namespace, plus one batched read of the started runs' statuses. The **Republish lifecycle event** action stays next to them.

### Live events of a run

The run detail has an **Events** panel listing the run's engine events as the live stream (`GET /api/runs/:id/stream`) delivers them, newest first: the time, the type, the step, subscriber or handler it names, and its error. A `run.triggered` links to the run it started and a `run.trigger_failed` names the subscriber and the reason; the `run.started` of a lifecycle-started run links back to its source run, and of a child run to its parent; a child step's events link to the child run. A `run.trigger_failed` that arrives also fills in that subscriber's reason in **Lifecycle subscribers**.

Nothing is stored or fetched for it: it shows what arrives while the page is open, the last 200 events, and starts empty on every load (the empty panel says so). The stream stays open on a settled run too, since a republish or the lifecycle sweep still reports to it, and it carries only what the stream route already sends, so a tenant pod sees its own runs' events as before.

The run detail's `ETag` also covers what it reads from other runs (their statuses, the waits on the run, the fleet's subscriptions), so a subscriber run that finishes changes the source run's detail even though the source run itself did not change.

### The `waiting` state

`waiting` is not a ninth run status — it is a **derived view** of a `suspended` run. The engine records one generic `suspended` status; the listing joins it against the signal-waiter table (`listSignalWaiters`) and reports what the run is parked on:

| `waiting.on` | The run is parked on |
| --- | --- |
| `signal` | a [`ctx.waitForSignal`](/docs/durable/concepts/sleep-and-signals) or `ctx.waitForEvent`; `name` is the signal or event name |
| `webhook` | a [`ctx.webhook().wait()`](/docs/durable/authoring/webhooks) callback |
| `child` | a [child run](/docs/durable/authoring/child-workflows); `name` is the child's run id |
| `breakpoint` | a `ctx.breakpoint()` — a human has to release it |
| `run` | a [`ctx.waitForRun`](/docs/durable/concepts/sleep-and-signals); `name` is the run waited for |

The kind comes from the waiter token's prefix, so no extra store read is needed: `wh:` is a webhook, `child:` a child run, `bp:` a breakpoint (named `breakpoint` rather than its raw `bp:<runId>:<seq>` token), `runwait:` a `ctx.waitForRun` (named by the run it waits for), an `event:` token a `ctx.waitForEvent` (named by its decoded event name), and anything else a signal named by the token itself. `engine.continue` resumes a breakpoint through the same signal machinery.

A `suspended` run with no waiter gets no `waiting` value, and that absence is itself informative: a bare `ctx.sleep`, an in-flight remote step and a run whose wake was lost all fall into that bucket. Use [`durable:runs --stale`](/docs/durable/cli) to separate the last one from the first two.

`waiting` appears on the rows of `GET /api/runs` only, and only when the store exposes `listSignalWaiters` — a store-less `tenant` pod skips it silently.

### Display states

The `waiting` value is one input to a richer **display state** that the runs list and the run detail header both derive the same way, so they always agree. The stored status never changes. The console refines what it shows:

| Display state | Means |
| --- | --- |
| `sleeping` | Parked on a durable `ctx.sleep` timer. |
| `awaiting` | Waiting on a signal, webhook, child run, breakpoint or `onError` failure handler, named e.g. `signal approve`, `webhook wh:…`, `child ord-42.child.0`. |
| `no-worker` | The run's next work is queued on a worker group that has a real backlog (`depth > 0`) and zero live workers. |
| `queued` | A [singleton](/docs/durable/reliability/singleton) run gated behind another in-flight run holding its key, shown as `behind leader <id>`. |
| `blocked` | Shown as its own state, with the reason from `run.error.message`. No *compatible* worker exists, which starting another worker of the same build cannot fix. See [Fleet health](#fleet-health). |
| `cancelling` | A compensating cancel is undoing the saga; the run turns `cancelled` when it is done. |
| `running` | Everything else open or in flight, including a settled step waiting to be replayed with nothing currently blocking it. |

`no-worker` is gated on a **real backlog**, not on zero live workers alone. A worker only heartbeats for a group while it serves it, so an idle group (a run parked on its reconcile timer with nothing enqueued, a schedule between fires) legitimately reports no live workers without anything being stuck. Worker health comes from `GET /api/workers`, so on transports without `groupHealth` (anything but BullMQ, queue and db) nothing ever reads `no-worker`.

### Filter pickers

The tag, tenant and search-attribute filters list the values the runs actually carry, each with a count, and take **several** values at once. A free-text box is usable only by an operator who already knows the tenant name or tag, and a typo there returns an empty list that reads exactly like "no runs match".

- **Options are counted over the runs the *other* filters already select.** Pick a tenant and the tag picker offers that tenant's tags, so a picker never offers a value whose result set is empty. Status is deliberately left out of that scope, so the options don't collapse to the status being viewed.
- **Several values on one axis are ORed, and the axes are ANDed.** For example: these two tenants, tagged either of these two ways. On search attributes that needs the `in` operator (shown as *is any of*), because two equality predicates on one key are ANDed like every other pair and no run has two values for one attribute.
- **Typed text still works.** The offered list is a bounded top-N (tag cardinality grows with the data, since a `singleton:<key>` tag is minted per key), so a rare value can be real and absent from it. Engine-minted tags are listed last.

A tag or tenant chip on a run row **adds** to the selection instead of replacing it, so a "these two kinds of run" view can be built by clicking.

<Callout type="info">
On the Lucid store, counts on the run-table axes (workflow, status, namespace) are exact `GROUP BY`s over the whole matching set. **Tag and search-attribute counts are taken over a bounded scan** of the newest 5,000 matching runs, because those values live in a JSON column and a side table rather than in the row being counted. Treat them as "how common, roughly", not as totals. A store without a native value enumeration (or a store-less tenant pod) gets the same bounded scan for every axis.
</Callout>

### Namespace and origin filters

**Namespace** matches the run's `namespace` (its worker pool) exactly and is pushed down to the store as the `namespace` param on `GET /api/runs` and `POST /api/bulk/:action`. Its default is **every namespace**. The dashboard's read paths are not namespace-scoped, so this is a filter the operator chooses, not a scope imposed on them, and not an authorization boundary either. Selecting several namespaces compares them side by side. To scope the console by customer, see [Organizations](#organizations).

**Origin** (which package declared the run's workflow) is a row of facet chips above the list: `all`, one chip per package, and `app` when any loaded run has none, each with a count. A run with no origin is the app's own workflow (one registered without a package `origin`), as are runs created before the field existed. The row only appears once at least one loaded run has a named package origin: on an app where no workflow declares one, every run is the app's own and there is nothing to choose between. An exact-match store filter can't express "no origin", so the chips are counted over the rows the console has already loaded rather than pushed down. That keeps the `app` count on screen while a package is selected, so the app's own runs never look like they don't exist.

### At scale: paging and list rows

A deployment accumulates runs for as long as [retention](/docs/durable/reliability/retention) keeps them, so the console treats the list as **pages**:

- The console asks `GET /api/runs` for **100 rows at a time** and fetches the next page as the last loaded rows scroll into view. The server defaults `size` to 50 and caps it at 200.
- The list is **virtualized**: only the rows in the viewport are mounted, so a deep page costs the same DOM as a shallow one.
- `GET /api/runs` returns list **rows**, not whole runs: id, workflow and version, status, namespace, origin, tags, timestamps, `recoveryAttempts` and `waiting`. `input`, `output` and `error` are left out, because no row renders them and on a busy deployment they are most of the bytes. `GET /api/runs/:id` still carries all three.

### Dead-letter runs and their links

A run that crash-recovery gives up on after `maxRecoveryAttempts` moves to the terminal **`dead`** status. The console shows it as a first-class status, with a `dead` filter chip and a distinct badge. A dead run stays inspectable and can still be retried from the UI once you've fixed the cause.

When your [`onDead` handler](/docs/durable/reliability/dead-letter#routing-to-a-dlq-workflow) starts a handler run under the id `dlq:<deadRunId>`, the console links the two **both ways**. A `dlq:` run gets a red `dlq` chip in the list and a banner linking back to the dead run. A `dead` run's detail looks up `dlq:<its id>` and, when that run exists, shows a *Dead-lettered* banner with an **open DLQ handler** link.

### Recovering a lost remote step dispatch

A remote step with no `timeoutMs` dispatches its job, persists a `pending` checkpoint and suspends until the worker's result resumes it. If the worker crashed mid-step or the transport dropped the job, the result never comes. By design the reconcile re-drive re-suspends a still-`pending` step instead of re-dispatching it, so a slow worker is never double-run, and the run waits indefinitely.

The timeline flags this instead of drawing it as a healthy in-flight step. A remote step `pending` for more than **10 minutes** is checked against its group's worker heartbeats:

- If a worker beat for the group in the last 90 seconds, the row reads *being worked by `<instanceId>` — heartbeat Ns ago* (plus the worker's in-flight count when it reports one). The dispatch reached a live worker, so wait.
- If no worker did, the row reads *awaiting worker result — dispatched Nm ago, no live worker (possibly lost)*.

A live heartbeat proves the worker *process* is alive, not that the step is progressing. From a lost row you have two ways to recover:

- **Re-dispatch** — `POST /api/runs/:id/redispatch` (the console's *Re-dispatch* action) re-enqueues every `pending` remote step on the run, bumping its `attempts`, so the idempotent step re-runs and its result resumes the run. It is the same as `engine.redispatchPending(runId)`.
- **Broker bridge (BullMQ and queue)** — when a task job reaches a terminal `failed` state with no result (its worker crashed, or it stalled past the broker's stalled-count limit), the transport publishes a retryable failed result for the step, so the engine settles the checkpoint and its normal retry re-dispatches. That bridge lives in the consumer: a worker on another SDK that does not implement it still leaves the step `pending`.
- **Self-heal** — set `remoteRedispatchMs` (and optionally `remoteRedispatchMax`, default `10`) in `config/durable.ts`, and a reconcile pass re-dispatches a remote step still `pending` past the window by itself, recording a `warn`-level `step.redispatched` event on the checkpoint; the `step.started` event of that re-drive carries `redispatched: true`, so an alert can tell "re-driven after a lost worker" apart from "retried after a failure". Once the bound is spent, the step fails with `remote_step_lost`. This is off by default. See [Failure modes](/docs/durable/reliability/failure-modes#lost-remote-dispatch-the-run-suspends-and-nothing-auto-redrives-it) for the window-sizing rules.

## Organizations

With [organizations](/docs/durable/concepts/organizations) turned on, the console shows the runs of
the viewer's own active organization. A viewer with no organization sees an empty console that asks
them to choose one.

To let a viewer see more, return `tenants` from `authorize`: a list of organization ids, or `'*'` for
every organization and the runs that belong to none.

```ts title="config/durable_dashboard.ts"
import { defineConfig } from '@adonis-agora/durable/dashboard'

export default defineConfig({
  authorize: async (ctx) => {
    const user = await ctx.auth.authenticate()
    if (user.isSupport) return { allowed: true, tenants: '*' }
    if (user.isPartner) return { allowed: true, tenants: await user.managedOrganizationIds() }
    return user.isAdmin
  },
})
```

The topbar then shows an **Organization** picker: "All organizations" first, then each organization
by name (the labels come from `tenancy.label` in `config/context.ts`, or authkit). The pick lives in
the URL (`?tenant=org-42`), so a link opens the same view, and each switch is written to the
console's audit hook. While several organizations are shown, each run row names its organization.
Retry, cancel and the other actions only reach runs of the organizations the viewer may see; a
`?tenant=` outside them shows nothing and is audited.

## Switching between consoles

When the app has other Agora consoles (telescope, payments, media, the agent console, the authkit
admin), the durable brand at the top left becomes a menu that links to them. It lists only the
consoles the current viewer may open: each one is asked through its own `authorize`. With no other
console, or none this viewer may open, the brand stays as it is. There is nothing to configure.

<kbd>Ctrl</kbd>/<kbd>⌘</kbd> + <kbd>K</kbd> opens a search across those consoles: a run id opens
the run, a workflow name opens the workflow's page, and the other consoles answer with their own
hits (payments, users, entries).

The menu runs the other consoles' `authorize` on each page load. If yours writes an audit trail,
skip it for these checks: the request carries `ctx.agoraProbe === true` while they run.

```ts title="app/policies/console_access.ts"
export default class ConsoleAccess {
  async authorize(ctx: HttpContext) {
    const allowed = ctx.auth.user?.isAdmin === true
    if (!(ctx as { agoraProbe?: boolean }).agoraProbe) await audit.record('console.open', ctx)
    return allowed
  }
}
```

A console your app mounts by itself can join the menu with `registerAgoraConsole` from a provider's
`boot()`:

```ts title="providers/reports_provider.ts"
import type { ApplicationService } from '@adonisjs/core/types'
import { registerAgoraConsole } from '@adonis-agora/durable/dashboard'

export default class ReportsProvider {
  constructor(protected app: ApplicationService) {}

  async boot() {
    await registerAgoraConsole(this.app.container, {
      id: 'reports',
      title: 'Reports',
      icon: 'generic',
      path: '/reports',
      order: 60,
      authorize: async (ctx) => ({ allowed: ctx.auth.user?.isAdmin === true }),
    })
  }
}
```

## MCP tools

When the app registers `@adonis-agora/agent/mcp_provider`, the console's data is also served to coding agents (Claude Code, Cursor, Claude Desktop) on the app's dev MCP endpoint, `/mcp/agora`. There is nothing to configure here: the tools follow this console's `authorize`, so whoever can open the console can use them, and nobody else. A disabled console (`enabled: false`) serves no tools. The [agent docs](/docs/agent/dev-tools) show how to connect a client.

```sh
claude mcp add --transport http agora http://localhost:3333/mcp/agora \
  --header "Authorization: Bearer $CONSOLE_TOKEN"
```

Reads are listed by default. They return what the console shows, through the same `redact` hooks:

| Tool | What it returns |
| --- | --- |
| `durable_list_runs` | Runs, newest first. Filters: `status`, `workflow`, `tag`, `namespace`, `createdAfter`/`createdBefore`. Paged with `page` and `limit`. |
| `durable_get_run` | One run with its step timeline, children, fans and lifecycle links. Input, output and error over 4 KB are cut; `field: 'run.output'` (or `timeline.3.input`) returns one in full. |
| `durable_list_fan_members` | One page of a wide fan's members (`failed: true` for the failed ones). Paged with `page` and `limit`. |
| `durable_count_runs_by` | How many runs take each value of `status`, `workflow`, `namespace`, `tag`, `attr` or `attr.<key>`. |
| `durable_get_health` | Queue backlog and live workers per group, pending/dead/blocked counts, fleet compatibility. |
| `durable_list_workers` | Every live worker's heartbeat. |
| `durable_list_schedules` | Schedules with their pause state and next fire. Paged with `page` and `limit`. |
| `durable_get_run_event` | The latest value a run published with `ctx.setEvent`. |

The actions are hidden until the app opts in with `devTools: { actions: ['durable'] }` in `config/mcp.ts`:
`durable_retry_run`, `durable_cancel_run` (`compensate` for the saga undo), `durable_continue_run`,
`durable_signal_run` (`payload` as a JSON string), `durable_trigger_schedule` and
`durable_pause_schedule` (`paused: false` resumes). Each one goes through your `audit` hook like a
console action, with the actor `mcp:<caller>` and the method `MCP`.

## Fleet health

When you run a [split or polyglot cluster](/docs/durable/cluster), the console grows a **health and compatibility panel** fed by the [handshake](/docs/durable/cluster/handshake) descriptors and diagnostics events:

- **Per pod** — its protocol version, negotiated level (**compatible** / **degraded** / **incompatible**), and a red flag with the exact reason on a mismatch (e.g. *"no common protocol major: local speaks [1, 1], remote speaks [2, 2]"*).
- **Blocked runs** — runs parked because no live worker advertises a [required capability](/docs/durable/cluster/handshake#capability-aware-routing), so a stuck fleet is diagnosable at a glance rather than a silent hang.

A store-less `tenant` api/dashboard pod serves this same view — its reads proxy to the control plane over the wire, so the panel looks identical whether or not the pod owns a store. `retry` (an in-place retry), `retry-with-input`, `continue`, the value pickers and the list's `waiting` column all ride the wire too. Against a control plane too old to know those verbs, each falls back to what it did before: `retry` re-dispatches the run's pending steps, `retry-with-input` and `continue` answer `404`, the pickers count a bounded listing, and rows carry no `waiting`. Some verbs have no wire equivalent yet and always answer `404` on such a pod: the [human-in-the-loop verbs](#human-in-the-loop-signals-updates-and-tasks) (`signal`, `update`, `tasks/*`), [`events/:key` and `webhooks/:token`](#live-queries-webhooks-and-metrics), and the [schedule controls](#schedules).

## Engine health and admin surface

The console's worker cards and its actions are a thin layer over methods `WorkflowEngine` exposes directly. Import the engine from `@adonis-agora/durable/services/main` when you're scripting an operational task (an ace command, a REPL session) instead of clicking through the console.

**Worker liveness** — `engine.workerHealth(extra?: string[])` returns one `GroupHealth` per worker group. It is the same call behind `GET /api/workers` and the [Telescope](/docs/durable/observability/telescope) worker panel:

```ts
interface GroupHealth {
  group: string
  /** Outstanding jobs in the group's task queue: waiting + active + delayed + prioritized on BullMQ,
   *  pending only on the queue transport, pending + claimed task rows on the db transport. */
  depth: number
  /** Workers with a non-expired heartbeat for this group. */
  liveWorkers: WorkerHeartbeat[]
}

interface WorkerHeartbeat {
  group: string
  /** Stable per-process id (host + pid), so N replicas of a group each show as a distinct worker. */
  instanceId: string
  lastBeatAt: number
  /** BullMQ, queue and db workers: concurrency, in-flight, RSS/CPU, throughput, p95, last adjustment. */
  status?: WorkerStatus
}
```

`depth > 0 && liveWorkers.length === 0` is the actionable alert: work is queued and nothing is consuming it. Pass `extra` to include groups the engine can't derive from its registrations. Only the BullMQ, queue and db transports implement `groupHealth` (queue with a worker-key store), so on other transports the list is empty.

**Bulk and tree operations:**

- `engine.cancelWhere(filter, opts?)` cancels every run matching a run query (workflow, status, tag, namespace, search-attribute predicates), each through the normal `cancel` path: child cascade, optional `{ compensate: true }` saga undo, cancel listeners and the control-plane broadcast. It is the scriptable form of the console's bulk cancel, without the 500-run cap. It returns one `RunResult` per run it cancelled (a run that no longer exists is skipped).
- `engine.deleteRun(runId)` hard-deletes a run and its whole child subtree (checkpoints, signal waiters, search-attribute rows) and returns the number of runs deleted. Unlike `cancel`, the run disappears from the listing. Cancel a live run first, since deleting one mid-flight orphans its worker. For deleting by scope, see [`engine.purgeRuns`](/docs/durable/reliability/retention#purging-on-demand--enginepurgeruns).
- `engine.getRunChildren(parentRunId)` returns the ids a run spawned via `ctx.child` or `ctx.startChild`. The console's run tree and the `cancel` cascade walk the same parent-to-children edge.

**Graceful shutdown** — `engine.drain(timeoutMs = 10_000)` stops the engine picking up new runs and waits for in-flight executions to settle, up to `timeoutMs`, then releases the recovery leases of anything still in flight so the next pod can take over without waiting for them to expire. `durable:work` already drains on stop, so you only call it yourself when you run the engine some other way.

**Cross-instance hooks** — `onEnqueued` and `onCancel` let an instance react to activity from *other* instances over the control plane, without polling:

```ts title="start/durable.ts"
import engine from '@adonis-agora/durable/services/main'

// Pick up a run the instant another pod enqueues it.
const stopEnqueued = engine.onEnqueued((runId) => engine.runOne(runId))

// Cooperative cancellation: abort long in-flight work instead of finishing it just to discard it.
const stopCancel = engine.onCancel((runId) => myWorkerBridge.abort(runId))
```

Both return an unsubscribe function. `onEnqueued` is only useful on instances that should execute runs.

## Calling the API directly

The JSON API is a small, framework-light surface — `listRuns`, `getRun`, `runValues`, `retryRun`, `retryWithInputRun`, `continueRun`, `redispatchPendingRun`, `cancelRun`, `bulkAction`, `getRunEvent`, `deliverWebhook`, `metricsText`, `health`, `workers`, `topology` and `compat`, all exported from `@adonis-agora/durable/dashboard` — so you can build your own UI or operational scripts on the same routes. The full wire contract, human-in-the-loop and schedule verbs included, is published as [the OpenAPI document](#the-openapi-contract):

```ts
// Retry every run that failed on a transient charge error, in one call.
const res = await fetch('/durable/api/bulk/retry?filter[status]=failed&filter[workflow]=charge-order', {
  method: 'POST',
  headers,
})

const { matched, applied } = await res.json()
if (matched === 500) {
  // The cap was hit — narrow the filter and repeat.
}
```

### The OpenAPI contract

`GET /durable/api/openapi.json` serves a hand-written **OpenAPI 3.1** document describing every route above — paths, request bodies, response shapes, the run and checkpoint schemas. It is the single machine-readable statement of the wire contract: generate a typed client from it, diff it in CI to catch a response reshaping, or import it into an API console. It is kept in lockstep with the handlers by a spec that asserts the document matches the registered route table, so it cannot silently drift.

For deep operational health views (success rate, throughput, top failures) inside your existing observability UI, see the [Telescope](/docs/durable/observability/telescope) integration.
