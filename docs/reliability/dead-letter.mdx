Most failures are transient and recover cleanly. But occasionally a run is a **poison pill**: it crashes the process every time recovery picks it up — a deserialization bug, a non-deterministic change, an infinite loop in a step. Left alone, crash-recovery would resume it, crash, resume it again on the next boot, and loop forever, taking the whole instance down with it each time. The dead-letter queue breaks that loop.

## Capping recovery: `maxRecoveryAttempts`

Crash-recovery is **self-healing and periodic**: while a run executes its worker renews a recovery lease, so a crashed worker's lease expires and recovery (`engine.recoverIncomplete()`, called every tick by the [`durable:work`](/docs/durable/cli) loop, or by the embedded loop of `worker: { embedded: true }`) reclaims the orphaned run within ~`leaseMs` — on any instance, not just on the next boot. That's what makes a genuine poison pill visible: it gets picked up again and again. Every time crash-recovery picks up a run that still reads `running` once it holds the lease (it re-reads the run under the lease, so a run that settled after the orphan listing is left alone and never counted), the engine increments that run's `recoveryAttempts` *before* resuming it (so a crash mid-resume still advances the counter).

A run whose remote step is still in flight is not counted. A free run lease doesn't mean anything crashed in that case: the step is on the transport with a worker that holds no run lease. Recovery parks such a run `suspended` on the step's deadline or the `reconcileMs` wake, and the worker's result resumes it. A slow remote step therefore can't burn the budget and be dead-lettered while its worker is still busy.

Set `maxRecoveryAttempts` in `config/durable.ts`, and once a run exceeds it (the pickup that would be attempt `maxRecoveryAttempts + 1`), instead of resuming yet again the engine moves the run to the terminal **`dead`** status with a `max_recovery_attempts` error, releases its lease, and stops touching it:

```ts title="config/durable.ts"
export default defineConfig({
  // … plus your transport/store (see Getting Started)
  maxRecoveryAttempts: 5, // after 5 crash-recoveries, dead-letter the run instead of looping
})
```

Omit `maxRecoveryAttempts` for unlimited recovery (the default). A `dead` run is terminal but **not lost**: it stays fully inspectable in the [dashboard](/docs/durable/observability/dashboard) — its history, its checkpoints, its error — and it can be retried from there (or via [`durable:retry`](/docs/durable/cli)) once you've shipped a fix. A retry (`engine.requeue`) of a `dead` or `failed` run resets its `recoveryAttempts` to 0, so the retried run gets the full budget again. Requeueing a run that is still live keeps its count. The point is that one poison pill no longer keeps the process crashing for every other run.

## Handling dead runs: `engine.onDead`

Parking a dead run is the floor, not the ceiling. Subscribe with `engine.onDead` to be notified the moment a run is dead-lettered — the listener receives the dead `WorkflowRun` (status `dead`, with its error) — so you can do something active: page an on-call engineer, push to a real message queue, or kick off a workflow that handles it.

```ts title="start/durable.ts"
import logger from '@adonisjs/core/services/logger'
import engine from '@adonis-agora/durable/services/main'

engine.onDead((run) => {
  logger.error(`run ${run.id} (${run.workflow}) dead-lettered: ${run.error?.message}`)
  void pager.alert('durable-poison-pill', { runId: run.id, workflow: run.workflow })
})
```

`onDead` returns an unsubscribe function. It fires on the instance that dead-letters the run, which is whichever worker's recovery pass picked the run up — so register the listener in a preload that every worker process loads (`start/durable.ts`), not only in the web process. A listener registered nowhere that runs the worker loop never fires.

The listener is called synchronously and its return value is not awaited. A throw is swallowed so that a broken handler can't break recovery, and a rejected promise goes unobserved, so catch inside it (`void pager.alert(...).catch(...)`). The hook is in-memory: if the process dies between the `dead` write and the call, nothing replays it. For a handler that must not be missed, start a DLQ workflow from it (below) and alert on the `run.failed` event or on `dead` runs in the dashboard as well.

Dead-lettering also goes through the engine's event stream: the transition emits a `run.failed` event whose `error.code` is `max_recovery_attempts`, so [events and interceptors](/docs/durable/observability/events-and-interceptors), OpenTelemetry and Telescope see a dead-lettered run as a failure without any extra wiring. The `dead` status and that error code are what tell it apart from an ordinary step failure.

## Routing to a DLQ workflow

The most powerful option is to route dead runs into a *workflow of their own* — a durable handler that gets all the reliability machinery (retries, steps, its own observability) to triage the failure. Start it from your `onDead` listener with a deterministic `dlq:<runId>` id so a run is never double-handled (`start` is idempotent by run id):

```ts title="start/durable.ts"
import engine from '@adonis-agora/durable/services/main'

// The handler workflow — typed to the original run's input + error.
interface DeadLetter {
  deadRunId: string
  workflow: string
  input: unknown
  error?: { message: string; code?: string }
}

engine.register('dlq', '1', async (ctx, dl: DeadLetter) => {
  await ctx.localStep('alert', () =>
    alerts.page('durable-dead-letter', { runId: dl.deadRunId, workflow: dl.workflow, error: dl.error?.message }),
  )
  const ticket = await ctx.localStep('open-ticket', () =>
    tickets.create({
      title: `Dead-lettered run ${dl.deadRunId} (${dl.workflow})`,
      body: dl.error?.message ?? 'unknown error',
      payload: dl.input, // the original input, ready to replay after a fix
    }),
  )
  return { ticketId: ticket.id }
})

// Route every dead run into it — idempotent by `dlq:<runId>`.
engine.onDead((run) => {
  void engine.start(
    'dlq',
    { deadRunId: run.id, workflow: run.workflow, input: run.input, error: run.error },
    `dlq:${run.id}`,
  )
})
```

### A class-based handler under `app/workflows`

When the handler deserves its own file, write it as an ordinary [`BaseWorkflow`](/docs/durable/authoring/app-workflows) class. It is auto-registered like any other workflow and gets its services through the constructor. Then start it from `onDead` with the `dlq:<runId>` id:

```ts title="app/workflows/pipeline_dlq_workflow.ts"
import { inject } from '@adonisjs/core'
import { BaseWorkflow } from '@adonis-agora/durable'
import type { WorkflowCtx } from '@adonis-agora/durable'
import AlertService from '#services/alert_service'
import TicketService from '#services/ticket_service'

interface DeadLetter {
  deadRunId: string
  workflow: string
  input: unknown
  error?: { message: string; code?: string }
}

@inject()
export default class PipelineDlqWorkflow extends BaseWorkflow {
  static workflow = { name: 'pipeline-dlq', version: '1' }

  constructor(
    private alerts: AlertService,
    private tickets: TicketService,
  ) {
    super()
  }

  async run(ctx: WorkflowCtx, dl: DeadLetter) {
    await ctx.step(this.alerts.page, { runId: dl.deadRunId, workflow: dl.workflow })
    const ticket = await ctx.step(this.tickets.create, {
      title: `Dead-lettered run ${dl.deadRunId} (${dl.workflow})`,
      payload: dl.input,
    })
    return { ticketId: ticket.id }
  }
}
```

```ts title="start/durable.ts"
import engine from '@adonis-agora/durable/services/main'
import PipelineDlqWorkflow from '#workflows/pipeline_dlq_workflow'

engine.onDead((run) => {
  void PipelineDlqWorkflow.dispatch(
    { deadRunId: run.id, workflow: run.workflow, input: run.input, error: run.error },
    { runId: `dlq:${run.id}` },
  )
})
```

### Per-workflow routing

Dead-lettering is usually **per-workflow**: a dead `checkout` run wants a different handler than a dead `pipeline` run. There is one `onDead` hook per engine, so route on `run.workflow` inside it, and send everything you didn't name to a catch-all handler:

```ts title="start/durable.ts"
import engine from '@adonis-agora/durable/services/main'

const handlers: Record<string, string> = {
  pipeline: 'pipeline-dlq',
  checkout: 'checkout-dlq',
}

engine.onDead((run) => {
  const handler = handlers[run.workflow] ?? 'global-dlq' // backstop for everything else
  void engine.start(
    handler,
    { deadRunId: run.id, workflow: run.workflow, input: run.input, error: run.error },
    `dlq:${run.id}`,
  )
})
```

Keep the `dlq:<runId>` id whichever handler you pick. The dashboard relies on that id convention (see below).

Because every start is idempotent by `dlq:<runId>`, a run that gets dead-lettered (and re-detected) more than once still triggers exactly one DLQ run. The DLQ run is a normal durable run — it shows up in the dashboard with its own history, so you can confirm it did its job (alerted, opened a ticket, compensated), then retry the original once it's fixed.

## Dead runs in the dashboard

The [dashboard](/docs/durable/observability/dashboard) links the two ends of a dead-letter by the `dlq:<runId>` id:

- A run whose id starts with `dlq:` gets a red **dlq** chip in the runs list. Its detail page shows a *Dead-letter handler* banner that links back to the dead run it is handling.
- A `dead` run's detail page looks up `dlq:<its id>`. If that handler run exists, the page shows a *Dead-lettered* banner with an **open DLQ handler** link. If it doesn't, no link is shown.

From either end you can walk from a poison pill to its handler and back, check that the handler did its job, and retry the original once it's fixed.

## Retrying a dead run with corrected input

When the cause was bad input, `engine.retryWithInput(runId, input, newRunId?)` starts a fresh run with the same workflow but corrected input — useful for replaying a dead run once you've fixed the data that poisoned it:

```ts
const { runId } = (await engine.retryWithInput(deadRunId, { ...originalInput, fixed: true }))!
```

It is a **new** run with a clean history (`newRunId` defaults to `<runId>~retry~<8 hex chars>`), started with the original run's tags and namespace; the dead run stays as it is, inspectable. It resolves to `{ runId }`, or `null` when `deadRunId` is unknown. When the input was fine and the fix was a deploy, retry the run itself instead (`engine.requeue(runId)` / `durable:retry`), which replays its completed steps and resets `recoveryAttempts`.
