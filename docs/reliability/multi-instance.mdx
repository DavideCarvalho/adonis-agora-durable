Web and worker instances consume the SAME result queue, in competition, and on the `queue` and `db` transports the same heartbeat queue too (a beat is a job or a row that one instance takes). On `bullmq`, heartbeats travel over Redis pub/sub instead, so every instance hears every beat; results are still point-to-point. Each point-to-point delivery lands on exactly one instance:

- **It landed on the dispatcher**: the fast in-memory path — the result resolves (or the heartbeat re-arms the liveness timer) directly.
- **It landed on another instance**: that instance writes the checkpoint — the result (`completeRemoteResult`), or the heartbeat's `lastHeartbeatAt` (at most one write per step per `heartbeatPersistThrottleMs`, default 10s — a `WorkflowEngine` constructor option, not a `config/durable.ts` field) — and, for a result, tries to resume the run, which fails while the dispatcher still holds the lease (the lease covers the whole execution). The dispatcher's in-memory timer doesn't hear it; it reads the checkpoint when the timer fires.

Practical rules:

1. **Steps WITHOUT `timeoutMs` suspend durably**: any instance can resume the run from the checkpoint. This is the dead-pod-proof mode (scale-down/crash/deploy). Combine it with `remoteRedispatchMs` + `remoteRedispatchMax` against a lost dispatch, and with `reconcileMs` (default 5 min) against a lost wake.
2. **Steps WITH `timeoutMs` get fast dead-worker detection.** When the window runs out, the dispatcher re-reads the checkpoint before failing: a completed step resolves with the recorded output; a step whose persisted `lastHeartbeatAt` is still within `timeoutMs` (a beat consumed by another instance) re-arms for the rest of the window instead of failing over a live worker; only a step silent everywhere times out.
3. **A beat consumed elsewhere costs at most one throttle window of extra detection.** Another instance persists a step's beats at most once per `heartbeatPersistThrottleMs` (default 10s), so the newest beat it heard can be up to that much newer than the one on the checkpoint. Once the dispatcher sees a persisted beat it did not hear itself, it allows that much extra silence before timing out — a live worker is never failed over, and a dead one is detected within `timeoutMs` plus the throttle. A single instance (or a dispatcher that heard the beats itself) gets no allowance and detects a dead worker within `timeoutMs`, as before.
4. **Due timers come in batches**: each timer pass loads at most `timerBatchSize` (config option, default 500) due runs, most overdue first, and walks them in a shuffled order, so a recovery wave of thousands of due runs drains over a few ticks and the instances don't contend for the same leases row by row.
5. **Processes that never execute steps should set `consumers: 'never'`** (a pure producer): no point-to-point delivery lands on them, so the race with the worker fleet is over. `durable:work` re-enables consumption for itself via `engine.startConsumers()`. The `queue`, `db` and `bullmq` transports all defer their consumers this way.

## Remote workflow turns

A [remote workflow](/docs/durable/python) advances one turn at a time: the engine sends the run's history to a workflow worker, which replays the body and sends back a **decision**. The decisions queue (`<P>-decisions` on `bullmq`, `<prefix>:decisions` on `queue`) is point-to-point too, so with several engine replicas the replica that takes a decision is often not the one that dispatched the turn. Nothing waits for the decision in memory:

1. **Mark, release, then enqueue.** Before enqueueing a turn, the engine mints a random, globally unique `taskId` (two replicas re-driving the same run never mint the same one), records it on the run (`awaitingDecisionTaskId`), suspends the run and releases its lease. A decision that arrives a millisecond later, on any replica, finds both.
2. **Any replica applies it.** Every engine that registers a remote workflow consumes decisions. The replica that takes one leases the run, checks that it still awaits that exact `taskId`, clears the marker in the same conditional write that claims the turn, and applies the decision — checkpoints, child starts, the settle. A decision for a turn the run no longer awaits (a duplicate redelivery, the late reply of a turn already re-driven) is dropped, so a decision applies at most once.
3. **A wake does not re-dispatch over a turn in flight.** A step result, a signal or a recheck that lands while a turn is out leaves the run alone; the turn's decision is applied as usual and its suspend rechecks what it waits on (`reconcileMs` is the fallback).
4. **A lost decision is re-driven, not failed.** Set `remoteAdvanceSilenceMs` in `config/durable.ts` (or `timeoutMs` on a `RemoteWorkflowExecutor`, per workflow; the shorter wins). A turn with no decision and no run-scoped heartbeat for that long is re-dispatched by the timer poller under a fresh `taskId`, with the same history; the worker's replay is deterministic. Without a window, a turn waits for its decision.
5. **Heartbeats keep a live turn alive.** A worker beats for the run (`{ runId, seq: 0, group }`, no `stepId`) while it replays a turn: the Python `durable-worker` and the bundled TypeScript transports every 5 s. Each beat pushes the deadline forward, throttled to one write per half window, so a long turn is never re-driven while its worker is alive. Keep the window well above the beat interval.

`waitForRun` does not resolve on the suspend of a run awaiting a turn; it waits for the decision. An in-process executor that returns its decision directly (`LocalWorkflowTurnExecutor`) is awaited under the lease instead; with `remoteAdvanceSilenceMs` set, a silent one releases the lease and leaves the run to crash recovery rather than failing it.

The marker is a nullable column of `durable_workflow_runs`, `awaiting_decision_task_id`. `createDurableTables` creates it, and the boot-time `ensureSchema()` adds it to an existing table (with the usual one-time repair warning).
