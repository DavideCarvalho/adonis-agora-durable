By default the engine keeps every run forever. That is the right default for a workflow engine — a run's history *is* the audit trail — but on a busy deployment the terminal runs (`completed`, `failed`, `cancelled`, `dead`) accumulate without bound, and eventually the runs table is the biggest thing in your database. Retention bounds it: declare how long each terminal status is worth keeping, and the worker tick hard-deletes runs past their age — optionally archiving each one first.

## The `retention` config

Set a maximum age per terminal status in `config/durable.ts` — a duration string (`'30d'`, `'12h'`) or milliseconds. Age is measured from the run's **last activity** (`updatedAt`), not its creation:

```ts title="config/durable.ts"
export default defineConfig({
  // … plus your transport/store (see Getting Started)
  retention: {
    completed: '30d', // the happy path is cheap to keep and cheap to drop
    cancelled: '30d',
    failed: '90d',    // failures are evidence — keep them longer
    dead: '180d',     // a poison pill's post-mortem window
  },
})
```

Every field is optional and an omitted status is kept forever — so `retention: { completed: '7d' }` alone drops old successes and touches nothing else. Omit `retention` entirely (the default) and nothing is ever deleted.

Durations go through the same parser as every other duration option: a number is milliseconds, a string is `<number><unit>` with `ms`, `s`, `m` (**minutes**), `h`, `d` or `w` (long forms like `'7 days'` work too). A malformed string (`'1 month'`, `'7dayz'`) throws when the provider builds the engine, so a typo fails boot instead of quietly never pruning.

## Scoped policies — one tenant, one kind of run

The per-status ages apply to every run the worker sees. `retention.policies` adds **scoped** rules next to them: each one hard-deletes terminal runs in its `statuses` that match its `scope` once their last activity is older than `maxAge`. The scope is the identity axes of a run query — `namespace`/`namespaces`, `workflow`/`workflows`, `tag`/`tags`, and search-attribute `attributes`:

```ts title="config/durable.ts"
export default defineConfig({
  retention: {
    // The default for everything…
    completed: '30d',
    failed: '90d',
    policies: [
      // …but chat turns are throwaway after a day,
      { statuses: ['completed', 'cancelled'], maxAge: '1d', scope: { tags: ['chat'] } },
      // and one noisy tenant keeps its successes for a week.
      { statuses: ['completed'], maxAge: '7d', scope: { namespace: 'acme' } },
    ],
  },
})
```

Every policy needs all three fields — `statuses`, `maxAge` and `scope`. Only the terminal statuses (`completed`, `failed`, `cancelled`, `dead`) count; any other status in `statuses` is ignored, because pruning a live run would race the engine. Each per-status age and each policy is its own pass over the store, so a run matched by several rules is deleted by whichever one is strictest.

A scope matches each run by its **own** row. Children inherit their parent's `namespace` but not its `tags`. The child subtree is deleted along with a matched parent anyway, but a child is only matched *on its own* through a scope that fits it, so use `namespace` or `workflows` (listing the child workflows too) when a whole run tree has to age out on one clock.

<Callout type="info" title="Namespaced workers sweep only their partition">
A worker whose config sets `namespace` only ever prunes that namespace. The per-status ages are confined to it, and a policy whose `scope.namespace` names a *different* namespace is skipped. A worker with no `namespace` (the operator) sweeps every partition.
</Callout>

## How the sweep runs

The sweep (`engine.sweepRetention()`) is a phase of the [`durable:work`](/docs/durable/cli) tick — the same loop that drives recovery, timers and schedules — self-throttled to **one pass per minute per instance**, so calling it every tick is a no-op most of the time. Each pass is bounded (100 candidates per status), so a large backlog drains across passes rather than stalling a tick. Deletion is a *hard* delete: the run, its checkpoints, its signal waiters and search-attribute rows, and — cascading down — its entire child subtree go with it. A deleted run's count includes that subtree. Each pass collects its runs and their subtrees (children first) and deletes them in one call to the store's optional `deleteRuns`, a few `IN (...)` statements in one transaction, instead of four statements per run; a store without `deleteRuns` gets one `deleteRun` per run. If the batch delete fails, the whole pass is kept and the next pass retries it. With [`eventBufferTtl`](/docs/durable/api-reference#durableconfig) set, the same pass also deletes buffered events older than the TTL, in batches of 500.

<Callout type="warn" title="Eviction cascades down, not up">
Deleting a run takes its **children**, but the sweep does not know about a still-live *parent* awaiting a custom-id child — a completed child evicted out from under a suspended parent strands the join. Size the ages well beyond your longest-running parents.
</Callout>

Retention only runs inside `durable:work`. A web process, a `node ace` one-off or anything else that boots the engine never prunes, and while the engine is draining for shutdown the sweep is skipped.

## Archiving before deletion — `engine.onEvict`

Retention deletes; `onEvict` is how you keep a copy. Register a hook and it runs **before** each run's deletion, receiving the run and its full checkpoint timeline — write them to S3, a cold table, a file:

```ts title="start/durable.ts"
engine.onEvict(async (run, checkpoints) => {
  await s3.putObject({
    Bucket: 'durable-archive',
    Key: `${run.workflow}/${run.id}.json`,
    Body: JSON.stringify({ run, checkpoints }),
  })
})
```

Hooks are awaited in registration order, and a hook that **throws skips that run's deletion** — the run stays in the store and the next sweep retries it. A broken archive can therefore never lose data; the failure surfaces as a warning log, not a silent gap in the archive. `onEvict` returns an unsubscribe function, like every other engine listener.

<Callout type="info">
The archived `{ run, checkpoints }` pair is the same shape the [replay fixture](/docs/durable/testing#replay-ci--assertreplayable) uses — an archived run can be fed back through `parseRunHistory` and `assertReplayable` later.
</Callout>

## Purging on demand — `engine.purgeRuns`

Retention ages history out. Sometimes you need everything for a scope gone *now*: a tenant deleted their account, or a feature's data is being wiped. `engine.purgeRuns(scope, opts?)` hard-deletes every run matching a scope (the same scope shape as a retention policy) in bounded batches, and `engine.purgeNamespace(namespace, opts?)` is the shortcut for one tenant:

```ts title="app/services/tenant_offboarding.ts"
import engine from '@adonis-agora/durable/services/main'

await engine.purgeNamespace('acme')                    // every run a tenant/partition owns
await engine.purgeRuns({ tag: `tenant:${tenantId}` }) // or any other scope
```

- **Live runs** in the scope are cancelled first (a plain cancel with no saga undo), then deleted. Pass `cancelLive: false` to leave live runs, and live descendants of finished ones, alone and delete terminal history only.
- **Child runs** are deleted with their root even when they don't match the scope themselves. Pass `children: false` to delete exactly the matching runs.
- `batchSize` (default `500`) bounds each round, and rounds repeat until the scope is empty. Each round's runs are deleted with one `deleteRuns` call when the store has it.
- An **empty scope is rejected**, because it would delete every run in the store.
- `onEvict` hooks are **not** called. A purge is an explicit delete, not retention, so archive first if you need a copy.

It returns how many runs were deleted, children included.

## Dashboard implications

A deleted run's history is gone. You can't drill into a `completed` run from three weeks ago if `completed` is capped at 14 days, and there is no undo. That trade is deliberate: retention gives up long-tail auditability for a bounded runs table. Size each age around how long you actually need to debug or audit that outcome, not around "just in case", and use `onEvict` when you need both.

## Operational guidance

Because ages are set **per status**, different outcomes can be kept for different lengths of time. A reasonable starting point:

- `completed` / `cancelled` are the "nothing to see here" outcomes. A couple of weeks is usually enough to answer "did this run, and when".
- `failed` / `dead` are the outcomes you actually investigate. Keep them longer (`'90d'` or more), since a failed or dead-lettered run is exactly the history you'll want when debugging weeks later.

Start with long ages and tighten them once you've confirmed nothing depends on the older history. Pruning can't be undone, and leaving `retention` off costs nothing until table growth becomes a real problem.
