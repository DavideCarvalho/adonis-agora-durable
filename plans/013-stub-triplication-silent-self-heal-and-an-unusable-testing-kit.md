The DDL now exists in **three** places: `lucid-schema.ts`, the stub, and a copy in
every consumer's `database/migrations/`. Plan 008 fixed the second; nothing stops

### The correction to plan 004 — read this before deciding

Plan 004 tried exactly the deduplication this item wants: rewrite the stub as
`await createDurableTables(this.db)`. It was **REJECTED** because
`createDurableTables` calls `db.connection(name).schema`, and `BaseSchema.db` is a
`QueryClientContract`, which has no `.connection()`. That mechanism finding is
correct and was independently verified against `@adonisjs/lucid@22.4.2`.

**But the conclusion "that cannot work" was too broad, and the consumer just
disproved it.** meuprontoo's new
`database/migrations/1785100000000_converge_durable_tables.ts` calls
`createDurableTables(db, this.db.connectionName)` where `db` is imported from
`@adonisjs/lucid/services/db` — the `Database` manager, not the schema's client.
It runs, and the app's suite is green at 526. The repo already had that idiom and
its rationale in `1784800000000_seed_email_change_no_password.ts:37-47`.

So the drift-proof stub **is** achievable; 004 just reached for the wrong handle.
Read meuprontoo's file before writing yours — it is the working exemplar:
`/home/dudousxd/personal/exames-monorepo-worktrees/adopt-oidc-guard/apps/meuprontoo/database/migrations/1785100000000_converge_durable_tables.ts`

**What you must decide and justify:** a stub that calls into the library is no
longer a DDL snapshot, so a later version bump changes what a *fresh* database
gets from an *old* migration file. The consumer accepted that trade (the schema
belongs to the library; `createDurableTables` only ever adds tables and nullable
columns). Decide whether this library should make the same trade for everyone.
If you conclude the snapshot property is worth keeping, then item A becomes "add a
test that fails when the stub and `createDurableTables` disagree" — which is the
weaker but still-real fix. **Either is acceptable; a silent third copy is not.**

## Item B — the self-heal made the drift undetectable

Two individually reasonable behaviours combined to hide item A completely:

- `ensureSchema` (`src/stores/lucid-schema.ts`, the `hasColumn` branches around
  `:97-118`) silently `ALTER`s missing columns in at boot, and the provider calls
  it whenever `autoSchema !== false` (`providers/durable_provider.ts`, near the
  `store.ensureSchema?.()` call).
- `persistHeartbeat` (`src/engine.ts`, around the `recordStepHeartbeat` call) ends
  in `.catch(() => undefined)`, documented as "a lost liveness update never harms
  the run".

So the heartbeat write failed silently *and* the column got added silently, and
nothing anywhere could surface that a migration-managed schema was wrong.

**Make the self-heal audible.** When `ensureSchema` actually applies an `ALTER`
(not when it no-ops), that is information the operator wants: it means the
migration-managed schema is behind the library. A `warn` naming the table and
columns is enough. Do **not** make it throw, and do not change `autoSchema`'s
default — apps depend on the repair today, including at least one in production.

The distinction that matters: warn only on **applied** repairs. A warning that
fires on every boot regardless is noise that gets filtered, and then this item has
achieved nothing.

## Item C — `@adonis-agora/durable/testing` is unusable outside vitest

The `testing` barrel imports `vitest` unconditionally, so a Japa-based app cannot
import `createTestEngine` / `assertRunStatus` / `assertStepsRan`, and the
package's `exports` map blocks deep-importing the real file to get around it.

meuprontoo documents this at `tests/functional/exam_ingest.spec.ts:16-38` and
maintains a hand-built harness because of it. **That note was written against
0.8.0 and is still true at 0.19.2** — eleven minors later. A testing kit that a
whole class of consumers cannot import is not shipping.

Locate the unconditional import, and decide the split: the assertion helpers
almost certainly do not need a test runner at all, and only whatever genuinely
needs `vitest` should live behind a subpath (or a lazy import). Verify what
actually requires it rather than assuming the whole barrel does.

**The acceptance test is a consumer, not a unit test.** A spec inside this repo
runs under vitest and therefore cannot prove the fix. Prove it by importing the
helpers from a Node process with no vitest in scope — that is the only shape of
evidence that means anything here.

## Steps

### A1 — Decide, and say so before implementing

State which of the two shapes you chose (stub calls `createDurableTables`, or stub
keeps the DDL plus a drift test) and why. If you pick the first, read the consumer
exemplar first and say what you took from it.

### A2 — Implement, and prove the stub works

A stub that does not run is worse than a stale one. Prove it end to end: generate
the migration into a scratch app or exercise the stub's rendered output against a
real SQLite/Postgres connection, and show the six tables plus the two heartbeat
columns exist afterwards. Report how you proved it, not just that you did.

### A3 — Guard the drift, whichever shape you chose

If the stub now calls the function, the drift is structurally impossible and a test
would be theatre — say that instead of writing one. If the stub still holds DDL,
the drift test is the deliverable, and it must fail when you remove a column from
one side. Prove it fails.

### B1 — Warn on applied repairs only

Implement, then test both directions: a schema already correct → **no** warning; a
schema missing the heartbeat columns → exactly one warning naming table and
columns. The negative case is the one that matters.

### B2 — Mutation

Make the warning unconditional → the "already correct" test fails. That split
proves the test distinguishes applied from no-op, which is the whole point of B.

### C1 — Find what actually needs vitest

Report the import and which exports genuinely depend on it. If the assertion
helpers do not, say so plainly.

### C2 — Fix, then prove it from outside

A Node process with no vitest available imports the helpers and uses them. Show
the command and its output. A vitest-hosted spec cannot prove this and does not
count.

### Final

`pnpm build`, `pnpm typecheck`, `pnpm lint`, `npx vitest run` vs 976|19.

Changeset: **patch** for B; **minor** if C changes the `exports` map or moves an
export. For A, the text must tell an existing consumer whether they need to do

## Maintenance notes

- **Item A is the strongest argument yet for auditing consumers.** From inside
  this repo, plan 008 looks like a complete fix: the stub is correct on this
  branch. From the consumer, you can see that the fix does not reach anyone who
  already ran `configure` — their migration file is a frozen copy of the old stub,
  and it is only the silent self-heal that keeps their app working. A fix to a
  generator does not fix what it already generated.
- **Item B is the mechanism that let A hide.** Two defensive behaviours, each
  correct alone, combined into an information vacuum. Worth a habit: whenever
  something self-repairs, ask what would have told you it was needed.
- **Plan 004's rejection is a useful failure to keep.** It was right that
  `this.db` cannot reach `.connection()`, and it generalised that into "the
  approach cannot work", which closed the door on a design that a consumer opened
  eleven months of versions later with a two-line import change. Record the
  mechanism, not the verdict.
