**Plan 004 was blocked, and its approach is disproved.** It instructed the

> **CORRECTION (plan 013, 2026-07-29). The mechanism above is right; the
> conclusion "that cannot work" was too broad, and it closed the door on a design
> that does work.** `this.db` is indeed the wrong handle — but it is not the only
> handle. `@adonisjs/lucid/services/db` *is* the `Database` manager, and `this.db`
> is still useful for the connection NAME:
>
> ```ts
> import db from '@adonisjs/lucid/services/db'
> await createDurableTables(db, this.db.connectionName)
> ```
>
> A consumer (meuprontoo) shipped exactly that, eleven minor versions later, after
> the door had been closed here. Plan 013 adopted it for the stub and proved it end
> to end: rendered stub → real `MigrationRunner` → real SQLite → six tables, both
> heartbeat columns, a heartbeat round-trip through `LucidStateStore`, then a clean
> rollback (`test/fixtures/stub-migration/run.mjs`, driven by
> `migration-stub-runs.spec.ts`). Two constraints 004 could not have known:
> `services/db` only works inside a **booted** app (its module body resolves
> `container.make(Database)` off the app service), which migrations are; and the
> stub needs `static disableTransactions = true`, because the DDL runs on a

> **The transferable lesson: record the mechanism, not the verdict.** "`this.db`

> extrapolation from one failed handle to the whole design, and it cost eleven
> releases of a stub that only worked because a silent self-heal patched every
> consumer's database at boot.

## Findings considered and rejected

Recorded so they are not re-audited on the next pass:

- **Import cycles.** A naive scan reports 33, including 11 variants of
  `interfaces.ts → workflow-ref.ts → engine.ts → interfaces.ts`. All are
  `import type` and are erased at compile time; a value-import-only graph
  returns zero cycles. No initialization-order hazard exists.
- **Determinism of replay.** Checked specifically for `Date.now()`,
  `Math.random()`, `new Date()` and unordered iteration reachable from workflow
  bodies. None found — `ctx.now`/`ctx.sideEffect` checkpoint through
  `localStep`, bounded waits stamp their deadline once, and `gatherCalls`
  reserves a contiguous seq block in list order.
- **Dashboard authentication.** HMAC-SHA256 session cookie with a
  length-guarded `timingSafeEqual`, a correct open-redirect guard, uniform login
  failures (no user enumeration), `HttpOnly` + `SameSite=Lax` + conditionally
  `Secure`, and a default `authorize` hook that denies in production. Sound.
- **`pnpm audit` advisories.** Not run — blocked by the broken pnpm pin (plan
  001). Recorded as a gap, not a clean bill of health: re-run after 001 lands.
  The package's published runtime dependency surface is only `zod` and
  `@standard-schema/spec`, so exposure is expected to be small, but that is
  inference rather than measurement.
- **Durable-entity history growth.** The entity runner never continues-as-new,
  so a hot key's replay cost grows with operation count. This is an explicitly
  documented tradeoff in `docs/authoring/entities.mdx:211-213` with the correct
  mitigation (shard the key) — a settled decision, not a defect.

## Reported but NOT planned

These were surfaced during the audit and are real enough to record, but were not
selected for planning and — importantly — were **not** independently verified by
the advisor. Treat each as a lead to confirm, not a fact:

- `releaseRunLock(runId)` takes no owner argument, so no store can enforce lease
  ownership on release; and the boolean `renewRunLock` returns is discarded at
  `engine.ts:2124-2131`. Together these reportedly let a stalled worker wipe a
  live lease held by another instance.
- `resume()` admits `failed` runs (`engine.ts:1087`), reportedly letting a late
  child signal replay a failed parent and re-run its saga compensations.
- The default in-memory admission queue reportedly removes a waiter only on a
  successful admit, so an abandoned waiter can permanently deadlock the queue.
  The Redis backend prunes by TTL; the default one does not.
- The `db` transport's 30s claim lease is reportedly never renewed while a
  handler runs, so any step slower than 30s can be claimed and executed twice.
- Several unbounded queries on the poll path (`dueBlockedRuns`, `sweepTimeouts`,
  `listSignalWaiters('child:')`) reportedly issue full table scans every tick.
- `engine.ts` is 3,411 lines with 43 private fields — measured, not disputed. A
  split is the right long-term move but must come *after* 006's tests exist as a
  safety net.

Plan 006's "Maintenance notes" section carries the first two of these in more
detail, since they share the primitive it introduces.

3. **Step 1's STOP was too eager.** "If the full suite passes twice, STOP" would

### The finding this surfaced — `configure-export.spec.ts` never runs in CI

Chasing defect 1 revealed something worse than the flake. In `turbo.json` the
`test` task is `"dependsOn": ["^build"]` — **upstream** packages' builds, not
this package's own. And `.github/workflows/release.yml` runs `pnpm install`,
`lint`, `typecheck`, `test`, with **no build step before `test`** (grep for
`build` in that file returns nothing).

So on a fresh CI checkout `packages/adonis/dist/` does not exist, the
`existsSync` guard fires, and the spec **silently skips**. The only reason it
runs locally is that a developer's `dist/` happens to be lying around from an
earlier build.

That means plan 002's regression guard — the thing that catches
`node ace add @adonis-agora/durable` being a no-op, which is the exact bug that
shipped — **provides no protection in CI, including in the release gate plan 007
just installed.** A green release run does not mean the `configure` export
survived; it means the check was skipped.

This is the same shape as the `accountStore?` finding in adonis-authkit
(plan 010 there): **a guard that degrades to a no-op when a precondition is
missing is invisible when it is missing.** Two independent instances in one
session is a pattern worth naming.

Plan 011 should either add a build step before `test` in the release workflow, or
change the `it.skip` into a hard failure when `dist/` is absent in CI (`process.env.CI`),
or make the `test` task depend on this package's own `build`. The third is
probably right, but it needs checking against turbo cache behaviour — and note
that `turbo` is untrustworthy for verifying this class of change (see the
telescope notes; the native binary and dist artifact are not tracked inputs).

### The plan's Step 2 recipe cannot succeed, and fails in the misleading direction

Plan 011 said to verify route (a) with `rm -rf packages/adonis/dist` then
`pnpm test --force`. Run literally, turbo *does* run the build — the `tsc` line
is visible in the log, cache bypassed — and `dist/src/index.js` still does not
appear. An executor following the plan would conclude route (a) is broken, fall
through to route (c), edit `release.yml` needlessly, and leave `ci.yml` broken.

Cause, isolated with three controlled runs rather than guessed:
`tsconfig.base.json` sets `"incremental": true` and `packages/adonis/tsconfig.json`
sets `"tsBuildInfoFile": ".tsbuildinfo"` — a **dotfile**, invisible to a casual
`ls` and unmatched by `ls *.tsbuildinfo`. Delete `dist/` without it and tsc
believes every output is current and emits nothing. The `copy:stubs` half still
runs (plain `cp`), so you get a `dist/` holding `assets/` and `stubs/` and **zero
JavaScript** — a build that looks like it ran.

Correct recipe: `rm -rf packages/adonis/dist packages/adonis/.tsbuildinfo`.

A near-miss worth recording: both workflows run `pnpm typecheck` before
`pnpm test`, and typecheck shares that same buildinfo file with build. Had
TypeScript not distinguish a `--noEmit` buildinfo, route (a) would have shipped a
**false red** — the new hard failure firing on every CI run. TS 5.9.3 does
distinguish it, so this is safe, but nothing in the plan established that and it
is not self-evident.

### Follow-up opened as plan 012

`turbo.json`'s `build` declares `outputs: ["dist/**"]` and not the buildinfo,
while `typecheck` declares `outputs: ["*.tsbuildinfo"]` — a glob that does **not**
match the dotfile the config actually writes. So turbo can restore a cached
`dist/` while the buildinfo drifts, or the reverse. Combined with the no-emit
behaviour above, that is a live "build silently produces nothing" hazard for
anyone who removes `dist/` by hand.

### Minor

`pnpm lint` is `biome check .`, not a turbo task, so the dispatch instruction
"always pass `--force` to turbo" does not apply to it (`no such flag: --force`).

test", because the snapshot property the DDL copy nominally buys is already a
fiction: `autoSchema` defaults to on, so `ensureSchema()` → `createDurableTables`
converges the database to the installed library at every boot regardless. Keeping
a snapshot does not give a consumer a pinned schema; it gives them a migration
history that disagrees with their database. See the CORRECTION note under plan
004 above for the mechanism and the proof.

The old `migration-stub-schema.spec.ts` (column-list diff) was replaced rather
than kept: it only covered `durable_step_checkpoints`, so a drift in
`durable_workflow_runs` would have sailed past it. It now guards the property
that makes drift impossible — no DDL in the stub, delegation to the two public
functions, manager from `services/db`, transaction opt-out — and a new
`migration-stub-runs.spec.ts` covers the risk the trade introduces: a DDL
snapshot could go stale but never fail to RUN.

**Verified for the changeset's advice:** the *published* stub (`origin/master`)
differs from `createDurableTables` on **exactly** the two heartbeat columns, and
on nothing else — all 6 tables, all columns, all indexes compared
programmatically. So "your database already has the right shape thanks to the
self-heal; a convergence migration is about recording it, not repairing it" is
accurate, and plan 013's STOP condition 4 does not fire.

**Item B — the self-heal warns on applied repairs only.** `createDurableTables`
takes an optional third arg (`{ logger }`), collects every `<table>.<column>` it
actually `ALTER`ed, and emits ONE `warn` at the end, or none. Default sink is
`console`, which is not laziness: `LucidStateStore.ensureSchema()` is the boot
path and has no logger to pass, so a no-op default would make item B audible only
to callers who already knew to look. Mutations both ways: `if (repairs.length > 0)`
→ `if (true)` fails the three "says nothing" tests and passes the three positive
ones; deleting the heartbeat `repairs.push` is the exact mirror. The
fresh-database STOP condition does not fire — a `createTable` never reaches a
`hasColumn` branch, proven by the A2 harness staying silent on a fresh database.

stopped importing `vitest` in **0.9.0** (PR #10), which moved the two conformance
generators to `/testing/conformance`. The plan's "still true at 0.19.2" came from
a consumer's code comment written against 0.8.0 and never revisited — a reminder
that a consumer's comment dates from when it was written, not from the version it
sits next to. Verified against the built dist: `testing-kit/index.js` reaches no
bare specifier but `node:` builtins; `conformance.js` reaches `vitest` via
`state-store-conformance.js`.

What *was* missing was evidence at the level where the promise is made, so C
shipped as a consumer-shaped acceptance test: the built package copied (never
symlinked — Node resolves symlinks, so a symlink resolves `vitest` from the repo's
